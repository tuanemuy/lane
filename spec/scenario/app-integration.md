# アプリの連携

開発者が実装した表示アプリとスクリプトが、トークンで CMS に接続する。サイト訪問者は表示アプリを通じてコンテンツを閲覧し、フォームを送信する。用語は `spec/requirements.md` の 1 章に従う。

このカテゴリーの利用者は管理画面を使わない。開発者の操作は、アプリのコードの記述と、表示アプリ・スクリプトの実行である。CMS の応答は、アプリが型付きで受け取る結果とエラーである。

`spec/scenario/index.md` の「共通の規則」に加えて、このカテゴリーの全シナリオに次を適用する。

- トークンの範囲は、ワークスペース全体、または選んだモデル・フォームの集合である
- 容量や処理能力の上限で受け付けられない要求には、混雑または利用量の制限を理由とする失敗を返す。アプリは時間を置いて同じ要求を送り直す
- スキーマの反映が確定するまで、取得は反映前の構造の内容を返す。一つの取得結果に反映前後の構造を混在させない

## APP-01 アプリに接続を初期設定する

- **利用者**: 開発者
- **目的**: 表示アプリとスクリプトが、取得・送信のたびに接続と認証を記述せずに CMS を呼び出せるようにする
- **要件**: 2, 3.2, 9.3

### 正常系

1. 開発者は、アプリの実行環境からトークンの種類と許可を決める

   | 実行環境 | トークンの種類 | 許可 |
   | --- | --- | --- |
   | SSG（ビルド時） | サーバー用 | 公開取得。下書きを確認するビルドではプレビュー取得 |
   | SSR・サーバー側の処理 | サーバー用 | 公開取得、プレビュー取得、フォーム送信 |
   | ブラウザ（SPA など） | ブラウザ用 | 公開取得、フォーム送信 |
   | スクリプト | サーバー用 | スキーマ反映、コンテンツ管理 |

2. 開発者は、決めた種類と許可のトークンを得る。本番の配信・受付・反映に使うトークンは、アプリ連携の権限を持つメンバーが手動発行する（WS-06）。開発者自身の作業に使うトークンは、認証を経て得る（AUTH-06）。手元の設置では初期構成で宣言したトークンを使う（HOST-02）
3. 開発者は、サーバー用トークンを値を秘匿できる環境に保管する。ブラウザ用トークンは表示アプリの配布物に含める
4. Next.js と React の表示アプリ、およびスクリプトでは、開発者は SDK を使う。アプリのコードで、接続先、トークン、スキーマの定義を SDK に一度だけ指定する
5. 以後、開発者はモデルとフォームのキーを指定して取得・送信を呼び出す。取得結果、送信内容、入力エラーにはスキーマから得た型が付く。呼び出しごとに接続と認証を記述しない
6. SDK を使えない表示技術の開発者は、開発者向けの文書が示す HTTP API を直接呼び出す。接続先とトークンをアプリの設定に一度だけ置き、文書が示す方法でトークンと APP-07 の識別子を要求に添える。トークンと識別子の添え方、応答の意味は SDK と同じである
7. ブラウザで動くコードは、ブラウザ用トークンで公開取得とフォーム送信を直接呼び出す。サーバー用トークンをブラウザへ渡さない
8. 本番と検証を切り替えるとき、開発者は指定するトークンを切り替える。別の設置へ接続するときは接続先も切り替える。アプリの操作対象は、トークンを発行したワークスペースになる
9. トークンを入れ替えるとき、開発者は新しいトークンをアプリに指定して配信し、古いトークンの失効を、アプリ連携の権限を持つメンバーに依頼する（WS-07）。配信と受付は止まらない

### 異常系

- **入力エラー**: 接続先またはトークンの指定を誤ると、最初の要求が失敗する。開発者は指定を直す
- **権限不足（ブラウザ用トークン）**: ブラウザ用トークンでのプレビュー取得、スキーマ反映、コンテンツ管理は常に拒否される。開発者は、これらの操作をサーバー側へ移す
- **権限不足（利用元の限定）**: 利用元を限定したブラウザ用トークンを、許可していない利用元から使うと拒否される。開発者は、アプリ連携の権限を持つメンバーに、そのトークンの利用元の限定の変更を依頼する（WS-07）。トークンの値は変わらないので、表示アプリを配信し直す必要は無い
- **利用量の制限**: ブラウザ用トークンの利用量が制限を超えると、利用量の制限を理由とする失敗が返る。表示アプリは時間を置いて要求を送り直す。フォームの送信では、APP-08 の「混雑・送信制限」のとおり、受付失敗として返る

## APP-02 公開コンテンツを単件で取得する

- **利用者**: 開発者（表示アプリ）
- **目的**: 表示アプリが、一件の公開コンテンツを型付きで得て表示する
- **要件**: 3.1, 3.2, 3.3, 4.2, 4.4, 6.3

### 正常系

1. 表示アプリは、公開取得の許可を持つトークンで、モデルのキーと対象の指定を添えて取得を呼び出す。対象は、コンテンツID、または一意な項目のキーとその値で指定する。単一モデルでは対象を指定しない
2. CMS は、該当するコンテンツの公開内容を返す。結果には、コンテンツID、作成日時、公開内容の更新日時を含む
3. 表示アプリは、結果を現行スキーマの型で扱う
4. メディアの項目では、元の画像と各派生形式について、配信先、画像形式、幅、高さを受け取る。表示アプリは、表示する場所に合う派生形式を選ぶ。配信先は、CMS が管理する配信を指す。資格を示さない要求に返す内容と、内容の保持の規則は、[media.md](media.md) の「共通の規則」に従う。同じ配信先の内容は変わらない。表示アプリ、その CDN、ブラウザは、内容を長く保持できる
5. 生成が終わっていない派生形式と、生成に失敗した派生形式は、生成済みとして返らない。表示アプリは、その派生形式の代わりに元の画像を使う。定義を変更した派生形式は、新しい派生形式を配信できるまで、変更前の派生形式が返る

### 異常系

- **入力エラー**: 存在しないモデルまたは項目のキーを指定すると、そのキーを示すエラーが返る。変更前のキーを指定した場合も同じ扱いになる。開発者は、アプリのコードを現行スキーマに合わせる
- **入力エラー（一意でない項目）**: 一意にする制約を持たない項目で対象を指定すると、その項目では単件を指定できないことを示すエラーが返る。開発者は、コンテンツID または一意な項目で指定し直す
- **リソース不在**: 該当するコンテンツがない場合、存在しないことを示す結果が返る。未公開のコンテンツ、ごみ箱のコンテンツ、公開内容を持たない単一モデルも、同じ結果になる。CMS は、下書きの内容と存在、公開中のコンテンツの下書きの有無を明かさない。表示アプリは、ページが存在しない場合の表示を行う
- **非公開化・削除したメディアの配信先**: メディアの非公開化（MEDIA-07）と削除（MEDIA-08）の確定の後、CMS は、[media.md](media.md) の「共通の規則」のとおり、そのメディアの配信先への要求を拒否する。表示アプリ、その CDN、ブラウザが確定の前に保持した内容は、保持の期限まで残り得る。開発者は、必要な場合、表示アプリの側で保持した内容を破棄する

## APP-03 公開コンテンツの一覧を絞り込み・並び替え・件数を区切って取得する

- **利用者**: 開発者（表示アプリ）
- **目的**: 表示アプリが、条件に合う公開コンテンツの一覧と総件数を得て、ページ分割した一覧を表示する
- **要件**: 3.2, 3.3, 10.4

### 正常系

1. 表示アプリは、公開取得の許可を持つトークンで、モデルのキーに、絞り込みの条件、並び替え、区切る件数と取得する位置を添えて一覧を取得する
2. 絞り込みには、モデル直下の項目を使う
   - テキスト、数値、真偽値、日付、日時、単一選択の完全一致
   - 数値、日付、日時の範囲
   - 複数選択の指定値の包含
   - コンテンツ参照のコンテンツID による一致
3. 複数の条件を指定すると、すべてを満たすコンテンツに絞り込む
4. 並び替えには、モデル直下のテキスト、数値、日付、日時、単一選択の項目と、作成日時、更新日時を、昇順または降順で指定する。公開日と掲載順は、スキーマに定義した項目で並び替える
5. CMS は、条件に該当する公開内容を、指定した順序と件数で返す。並び替えの値が同じコンテンツの順序も決まっており、同じ条件の取得は同じ順序になる
6. CMS は、条件に該当する総件数を常に返す。表示アプリは総件数からページ数を求める
7. 表示アプリは、取得する位置を進めて続きを取得する
8. ブラウザで動くコードは、ブラウザ用トークンで同じ一覧を取得する

### 異常系

- **入力エラー**: 存在しないモデルまたは項目のキーを指定すると、そのキーを示すエラーが返る。開発者は、アプリのコードを現行スキーマに合わせる
- **入力エラー（扱えない条件）**: 絞り込みまたは並び替えに使えない項目を指定すると、項目と理由を示すエラーが返る。入れ子の内部の項目、参照先の項目、本文、項目の型に合わない値と比較方法が該当する。開発者は、モデル直下の項目に条件を移すか、表示アプリの側で絞り込む
- **入力エラー（上限）**: 絞り込みの条件の数と、区切る件数には、上限がある（APP-12）。超えると、上限を示すエラーが返る。開発者は、指定を上限以下にする
- **リソース不在**: 条件に該当するコンテンツがない場合、空の一覧と総件数 0 が返る。取得する位置が末尾を超えた場合も空の一覧が返る。エラーにはならない。未公開のコンテンツとごみ箱のコンテンツは、一覧にも総件数にも含まれない
- **一覧の途中での変化**: 続きを取得するまでの間に公開内容が変わると、同じコンテンツが二度現れるか、現れないことがある。CMS は、複数回の取得をまたいで一覧を固定しない。表示アプリは、コンテンツID で重複を取り除く

## APP-04 参照先を展開して取得する

- **利用者**: 開発者（表示アプリ）
- **目的**: 表示アプリが、コンテンツとその参照先の内容を一度の取得で得る
- **要件**: 3.2, 3.3, 4.3, 5.2

### 正常系

1. 表示アプリは、単件または一覧の取得に、展開するコンテンツ参照の項目と展開する深さを添える
2. CMS は、展開を指定した参照について、参照先の現在の公開内容を返す。参照先を再公開すると、参照元を再公開しなくても、次の取得から更新後の内容が返る
3. 展開を指定しない参照について、CMS は参照先のモデルのキー、コンテンツID、一意な値を返す。本文のコンテンツへのリンクも同じ情報を返す。表示アプリは、この情報から URL を組み立てる
4. 任意の参照の参照先が公開内容を持たない場合、CMS はその参照を未設定として返す。参照先を再び公開すると、参照元を再公開しなくても参照が返る
5. 参照が循環していても、取得は指定した深さで止まる。深さを超える参照は、展開を指定しない参照と同じ形で返る
6. 展開した参照先のモデルについても、APP-07 の識別子の一致を確認できる

### 異常系

- **入力エラー**: コンテンツ参照でない項目、または存在しない項目を展開に指定すると、項目のキーを示すエラーが返る。開発者は指定を直す
- **入力エラー（深さと参照先の件数の上限）**: 展開する深さと、1 回の取得で読む参照先の件数には、上限がある（APP-12）。上限を超えると、上限を示すエラーが返る。開発者は、深さか一覧の件数を減らすか、参照先を別の取得に分ける
- **権限不足**: トークンの範囲に含まないモデルの参照先の展開は、範囲の不足（`index.md` の「CMS に接続するコマンドと SDK の操作」）に当たる。開発者は、新しいトークンへ入れ替えるか、展開をやめる
- **リソース不在**: 任意の参照の参照先が、公開取り消し、ごみ箱への移動、完全削除で公開内容を持たなくなった場合、未設定として返る。表示アプリは、その参照がない場合の表示を行う。必須の参照と本文のリンクの参照先は、公開内容を持つ

## APP-05 プレビュー取得で最新の内容を取得する

- **利用者**: 開発者（表示アプリ）
- **目的**: 表示アプリが、未公開のコンテンツと公開中のコンテンツの変更を、公開せずに表示する
- **要件**: 3.2, 3.3, 4.2, 5.3, 9.3

### 正常系

1. 表示アプリのサーバー側の処理は、プレビュー取得の許可を持つサーバー用トークンで、取得をプレビュー取得として呼び出す。単件・一覧の取得方法、絞り込み、並び替え、参照先の展開は、公開取得と共通である
2. CMS は、取得時点で保存済みの最新の内容を返す。下書きがあるコンテンツでは下書き、なければ公開内容を返す。絞り込みと並び替えの条件は、返す内容の値に適用する
3. 結果では、返した内容が下書きと公開内容のどちらかを識別できる。更新日時は、返した内容の更新日時である
4. 制約違反（`content-editing.md` の「共通の規則」）だけを持つ下書きは返る。結果では、制約違反があることを識別できる
5. 表示アプリは、結果を公開取得と同じ型で扱い、同じ表示の実装で描画する
6. 展開した参照先にも最新の内容が返る。非公開のメディアには、有効期間を限ったプレビュー用の配信先が返る。表示アプリは、この配信先で、非公開のメディアも表示できる（[media.md](media.md)）
7. 下書きを確認するビルドでは、SSG のビルドが同じトークンでプレビュー取得を呼び出す
8. 表示アプリは、プレビューで取得した内容を見せる相手を自分で制御する

### 異常系

- **入力エラー（型を満たさない下書き）**: 単件の取得で、下書きに型を満たさない入力エラー（`content-editing.md` の「共通の規則」）がある場合、CMS は内容を返さず、エラー箇所の項目と理由を示す。公開内容で代替しない。表示アプリは、プレビューを表示できない理由としてエラー箇所を表示する。編集権限を持つメンバーは下書きを直して保存し、プレビューを開き直す
- **入力エラー（一覧）**: 一覧の取得では、型を満たさない入力エラーのある下書きを結果に含めず、含めなかった対象の件数と先頭（APP-12 の「結果に示す先頭の対象の件数」）を示す。表示アプリは、含めなかった対象があることを表示する
- **入力エラー（一意な値の重複）**: 一意な値による取得で複数のコンテンツが該当すると、CMS は重複と、該当するコンテンツの先頭（APP-12 の「一意な値による取得で複数のコンテンツが該当したときに示すコンテンツの件数」）を示し、一件を選ばない。表示アプリは、コンテンツID で取得し直す
- **入力エラー（キーと条件）**: 存在しないキー、扱えない条件、上限を超える指定は、APP-02 から APP-04 と同じ扱いになる
- **参照先を返せない**: 参照先の下書きに型を満たさない入力エラーがある場合と、必須の参照先がごみ箱にある、または存在しない場合、CMS はプレビューを完了できないことと、原因の参照先を示す。参照先を展開するかどうかによらない。編集権限を持つメンバーは、参照先の下書きを直すか、参照を付け替える。任意の参照で、ごみ箱にある、または存在しない参照先は、未設定として返る
- **権限不足**: ブラウザ用トークンと、プレビュー取得の許可を持たないトークンでは拒否される。メンバーに紐付くトークンの認可は、`index.md` の「トークンの許可」に従う
- **リソース不在**: 該当するコンテンツがない場合と、対象がごみ箱にある場合は、存在しないことを示す結果が返る

## APP-06 編集画面から渡された引き換えの値をトークンに引き換え、プレビューを表示する

- **利用者**: 開発者（表示アプリ）
- **目的**: 表示アプリが、編集画面でプレビューを開いたメンバーに、そのメンバーの認可で下書きを表示する
- **要件**: 2, 5.3, 9.3

### 正常系

1. 開発者は、スキーマで定義したモデルごとのプレビュー先の経路に対応する入口を、表示アプリに実装する
2. メンバーが編集画面でプレビューを開く（EDIT-12）。メンバーのブラウザは、一度だけ使える引き換えの値を伴って表示アプリの入口へ移る
3. 表示アプリのサーバー側の処理は、引き換えの値を CMS へ渡す
4. CMS は、引き換えのときに、そのメンバーに紐付くサーバー用トークンを発行して返す。このトークンは、プレビュー取得の許可だけを持ち、有効期間が限られている
5. このトークンは、トークンの一覧（WS-07）にメンバーに紐付くトークンとして載り、発行は操作履歴に残る。有効期間が切れると一覧から外れる。アプリ連携の権限を持つメンバーは、一覧から失効できる。引き換えなかった引き換えの値は、トークンを発行せず、一覧にも操作履歴にも載らない
6. 表示アプリは、トークンをサーバー側で保持し、メンバーのブラウザとの間のセッションに結び付ける。トークンの値をブラウザへ渡さない
7. 表示アプリは、保持したトークンで APP-05 のプレビュー取得を行い、対象コンテンツのページを表示する
8. メンバーは、有効期間の間、表示アプリ内のほかのページも下書きを含む内容で確認する
9. 有効期間が過ぎると、表示アプリはプレビューを終了する。メンバーは、編集画面からプレビューを開き直す

### 異常系

- **入力エラー**: 引き換えの値が、誤っている、使用済みである、または期限を過ぎている場合、CMS は引き換えを拒否する。表示アプリは下書きを表示せず、編集画面からプレビューを開き直すよう案内する
- **権限不足**: 引き換えの時点で、メンバーの利用が解除されている場合と、ワークスペースが利用終了の途中または利用を終了している場合、CMS は引き換えを拒否し、トークンを発行しない。表示アプリは下書きを表示しない。引き換えの後の利用の解除は、`index.md` の「トークンの許可」に従う。プレビュー取得が拒否されると、表示アプリはプレビューを終了する
- **リソース不在**: 対象コンテンツが、プレビューを開いた後にごみ箱へ移動または完全削除された場合、プレビュー取得は存在しないことを示す結果を返す。表示アプリは、ページが存在しない場合の表示を行う
- **操作の取り消し**: メンバーがプレビューをやめると、表示アプリは保持したトークンを破棄する。破棄しなかったトークンも、有効期間が過ぎると次の要求から拒否される

## APP-07 前提とするスキーマの識別子を添え、現行スキーマとの一致を確認する

- **利用者**: 開発者（表示アプリ）
- **目的**: 表示アプリが、コードが前提とするスキーマと現行スキーマの型の食い違いを、取得・送信の応答から知る
- **要件**: 3.2, 6.1, 6.4

### 正常系

1. 開発者は、APP-01 の初期設定で、識別子を添える単位を選ぶ。単位は、スキーマ全体、またはモデル・フォームごとである
2. アプリは、スキーマの定義から求めた識別子を、取得・送信の要求に添える。SDK は、初期設定で指定したスキーマの定義から識別子を求める。HTTP API を直接呼ぶアプリは、識別子を得るコマンド（SDEV-03）が示す識別子を添える。識別子を求めるために CMS へ接続しない
3. CMS は、要求を現行スキーマに従って処理し、添えられた識別子ごとに、現行スキーマの識別子と一致するかを応答で示す
4. モデルごとの識別子は、参照先のモデルの型の形を含まない。参照先を展開する取得では、展開する参照先のモデルの識別子も添え、それぞれの一致を確認する
5. 制約と検証、一意性、表示・運用の定義だけが異なる場合、識別子は一致する
6. 開発者は、不一致の応答を取得・送信の失敗として扱うかを、初期設定で選ぶ。失敗として扱わないアプリは、不一致を記録して処理を続ける

### 異常系

- **識別子の不一致**: CMS は不一致を理由に要求を拒否せず、現行スキーマに従う結果を返す。失敗として扱うアプリでは、その取得・送信が、不一致の対象を示して失敗する。開発者は、適用状況を確認し（SMIG-04）、表示アプリを現行スキーマに合わせて配信し直すか、スキーマを反映する（SMIG-06）
- **フォーム送信での不一致**: 不一致の応答を失敗として扱うアプリでも、CMS が受付完了とした回答は保存され、通知される。表示アプリは、訪問者に再送を求めない
- **入力エラー**: 現行スキーマに存在しないモデル・フォームの識別子を添えた場合、CMS はその識別子を不一致として示す。そのモデル・フォームを対象とする取得・送信は、APP-02 と APP-08 に従い、キーを示すエラーになる
- **互換性の判断**: CMS は、識別子の一致だけを示し、表示アプリが現行スキーマで表示を続けられるかを判断しない。互換性のない変更を適用した後、変更前のスキーマを前提とする表示アプリの表示は保証されない。移行の適用と表示アプリの配信の順序は、開発者が決める

## APP-08 フォームを送信し、受付結果を受け取る

- **利用者**: サイト訪問者、開発者（表示アプリ）
- **目的**: サイト訪問者が表示アプリのフォームから問い合わせを送り、受け付けられたかどうかを知る
- **要件**: 3.1, 3.2, 6.5, 8.1, 8.2, 10.4

### 正常系

1. 開発者は、フォームのスキーマから得た型で、表示アプリの入力欄と送信の処理を実装する
2. サイト訪問者は、表示アプリのフォームに入力して送信する
3. 表示アプリは、フォーム送信の許可を持つトークンで、フォームのキーと入力内容を CMS へ送る。サーバー側の処理からはサーバー用トークンで、ブラウザからはブラウザ用トークンで送る
4. 問い合わせ対象の項目には、訪問者が選んだ公開中のコンテンツのコンテンツID を指定する
5. 表示アプリは、送信に APP-07 の識別子を添えられる。応答は、受付結果とともに識別子の一致を示す
6. CMS は、受付時点の現行の定義で入力内容を検証し、回答を保存して、受付完了を返す。通知の送信結果を待たない。通知の送信に失敗しても、受付完了は変わらない。受付完了とした回答の通知は、`form-operation.md` の「共通の規則」に従う
7. 表示アプリは、受け付けたことを訪問者に表示する

### 異常系

受付できない送信に、CMS は受付完了を返さず、理由を付けた受付失敗を返す。表示アプリは、理由ごとに次の表示を行う。受付失敗の応答は、通知先と送信接続設定の詳細を含まない。

- **入力エラー（入力不備）**: 現行の定義を満たさない送信は、項目ごとの理由を付けて拒否される。必須項目の未入力、文字数・範囲・書式・選択数の違反、真であることを求める真偽値の偽、一致を求める二項目の不一致が該当する。表示アプリは、入力を保持したまま項目ごとの理由を表示する。訪問者は、該当する項目を直して送信し直す
- **入力エラー（許可されていない内容）**: 定義されていない項目、許可されていない選択肢の値、変更できない受付条件を含む送信は、入力不備を理由とする受付失敗として、該当するキーとともに拒否される。受付条件は、通知先、通知定義、受付状態、送信制限、回答の保持方針を指す。送信が指定できるのは、フォームの項目の値だけである。項目の値のほかの指定を含む送信は、受付条件を含む送信として、その指定のキーを示して拒否される。定義されていない項目と受付条件を含む送信の応答は、ほかの入力不備と同じ受付失敗の形であり、別の形のエラーにならない。CMS は、必須項目を初期値で補わず、入力内容を捨てて受け付けない。開発者は、表示アプリの送信内容を現行の定義に合わせる
- **入力エラー（問い合わせ対象）**: 問い合わせ対象が、公開中でない、またはその項目に許可したモデルのコンテンツでない場合、その項目の入力不備として拒否される。表示アプリは、訪問者に対象を選び直すよう促す
- **入力エラー（定義の変更）**: フォームの定義を変更する前の表示から送った送信も、現行の定義で検証される。現行の定義を満たさない場合は入力不備になる。表示アプリは、入力を保持し、現行のフォームで直して送り直すよう促す
- **受付停止**: フォームが受付停止の場合と、有効な通知先がない場合は、受付停止を理由に拒否される。表示アプリは、現在は受け付けていないことを表示する。訪問者が同じ内容を送り直しても受け付けられない
- **リソース不在（フォームが存在しない）**: 存在しないフォームのキー、変更前のキー、削除したフォームのキーへの送信は、フォームが存在しないことを理由に、キーを示して拒否される。表示アプリは、送信できないことを表示する。開発者は、表示アプリのキーを現行スキーマに合わせる
- **混雑・送信制限**: 送信制限または混雑で受け付けられない送信は、その理由の受付失敗として拒否される。送信制限は、フォームの送信制限（`form-operation.md` の「共通の規則」）と、ブラウザ用トークンの利用量の制限（WS-06）の二つを指す。どちらに達した送信も、送信制限を理由とする同じ形の受付失敗として、再び送信できる時期を示す。表示アプリは、入力を保持し、時間を置いて送り直すよう促す
- **保存の失敗**: 回答を保存できなかった送信は、保存の失敗を理由に拒否される。その回答は通知されない。表示アプリは、入力を保持し、送り直すよう促す
- **権限不足**: フォーム送信の許可を持たないトークン、失効したトークン、許可していない利用元からのブラウザ用トークンでは拒否される。表示アプリは、送信できないことを表示する。開発者は、APP-01 に従ってトークンを直す
- **受付結果を受け取れない**: 通信断で応答を受け取れなかった場合、表示アプリは受付結果を後から確認できない。訪問者が送り直すと、CMS は新しい送信として受け付ける。先の送信も受け付けられていた場合、回答と通知が重複する。回答の削除権限を持つメンバーが、重複した回答を削除する（FORM-08）
- **操作の取り消し**: 訪問者が送信の前にやめると、CMS には何も送られない。受付完了の後の回答は、回答の削除権限を持つメンバーが削除する（FORM-08）

## APP-09 スクリプトからコンテンツとメディアを管理する

- **利用者**: 開発者（スクリプト）
- **目的**: 開発者が、自分の環境で実行するスクリプトから、コンテンツとメディアを作成・更新・公開する
- **要件**: 3.1, 3.2, 4.2, 4.4, 5.1, 9.1, 9.3

### 正常系

1. 開発者は、コンテンツ管理の許可を持つサーバー用トークンを得て、スクリプトに APP-01 の初期設定を行う
2. スクリプトは、次の操作を型付きで呼び出す。指定する値は、スキーマから得た型に従う
   - コンテンツの一覧（通常の管理対象とごみ箱）、コンテンツの作成、最新の内容の取得、下書きの保存、下書きの破棄。通常の管理対象の一覧は、管理画面の一覧（EDIT-01）と同じ検索語と絞り込みを受ける
   - 公開、公開取り消し、ごみ箱への移動、ごみ箱からの復元、完全削除
   - メディアの登録
   - 値の書き換え（APP-10）
3. データを投入するスクリプトは、コンテンツID を指定してコンテンツを作成する。指定できるコンテンツID の形式は APP-12 が定める。SDK は、名前から同じ ID を求める関数を提供する。スクリプトは、コンテンツごとに決めた名前から ID を求めて指定する。やり直しても同じ ID になる。CMS は、未公開のコンテンツを指定した ID で作成する
4. 指定した ID のコンテンツが同じ内容で既にある場合、CMS は作成せず、同じ内容で既にあることを成功として示す。スクリプトは、そのコンテンツを作成済みとして次へ進む。投入を途中からやり直しても、コンテンツは重複しない
5. メディアを使うコンテンツでは、スクリプトはメディアを登録し、登録結果のメディアを項目の値に指定する。登録したメディアは非公開である。メディアの登録は、繰り返すたびに新しいメディアを作る。スクリプトは、作成済みのコンテンツの分のメディアを登録しない
6. スクリプトは、作成したコンテンツを公開する。CMS は、使用するメディアを公開の確定に合わせて公開する。操作の結果は CMS での確定を示し、表示アプリへの通知の送信結果を含まない。通知の状況は、アプリ連携の権限を持つメンバーが管理画面で確かめる（PUB-08）
7. CMS は、どの操作にも、管理画面と同じ規則、入力検証、認可を適用する

### 異常系

- **入力エラー（保存できない値）**: 現行スキーマの値の種類・構造に従わない値を指定した作成と下書きの保存は、項目と理由を示して拒否される。開発者は、スクリプトの値を現行スキーマに合わせる。必須項目の欠落と制約の違反は、下書きの入力エラーとして保存される
- **入力エラー（公開できない内容）**: 入力エラーの残る下書き、公開内容の間で一意な値が重複する下書き、参照切れ（`content-editing.md` の「共通の規則」）を持つ下書きの公開は、項目と理由を示して拒否される（PUB-01）。スクリプトは、下書きを直して保存し、公開し直す
- **入力エラー（一つの操作の上限）**: 一つの操作が対象にするコンテンツの件数と、新たに公開するメディアの数が上限（APP-12）を超える公開は、上限を示して拒否される。スクリプトは、対象を分けて公開する（PUB-01、PUB-02）
- **入力エラー（コンテンツID）**: 指定できる形式（APP-12）でないコンテンツID での作成は拒否される。開発者は、SDK の関数で名前から ID を求めて指定する
- **競合（違う内容で既にある）**: 指定した ID のコンテンツが違う内容で既にある場合、作成は、既にあることを示して拒否される。CMS は既にあるコンテンツを変えない。開発者は、別の ID を指定するか、既にあるコンテンツに下書きの保存を行う
- **入力エラー（メディア）**: 対応形式と容量の上限（MEDIA-01）を満たさないファイルの登録は、理由と上限を示して拒否される。開発者は、ファイルを対応形式に変えるか、容量を減らす
- **権限不足**: コンテンツ管理の許可を持たないトークンでは拒否される。操作ごとに必要な権限と、トークンによる要求の認可は、`index.md` の「権限」と「トークンの許可」に従う。公開中のコンテンツのごみ箱への移動と完全削除に必要な権限は、`publishing.md` の「公開取り消しを含む操作」に従う。開発者は、必要な権限に対応する操作を許可されたトークンを使う
- **単一モデルの二つ目**: 既に一つある単一モデルでの別の ID の作成と、ごみ箱からの復元の扱いは、EDIT-04 の「二つ目のコンテンツ」に従う
- **リソース不在**: 存在しないコンテンツID、モデル、項目を指定した操作は、対象を示すエラーになる。コンテンツ管理の許可での読み取りは、ごみ箱のコンテンツも、置き場所（通常・ごみ箱）を添えて返す。コンテンツ管理の許可での一覧は、未公開のコンテンツと、型を満たさない入力エラーのある下書きを持つコンテンツを含む。ごみ箱のコンテンツは、ごみ箱の一覧で得る。ごみ箱のコンテンツは、下書きの保存と公開の対象にならない。スクリプトは、復元してから操作する。完全削除したコンテンツの ID は、作成で再び指定できる
- **競合**: 読み取った後に他の操作で変わった内容への下書きの保存と公開は、競合として拒否される。スクリプトは、最新の内容を取得し直して操作をやり直す
- **操作の取り消し**: スクリプトを途中で止めると、確定済みの操作の結果が残る。開発者は、コンテンツID を指定した作成でスクリプトをやり直す。公開は公開取り消しで、ごみ箱への移動は復元で戻す。完全削除は戻せない

## APP-10 スクリプトから複数のコンテンツの値を書き換える

- **利用者**: 開発者（スクリプト）
- **目的**: 開発者が、複数のコンテンツの指定した項目の値を、一つの操作でまとめて変える
- **要件**: 4.2, 4.4, 5.4, 6.4, 9.1

### 正常系

1. スクリプトは、コンテンツ管理の許可を持つサーバー用トークンで、モデルのコンテンツの一覧とごみ箱の一覧から対象のコンテンツID を得て、対象のコンテンツの公開内容と下書きを読み取る。読み取りは、ごみ箱のコンテンツも、置き場所（通常・ごみ箱）を添えて返す
2. スクリプトは、新しい値を自分の環境で求める
3. スクリプトは、対象ごとに次を指定し、全体を一つの操作として要求する
   - コンテンツID
   - 書き換え先。公開内容、下書き、またはその両方
   - 書き換える項目と新しい値。書き換え先ごとに別の値を指定できる
   - 読み取った時点を示す情報
4. CMS は、`index.md` の「複数の対象を扱う操作」に従って確定する
5. 確定すると、指定した項目の値だけが変わる。ほかの項目と、書き換え先に選ばなかった内容は変わらない。下書きは公開されず、新たな下書きは作られない
6. 公開内容を書き換えたコンテンツでは、書き換え前の公開内容が履歴に残る。下書きを書き換えたコンテンツでは、書き換え前の下書きが履歴に残る。書き換えない項目に現行の制約の違反が残っていても、書き換えは行われる
7. 公開内容の書き換えで新たに使用するメディアは、確定に合わせて公開される
8. CMS は、公開内容を書き換えた対象を、一つの更新の通知で表示アプリへ伝える（APP-11）。下書きだけの書き換えは通知されない。スクリプトが受け取る結果は、通知の送信結果を含まない（APP-09）
9. ごみ箱のコンテンツは、ごみ箱に置いたまま下書きが書き換わる
10. 編集画面で読み取り専用になる非推奨の項目の値も、同じ操作で書き換えられる
11. 指定した値が、どれも現在の値と等しい対象は、変わらず、履歴にも残らない。その対象だけの操作は、表示アプリへ通知されない
12. スクリプトは、書き換えた対象と、変わらなかった対象を、結果として受け取る

### 異常系

次は、`index.md` の「複数の対象を扱う操作」の、対象ごとの条件を満たさない場合である。

- **入力エラー（公開内容の値）**: 公開内容に指定した値が公開時の検証を満たさない場合に拒否される。制約の違反、ほかの公開内容との一意な値の重複、公開内容を持たないコンテンツへの参照が該当する。開発者は値を直して要求し直す
- **入力エラー（下書きの値）**: 下書きに指定した値が現行スキーマの値の種類・構造に従わない場合に拒否される。必須項目の欠落と制約の違反は、下書きの入力エラーとして残して書き換えられる
- **入力エラー（件数の上限）**: コンテンツの件数と新たに公開するメディアの数が上限（`index.md` の「複数の対象を扱う操作」）を超えると、拒否される。開発者は、対象を上限以下の組に分けて、組ごとに要求する
- **リソース不在（書き換え先）**: 下書きを持たないコンテンツの下書き、または公開内容を持たないコンテンツの公開内容を書き換え先に指定すると拒否される。スクリプトは、その書き換え先を対象から外して要求し直す
- **リソース不在（対象）**: 存在しないコンテンツID または項目を指定すると拒否される
- **権限不足**: 必要な権限は、`index.md` の「権限」と「トークンの許可」に従う。開発者は、必要な権限に対応する操作を許可されたトークンを使う
- **競合**: 読み取った後に他の操作で変わった対象があると拒否される。スクリプトは、該当する対象を読み取り直し、値を求め直して要求し直す
- **メディアの公開**: 操作が拒否された場合、新たに使用するメディアは非公開のままになる
- **操作の取り消し**: 確定の前に要求が中断すると、どの対象も変わらない。対象を組に分けた場合、確定済みの組の変更は残る。確定した書き換えは、元の値を指定した値の書き換えで戻す。書き換え前の公開内容は、履歴から下書きとして復元できる（EDIT-14）

## APP-11 公開内容の変更の通知を表示アプリで受け取る

- **利用者**: 開発者（表示アプリ）
- **目的**: 表示アプリが、公開内容の変更を知り、キャッシュと生成済みのページを更新する
- **要件**: 4.1, 5.2, 5.4, 6.2

### 正常系

1. 開発者は、通知を受け取る入口を表示アプリに実装する。アプリ連携の権限を持つメンバーが、その宛先と秘密情報を表示アプリへの通知設定に登録する（WS-09）
2. CMS は、公開状態が確定した後に、表示アプリへ通知を送る
3. 表示アプリは、通知設定の秘密情報で、通知が CMS から届いたものであることを確かめる。SDK を使う表示アプリは、SDK の関数で確かめる
4. 表示アプリは、通知から次を読み取る
   - 変更した対象のモデルのキーとコンテンツID
   - 対象ごとの変更の種類。公開、更新、公開取り消しのいずれか
   - 一意な値が変わった対象の、変更前と変更後の一意な値
   - 変更した対象を公開内容から参照するコンテンツの、モデルのキーとコンテンツID
   - スキーマの反映による変更では、スキーマの版
   - 通知を識別する情報。同じ通知は、何度届いても同じ値を持つ
   - 変更の順序を判別する情報
5. 変更の種類は次のとおり決まる
   - 未公開のコンテンツの公開は、公開として届く
   - 公開中のコンテンツの公開と、公開内容の値の書き換えは、更新として届く
   - 公開取り消し、公開中のコンテンツのごみ箱への移動と完全削除、モデルの削除による公開中のコンテンツの削除は、公開取り消しとして届く
   - スキーマの移行と直接反映による公開内容の変更は、更新として届く
6. 一括公開、複数対象の公開取り消し、複数のコンテンツの値の書き換え、スキーマの反映は、変更した対象を列挙した一つの通知として届く。直接反映による公開内容の変更も、スキーマの反映の一つの通知として届く。通知は、対象の数によらず、変更したすべての対象と、その参照元を列挙する
7. 通知は非公開の内容を含まない。表示アプリは、変更した対象とその参照元のキャッシュを破棄し、通知が示すモデルのキーとコンテンツID で、公開取得で内容を取り直す
8. 一意な値が変わった対象について、表示アプリは旧 URL からの転送を自分で設定する
9. 下書きの保存と破棄、下書きだけの値の書き換え、取り消した操作、失敗した移行は、通知として届かない

### 異常系

- **入力エラー**: 秘密情報で確かめられない通知を、表示アプリは破棄する
- **重複と到着順の逆転**: 同じ通知が複数回届くことと、後の変更の通知が先に届くことがある。表示アプリは、通知を識別する情報で、処理済みの通知の重複を見分ける。変更の順序を判別する情報は、ワークスペースの変更の全体の順を示す。表示アプリは、変更した対象ごとに、変更の順序を判別する情報を比べ、その対象について処理済みの変更より古い通知を無視する。ほかの対象の変更は、古い通知でも処理する
- **設置の復旧の後**: バックアップからの復旧（HOST-08）の後、CMS の公開内容は復旧点へ戻る。CMS は、復旧を通知しない。変更の順序を判別する情報は、復旧点の続きから始まり、表示アプリが処理済みとした情報より古くなり得る。開発者は、利用の再開の後に、表示アプリのキャッシュと生成済みのページを公開取得で全体を取り直し、処理済みとして記録した情報を捨てる
- **リソース不在**: 通知を受けて公開取得を行った時点で、対象が既に公開内容を持たない場合がある。公開取得は存在しないことを示す結果を返す。表示アプリは、その対象のページを取り下げる
- **受け取りの失敗**: 表示アプリが通知を受け取れなかった場合（応答を待つ時間（APP-12）の内に応答しなかった場合を含む）、CMS は自動で再試行する。自動の再試行の回数と間隔、手動再試行の規則は、`spec/scenario/index.md` の「未対処の失敗」に従う。アプリ連携の権限を持つメンバーが、状況を確認して、送信失敗の宛先へ再試行する（PUB-08）。再試行した通知は、通知を識別する情報と、変更の順序を判別する情報を変えずに届く
- **表示反映の確認**: CMS は、表示アプリが通知を受け取った後の表示反映を確認しない。開発者は、表示アプリ上の反映を表示アプリの側で確かめる

## APP-12 取得と検索の規則・制限を確認する

- **利用者**: 開発者
- **目的**: 開発者が、取得の結果がどう決まるかと、取得できる範囲を知ったうえで表示アプリを実装する
- **要件**: 3.3, 10.4
