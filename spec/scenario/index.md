# シナリオ一覧

利用者がシステムに対して行う操作の一覧。各シナリオの流れと異常系はカテゴリーごとのファイルが定める。用語は `spec/requirements.md` の 1 章に従う。

利用者は、開発者、ワークスペースのメンバー、サイト訪問者、ホスティング運営者。メンバーは、権限の節が定める権限の組を持つ。

## 権限

メンバーは、ワークスペースごとに次の権限の組み合わせを持つ。どのメンバーも、コンテンツ、メディア、履歴、ごみ箱を閲覧できる。シナリオの「〜権限を持つメンバー」は、その権限を付与されたメンバーを指す。

| 権限 | 行える操作 |
| --- | --- |
| 編集権限 | コンテンツの作成・複製、下書きの保存・破棄、下書きの値の書き換え、履歴からの復元、メディアの登録と説明の編集、非公開のメディアの削除、失敗した派生形式の生成のやり直し |
| 公開権限 | 公開、公開取り消し、公開内容の値の書き換え |
| 削除権限 | ごみ箱への移動と復元、完全削除、履歴の版の削除 |
| メディア公開権限 | コンテンツの公開と公開内容の値の書き換えに伴うメディアの公開、メディアの非公開化、公開のメディアの削除 |
| スキーマ変更権限 | スキーマ・版の記録・反映結果の確認。スキーマ反映の許可を持つトークンの発行に必要 |
| 回答の閲覧権限 | 保存した回答の閲覧 |
| 回答の削除権限 | 保存した回答の閲覧と削除 |
| 通知設定の権限 | 通知先、通知定義、送信接続設定の変更、通知の送信結果の確認と手動再試行、送信失敗の対処済みの記録 |
| 受付管理の権限 | フォームの受付状態と回答の保持方針の変更 |
| メンバー管理の権限 | メンバーの招待、権限の変更、利用の解除 |
| アプリ連携の権限 | トークンの手動発行・失効、プレビュー先の表示アプリの URL の変更、表示アプリへの通知設定の変更、表示アプリへの通知の状況確認と手動再試行、送信失敗の対処済みの記録 |
| ワークスペース設定の権限 | コンテンツの保持方針の変更、操作履歴の確認 |

標準の役割は、権限の組み合わせに名前を付けたもの。メンバーには、標準の役割のほかに、権限を個別に組み合わせて付与できる。

| 役割 | 権限 |
| --- | --- |
| 管理者 | すべての権限 |
| 編集者 | 編集権限、公開権限、削除権限、メディア公開権限 |
| 閲覧者 | なし（閲覧だけ） |

所有者は、ワークスペースが指定する一人のメンバー。すべての権限を持ち、加えて所有者の変更と、多要素認証の必須化と解除を行える。所有者は役割ではなく、招待と権限の変更の対象にならない。

## 共通の規則

すべてのシナリオに適用する。各カテゴリーのファイルは、ここに加わる分だけを書く。

### スキーマの反映の適用中

スキーマの反映の適用中、CMS は、そのワークスペースのコンテンツを変える操作と、次の反映を確定しない。メディアの操作と取得は止めない。履歴の版を対象に加えたメディアの削除（MEDIA-08）は、履歴の版の削除がコンテンツを変える操作なので、確定しない。

### 複数の対象を扱う操作

管理画面の操作と、CMS に接続するコマンドと SDK の操作のうち、利用者が対象を選ぶ操作に適用する。フォームの既存の回答すべてへの保持方針の適用（FORM-06）は、対象を選ばないので、この規則の外にある。

- 一つの操作が対象にできるコンテンツの件数、履歴の版の件数、新たに公開できるメディアの数には、上限がある。履歴の版の件数は、コンテンツの件数と別に数える。回答、通知、通知と宛先の組を対象にする操作の件数にも、コンテンツと同じ上限がある。上限の値は APP-12 が定める。超える場合、CMS は確定せず、上限を示す。利用者は対象を分けて操作する
- 操作は、すべての対象への権限を必要とする。CMS は、すべての対象の検証、権限の確認、競合の確認を終えてから確定する。対象ごとの条件は、各操作が定める。一件でも条件を満たさなければ、何も変えず、該当する対象と理由をすべて示す。利用者は、該当する対象を直すか、対象から外して、操作し直す

### 管理画面の操作

- 権限の不足: 管理画面は、メンバーが権限を持たない操作を示さない。認可は操作のたびに、その時点の権限で判定する。画面を開いた後に権限が変わるなどして、権限を持たない操作が要求された場合、CMS は操作を確定せず、必要な権限を示す。画面は入力を保持する。メンバーは、メンバー管理の権限を持つメンバーに権限を依頼する
- 許可されていないワークスペース: 所属しないワークスペース、利用を解除されたワークスペース、利用終了の途中のワークスペース、利用を終了したワークスペース、存在しないワークスペースの対象は、存在しない対象として扱う。CMS は、どの場合も同じく、利用できないワークスペースであることを、所属するワークスペースの一覧とともに示し、そのワークスペースの情報も、利用を解除されたことも示さない（AUTH-05）
- 存在しない対象: CMS は対象がないことを示し、利用者は一覧へ戻る
- セッションの期限切れ: CMS は再ログインを求め、画面は入力を保持する。再ログインの後、利用者は同じ操作をやり直す
- スキーマの反映の適用中: 適用中に確定しない操作（「スキーマの反映の適用中」）が要求された場合、CMS は確定せず、適用中であることを示す。画面は入力を保持し、利用者は適用の完了後に同じ操作をやり直す。適用中の間、管理画面は、権限によらずすべてのメンバーに、コンテンツの一覧、編集画面、履歴、ごみ箱で、適用中であることと、そのワークスペースのコンテンツを変える操作を止めていることを示す
- 確認を伴う操作の取り消し: 利用者が確認で取り消すと、CMS はその操作による変更を行わない
- 確認した内容での確定: CMS は、確認で示した内容だけを確定する。確認の後の変化で確定を拒否するのは、各操作が確認の後の変化として一か所で挙げるものの変化だけである。確定するまでにそれが変わっていた場合、CMS は確定せず、確認を示し直し、変わった対象とその状態を示す。利用者は、確認し直すか、該当する対象を外して操作し直す。各操作が挙げない内容（件数など）は、確認の時点の値として示し、その後の変化は確定を妨げない
- 未保存の入力: 未保存の入力がある状態で、画面を離れる、ログアウトする、ワークスペースを切り替える場合、CMS は入力を失うことを確認する。利用者がやめると、入力は変わらない。保存できなかった入力は、画面を開いている間だけ保持する。画面を閉じる、または読み込み直すと失う
- 一覧の絞り込み: 条件に該当する対象が無い場合（該当なし）、CMS は該当が無いことと指定中の条件を示す。利用者は条件を変える。絞り込みの条件を受け付けられない場合（条件の誤り）、CMS は該当する条件と理由を示し、一覧を変えない。利用者は条件を直す
- 秘密情報: 秘密情報（認証情報、通知設定の秘密情報）は、登録済みかどうかだけを示し、値を示さない
- エラーの示し方: 入力の誤りと不足は、対象の項目と修正理由で示す。操作の結果、保存状況、エラーの理由は、利用者が理解できる言葉で示す
- キーボード操作: すべての操作を、キーボードだけで完了できる

### CMS に接続するコマンドと SDK の操作

- トークンが無い・失効・期限切れ: CMS は要求を拒否し、その理由を示す。利用者は有効なトークンを設定する
- 許可・範囲の不足: CMS は要求を拒否し、必要な許可と範囲を示す。利用者は、必要な許可と範囲を持つトークンを得る（アプリ連携の権限を持つメンバーに発行を依頼するか、AUTH-06 で認証し直す）
- CMS に到達できない: コマンドと SDK は到達できないことを示す。利用者は接続先を確かめてやり直す
- スキーマの反映の適用中: 適用中に確定しない要求（「スキーマの反映の適用中」）を拒否し、適用中であることを示す。利用者は、適用の完了後に要求し直す

### トークンの許可

- 手動発行（WS-06）と認証による発行（AUTH-06）でトークンに与えられる許可は、発行の時点で、発行するメンバーがそのワークスペースで持つ権限の範囲に限る。スキーマ反映の許可は、スキーマ変更権限を持つメンバーだけが与えられる。コンテンツ管理の許可は、編集権限、公開権限、削除権限、メディア公開権限のうち、メンバーが持つ権限に対応する操作だけを、そのトークンに許可する。権限と操作の対応は「権限」の表に従い、値の書き換えは、下書きが編集権限、公開内容が公開権限に対応する
- 手動発行したトークンと初期構成で宣言したトークン（HOST-02）が許可する操作は、発行の後、発行者の権限の変更と利用の解除で変わらない
- メンバーに紐付くトークン（AUTH-06、APP-06）の要求は、要求のたびに、トークンの許可と、そのメンバーがその時点で持つ権限の両方の範囲で認可する。メンバーの利用が解除されると、次の要求から拒否する
- シナリオの「〜権限を必要とする」は、トークンによる要求では、その権限に対応する操作を許可されたトークンを指す

### 未対処の失敗

フォームの通知と表示アプリへの通知の送信失敗は、次のいずれかまで未対処とする。

- 再試行を始めた。再試行の間は、送信失敗ではない。再び送信失敗になると、未対処で始まり、前の対処済みの記録を引き継がない
- 対応する権限を持つメンバーが、対処済みとして記録した。対処済みの記録は取り消せない。対処済みの送信失敗も再試行でき、未対処に戻るのは、その再試行が再び送信失敗になったときだけである
- フォームの通知では、その回答を削除した

送信結果と再試行は、通知の種類ごとに次のとおりとする。

| | フォームの通知 | 表示アプリへの通知 |
| --- | --- | --- |
| 送信結果の単位 | 回答ごとの通知 | 通知と宛先の組 |
| 送信結果 | 未送信、送信成功、送信失敗。送信を待つ通知、送信中の通知、再試行の間の通知は未送信で、その内訳として、送信待ちか送信中か、最初の通知か再試行かを示す | 送信待ち、送信成功、送信失敗。送信を待つ組と再試行の間の組は送信待ち |
| 自動の再試行 | 行わない。最初の送信が失敗すると送信失敗になる | 行う。試行は、最初の送信を含めて上限（APP-12）の回数までで、失敗した試行の後、APP-12 の間隔を置いて次の試行を行う。尽きてから送信失敗になる |
| 手動再試行 | 送信成功を確認できていない、現在有効な通知先へ送る。外れた宛先と、送信成功を確認済みの宛先へは送らない | その宛先へ、現在の宛先の設定で一回だけ送る。送信成功のほかの宛先へは送らない。失敗すれば、自動の再試行を行わずに送信失敗に戻る |
| 手動再試行に選んだ後、確定するまでに、再試行が先に始まっていた対象 | 一件の再試行として扱う。二通目を送らず、先に始まった再試行の結果を示す。この対象は、「複数の対象を扱う操作」の、条件を満たさない対象に当たらず、ほかの対象の再試行を妨げない | 同じ |
| 対処済みの記録に選んだ後、確定するまでに、再試行が始まっていた対象 | 再試行の結果によらず、「複数の対象を扱う操作」の、条件を満たさない対象に当たる。再び送信失敗になっていても、選んだ時点と別の送信失敗として扱う | 同じ |

CMS は、未対処の失敗があることと件数を、対応する権限を持つメンバーが管理画面を利用するときに示す。件数は、送信結果の単位で数える。失敗の一覧も同じ単位で、未対処と対処済みで絞り込める。未対処で絞り込んだ一覧の件数は、示した件数と一致する。ほかのシナリオは、この節の規則と回数を参照する。
