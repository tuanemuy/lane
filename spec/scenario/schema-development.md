# スキーマの開発

開発者が、スキーマをコードで定義し、手元で検証して型を得て、ワークスペースへ反映する。用語は `spec/requirements.md` の 1 章に従う。

## 共通の前提

- スキーマと移行定義は開発者のリポジトリにある。リポジトリの構成と管理主体は開発者が決める。
- 開発者は開発環境でコマンドを実行する。CMS に接続するコマンドは、開発環境に設定した接続先とトークンを使う。操作対象のワークスペースはトークンで決まる。
- CMS に接続するコマンドは、対象のワークスペースを結果に示す。

### CMS に接続する操作に共通する異常系

SDEV-05、SDEV-06、SDEV-07 のコマンドには、`index.md` の「共通の規則」を適用する。このファイルは次を加える。

- 権限不足（許可の発行条件）: スキーマ反映の許可とコンテンツ管理の許可をトークンに与える条件は、`index.md` の「トークンの許可」に従う。
- 権限不足（メンバーに紐付くトークン）: 開発者が認証を経て得たトークン（AUTH-06）の認可は、`index.md` の「トークンの許可」に従う。権限の不足で拒否された場合、開発者は、メンバー管理の権限を持つメンバーに権限を依頼する。
- リソース不在（意図と異なるワークスペース）: 結果に示されたワークスペースが意図と異なる場合、開発者はトークンを切り替えて実行し直す。

## SDEV-01 モデルとフォームのスキーマをコードで定義する

- 利用者: 開発者
- 目的: コンテンツとフォームの構造を、ワークスペースで一つのスキーマとしてコードに宣言する。
- 要件: 1, 2, 3.1, 4.1, 4.4, 5.3, 6.1, 6.4, 8.1, 8.2

### 正常系

1. 開発者は、リポジトリの任意の場所にスキーマのコードを置く。一つのワークスペースを使うアプリは、同じスキーマの定義を共有する。
2. 開発者は、モデルをキーで宣言する。複数件を持つモデルか、単一の情報かを選ぶ。
3. 開発者は、モデルに項目をキーで宣言する。項目の型は、テキスト（一行・複数行）、数値、真偽値、日付、日時、単一選択、複数選択、リッチテキスト、メディア、コンテンツ参照、項目のまとまり、繰り返し、許可した種類のブロックから選ぶ。
4. 開発者は、項目に、必須条件、初期値、標準の制約、一意にする制約、参照を許可するモデルを宣言する。日付・日時の初期値には、作成時点を指定できる。
5. 開発者は、表示と運用に使う定義を宣言する。表示名称と順序、編集画面に示す説明と入力例、一覧表示・検索に使う項目、画像の派生形式、モデルごとのプレビュー先の経路、非推奨を含む。
6. 開発者は、フォームをキーで宣言する。項目の型は、テキスト、数値、真偽値、日付、日時、単一選択、複数選択、公開コンテンツへの参照から選ぶ。検証は、必須、文字数、範囲、テキストの書式、選択肢と選択数、真偽値が真であること、同じ型の二項目の一致から選ぶ。フォームにも、一覧表示用の項目を宣言する。CMS は、回答の一覧表示と部分一致の検索にこの項目を使う（FORM-07）。
7. 問い合わせ対象を使うフォームでは、開発者は、コンテンツ参照の項目ごとに許可するモデルを宣言し、モデル側に問い合わせ対象の表示に使う項目を宣言する。問い合わせ対象の項目は一つのフォームに複数置ける。コンテンツと無関係なフォームは、モデルを宣言せずに定義できる。
8. 開発者は、スキーマを保存する。この時点で CMS は何も変わらない。続けて SDEV-02 で検証する。

表示名称だけを変えた場合、キーと保存済みの値は変わらず、移行定義を必要としない。モデル・項目・選択肢・ブロックの種類のキーを変えた場合は、SMIG-01 で移行定義を生成する。フォームとその項目のキーを変えた場合は、削除と追加として扱われる（SMIG-07、SMIG-13）。

### 異常系

- 入力エラー（スキーマ自体の不整合）: キーの重複、存在しないモデル・項目への参照定義、型に適用できない制約、初期値の型不適合、表示・検索用項目の不適合、必須の項目への非推奨の指定は、SDEV-02 の検証が検出する。開発者は示された定義を直す。
- 入力エラー（スキーマに書けないもの）: 通知メールの定義、通知先、受付状態、保持方針などの運用設定は、スキーマに宣言できない。開発者はこれらを管理画面の運用設定（FORM-02、FORM-03、FORM-05、FORM-06）または初期構成（HOST-02）で用意する。利用者独自の検証関数も宣言できない。開発者は標準の制約とテキストの書式のパターンで表す。
- 入力エラー（フォームで扱えない型）: フォームには、メディア、リッチテキスト、項目のまとまり、繰り返し、ブロックを宣言できない。SDEV-02 の検証が型の不適合として示す。
- 操作の取り消し: 開発者は、反映する前ならコードを元に戻すだけで取り消せる。CMS は反映するまでスキーマの変更を知らない。

## SDEV-02 CMS に接続せずにスキーマの不整合を検出する

- 利用者: 開発者
- 目的: 反映する前に、スキーマ自体の誤りを開発環境で見つけて直す。
- 要件: 3.1, 6.4

### 正常系

1. 開発者は、開発環境で検証のコマンドを実行する。コマンドは CMS に接続しない。
2. コマンドは、スキーマ全体を検証する。検証する内容は、キーの重複、存在しないモデル・項目への参照定義、型に適用できない制約、初期値の型不適合、表示・検索用項目の不適合、必須の項目への非推奨の指定。
3. 不整合が無ければ、コマンドは不整合が無いことを示して成功で終わる。
4. 移行定義がリポジトリにある場合、同じ検証のコマンドが、スキーマと移行定義の食い違いと移行定義の不整合も示す（SMIG-03）。スキーマ自体の不整合とは区別して示す。

### 異常系

- 入力エラー（不整合がある）: コマンドは、不整合ごとに、該当する定義と理由を示して失敗で終わる。開発者は定義を直して実行し直す。
- 入力エラー（必須の項目への非推奨の指定）: コマンドは、該当する項目と、任意化と非推奨の指定を同じ反映で行う手順を示す。開発者は項目を任意にして非推奨を指定し、SMIG-01 で移行定義を生成する。
- 入力エラー（スキーマのコードを読み込めない）: コマンドは、読み込めない箇所と理由を示して失敗で終わる。開発者はコードを直す。
- 検証を通さずに反映した場合: CMS は反映時に同じ検証を行い、不整合のあるスキーマを拒否する（SDEV-05、SMIG-06）。

既存データが反映後の条件を満たすかどうかは、この検証では分からない。開発者は SMIG-05 の適用の事前確認で確かめる。

## SDEV-03 CMS に接続せずに、スキーマから型と識別子を得る

- 利用者: 開発者
- 目的: 反映する前から、変更後のスキーマの型でアプリを実装し、スキーマの識別子を得る。
- 要件: 3.1, 3.2, 4.4, 6.1, 6.4

### 正常系

1. 開発者は、スキーマを変更して保存する。
2. 開発者は、開発環境でスキーマから型を得る。型は、スキーマからの対応の規則で導かれる。規則は、値の種類ごとの型、必須と任意、非推奨の示し方、参照の展開、画像の派生形式を定める。CMS への接続もスキーマの反映も必要としない。
3. 開発者は、得た型でアプリを実装する。型が表すものは次のとおり。
   - コンテンツの取得結果。メディアでは、元の画像と各派生形式の配信先、画像形式、幅、高さを含む
   - フォームの送信内容、項目ごとの入力エラー、受付完了と理由付きの受付失敗
   - コンテンツ管理の許可による作成、下書きの保存、値の書き換えで指定する値
   - 非推奨を指定したモデル・項目・選択肢・ブロックの種類が、非推奨であること
4. アプリは、識別子を要求に添える。誰が識別子を求めるかは APP-07 の手順 2 に従う。HTTP API を直接呼ぶアプリ（APP-01 の手順 6）では、開発者は識別子を得るコマンドを実行し、示された識別子をアプリに置く。コマンドは CMS に接続せず、スキーマ全体の識別子と、モデル・フォームごとの識別子を示す。
5. 現行スキーマの識別子との一致は、SDEV-07 で確かめる。

識別子は型の形だけから決まる。制約と検証、一意性、表示・運用の定義だけを変えても変わらない。画像の派生形式のキーを変えると変わる。モデル・フォームごとの識別子は、ほかのモデル・フォームの変更では変わらない。

### 異常系

- 入力エラー（スキーマに不整合がある）: 識別子を得るコマンドは、識別子を示さず、SDEV-02 と同じ不整合を示して失敗で終わる。開発者は定義を直して実行し直す。
- 入力エラー（アプリのコードが変更後の型に合わない）: 開発環境の型検査が、合わない箇所を示す。開発者はアプリのコードを直す。削除したキーを使う箇所と、非推奨の対象を使う箇所が分かる。
- 操作の取り消し: 開発者がスキーマを元に戻すと、型と識別子も元に戻る。

## SDEV-04 CMS を手元に設置して、編集画面・取得・フォーム受付を試す

- 利用者: 開発者
- 目的: 運用中のワークスペースに影響を与えずに、スキーマと移行定義を手元の設置で試す。
- 要件: 3.1, 8.1, 9.3, 10.1

### 正常系

1. 開発者は、初期構成に、ワークスペース、所有者、トークン、運用設定を宣言する（HOST-02）。フォーム受付を試す場合は、送信接続設定、フォームごとの通知先、受付状態を宣言する。
2. 開発者は、手順に沿って CMS を手元で起動する。データが空の状態で起動した CMS は、初期構成を読み込む。
3. 開発者は、初期構成で宣言したトークンと手元の設置の接続先を、開発環境とアプリに設定する。
4. 開発者は、スキーマを反映する。移行定義を作らずに進める場合は直接反映（SDEV-05）、移行定義を試す場合は SMIG-06 を使う。
5. CMS は、初期構成でキーを指定して宣言した運用設定を、そのキーのモデル・フォームの作成時に紐付ける。作成したフォームの受付状態は、`form-operation.md` の「共通の規則」に従う。
6. 開発者は、初期構成で宣言した所有者として管理画面にログインし（AUTH-02）、定義に対応する編集画面でコンテンツを作成・編集・公開する。項目の説明、入力例、制約が編集画面に示される。
7. 開発者は、アプリから取得とフォーム送信を試す（APP-02 から APP-08）。
8. 開発者は、スキーマを変更し、手順 4 から繰り返す。

手元の設置は、運用中の設置と同じ機能を持つ。運用中の設置で検証に使うワークスペースは、通常のワークスペースとして同じ手順で使う。反映先の切り替えは、トークンと接続先の切り替えで行う。

### 異常系

- 入力エラー（不正な初期構成）: CMS は起動せず、該当する宣言と理由を示す。開発者は初期構成を直して起動し直す。
- 入力エラー（初期構成を変えても反映されない）: データがある状態で起動した CMS は、初期構成を読み込まない。開発者は、管理画面で運用設定を変えるか、SDEV-06 でデータの保存先を空にして起動し直す。
- 入力エラー（フォームの受付を有効にできない）: 有効な通知先または送信接続設定が無いフォームは、受付を有効にできない。CMS は足りない設定を示す。開発者は管理画面で設定する（FORM-01、FORM-02、FORM-05）か、初期構成に宣言して SDEV-06 で起動し直す。
- 入力エラー（紐付かない運用設定）: 初期構成の運用設定が指定するキーのモデル・フォームがスキーマに無い場合、その運用設定は紐付けを待つ状態で残る。開発者は HOST-03 で確認し、初期構成のキーかスキーマを直す。
- 権限不足: 初期構成で宣言したトークンに必要な許可が無い場合、CMS は要求を拒否して不足している許可を示す。開発者は、管理画面でトークンを発行する（WS-06）か、初期構成の宣言を直して SDEV-06 で起動し直す。
- リソース不在（スキーマを反映していない）: アプリがモデル・フォームを指定して取得・送信すると、CMS は対象のキーを示すエラーを返す。開発者はスキーマを反映する。
- 操作の取り消し: 開発者は CMS を停止して試行をやめる。保存先のデータは残り、次に起動すると続きから使える。データを作り直す場合は SDEV-06 を行う。

## SDEV-05 スキーマの構造をワークスペースへ直接反映する

- 利用者: 開発者
- 目的: 移行定義を作らずに、手元のスキーマをワークスペースの現行スキーマにする。
- 要件: 3.1, 5.4, 6.1, 6.3, 9.1, 9.2, 9.3, 10.1

### 正常系

1. 開発者は、対象のワークスペースの、スキーマ反映の許可を持つトークンを開発環境に設定する。
2. 開発者は、直接反映のコマンドを実行する。コマンドは、スキーマ全体を CMS へ送る。
3. CMS は、スキーマを SDEV-02 と同じ内容で検証する。
4. CMS は、現行スキーマとの差分を求める。差分が、失われる値・項目・コンテンツ、削除して受付を終了するフォーム、キーの違いから削除と追加として扱うフォームと項目、不整合となる通知定義の参照のどれも生じない場合は、手順 6 へ進む。
5. 差分がそれらを生じる場合、コマンドは、生じるものを示し、開発者に確認を求める。開発者は内容を確かめて確認する。確認の後の要求は、確認を求めた要求と同じ、前提とする現行スキーマの版を添える。
6. CMS は、スキーマ全体を現行スキーマとして確定する。運用設定は上書きしない。新しいフォームの受付状態は、`form-operation.md` の「共通の規則」に従う。初期構成でそのキーに宣言した運用設定を紐付ける。
7. コマンドは、反映の成功と、反映後のスキーマの版と識別子を示す。
8. 直接反映によって公開内容が変わるか失われた場合、CMS は、確定後に、スキーマの反映として一つの通知で表示アプリへ伝える（APP-11）。通知は、スキーマの版、変更した対象、変更の種類を識別できる。失われた公開中のコンテンツは、公開取り消しとして伝える。通知の状況は PUB-08 で確認する。
9. CMS は、この版が直接反映によることと、失った値・項目・コンテンツの種類を、スキーマの版の記録に残す。移行定義の適用記録には残さない。直接反映を操作履歴に残す。

直接反映は、スキーマ反映の許可を持つトークンだけが要求できる。メンバーは管理画面から直接反映を行えない。

直接反映は差分だけから反映する。キーの変更は、削除と追加として扱う。変換規則のある組み合わせでの値の種類の変更は、移行の適用と同じ変換規則で値を変換する（SMIG-06）。変換規則のない組み合わせでの値の種類の変更は、同じキーの項目の削除と追加として扱う。キーをまたいで値を引き継ぐ変更は、移行定義で行う（SMIG-01）。

どのワークスペースへ直接反映できるかは、スキーマ反映の許可を持つトークンをどこに置くかで決まる。CMS は、ワークスペースが運用中かどうかで直接反映を拒否しない。運用中のワークスペースへの直接反映を防ぐ場合、開発者は、そのワークスペースのトークンを直接反映に使う環境に置かない。

### 異常系

- 入力エラー（スキーマに不整合がある）: CMS は反映を拒否し、該当する定義と理由を示す。現行スキーマ、データ、運用設定は変わらない。開発者は定義を直して実行し直す。拒否した反映と失敗した反映は、表示アプリへ通知しない。
- 入力エラー（反映後の公開内容による失敗）: 反映後の公開内容が、SMIG-06 の「失敗する場合」のいずれかに当たると、反映は失敗し、CMS は何も変更しない。失敗の条件、CMS が示す内容、開発者の次の操作は、SMIG-06 の「失敗する場合」に従う。そのうち、移行定義を直す解消方法は、直接反映では使えない。
- 別の反映が適用中、別の反映が先に確定していた、差分が無い: SMIG の「版を変える要求に共通する異常系」に従う。直接反映のコマンドは、SMIG の「共通の前提」のとおり、開発者に示した現行スキーマの版を、前提とする版として要求に添える。
- 操作の取り消し（確認で取りやめる）: 開発者が手順 5 で確認しなければ、CMS は何も変更しない。
- 操作の取り消し（対話できない環境）: コマンドは、確認の指定が無ければ、手順 5 で示すものを示して反映せずに終わる。開発者は、内容を確かめたうえで確認を指定して実行し直す。
- 受け付けた後の失敗・中断: CMS が受け付けた直接反映は取り消せない。コマンドを中断しても、接続が切れても、CMS は反映を進め、確定か失敗のどちらかで終える。容量や処理能力の上限による失敗、確定の時点の切り替えの拒否、進行が止まった反映の中断の扱いは、SMIG-06 と SMIG-14 に従う。失敗した直接反映は、現行スキーマ、データ、運用設定を変えない。開発者は、SMIG-14 で結果を確かめてから、実行し直す。
- 操作の取り消し（確定後）: 確定した直接反映は、スキーマを元に戻して再び直接反映することで戻す。失われた値・項目・コンテンツは戻らない。戻す手段は、設置全体のバックアップからの復旧（HOST-08）か、手元の設置での作り直し（SDEV-06）に限られる。
- 権限不足・リソース不在: 共通の異常系に従う。必要な許可はスキーマ反映。
- 直接反映の後に移行定義を適用できない: 直接反映によって、現行スキーマのコンテンツの構造が適用済みの移行定義を順に適用した結果と食い違うと、CMS は移行定義の適用を拒否する。開発者は、直接反映で一致する構造に戻すか、SMIG-08 で移行定義を適用済みとして記録する。

## SDEV-06 データの保存先を空にして起動し直し、同じ状態からデータを投入する

- 利用者: 開発者
- 目的: 手元の設置のデータを作り直し、同じコンテンツID を持つ同じ状態から開発を再開する。
- 要件: 3.1, 3.2, 4.2, 9.3, 10.1

### 正常系

1. 開発者は、CMS を停止する。
2. 開発者は、手順書に沿って設置のデータの保存先を空にする。設置のすべてのワークスペースのデータが消える。
3. 開発者は、CMS を起動する。データが空の状態で起動した CMS は、初期構成を読み込み、ワークスペース、所有者、トークン、運用設定を用意する。トークンの値は初期構成で宣言した値のため、開発環境とアプリの設定を変える必要は無い。
4. 開発者は、スキーマを反映する（SDEV-05 または SMIG-06）。CMS は、初期構成のモデル・フォームごとの運用設定を、キーが一致する対象に紐付ける。
5. 開発者は、開発環境で、データを投入するスクリプトを実行する。スクリプトは、コンテンツ管理の許可を持つトークンで、コンテンツID を指定してコンテンツを作成し、メディアを登録し、必要なコンテンツを公開する（APP-09）。投入するデータとスクリプトは開発者が用意する。値はスキーマの型で扱える。
6. CMS は、指定した ID でコンテンツを作成する。起動し直すたびに、同じ ID のコンテンツができる。
7. 開発者は、管理画面とアプリで、投入した状態を確かめて開発を再開する。

### 異常系

- 入力エラー（投入する値がスキーマに合わない）: CMS は、管理画面と同じ入力検証を適用する。現行スキーマの値の種類・構造に合わない値の作成は、項目ごとの理由を付けて拒否する。必須の欠落や制約の違反は下書きの入力エラーとして保存し、公開は拒否する。開発者は投入するデータを直して実行し直す。
- 入力エラー（不正な初期構成）: CMS は起動せず、該当する宣言と理由を示す。開発者は初期構成を直して起動し直す。
- 投入が途中で止まった: 開発者はスクリプトを最初から実行し直す。指定した ID のコンテンツが同じ内容で既にある作成に対して、CMS は作成せず、同じ内容で既にあることを成功として示す。コンテンツは重複しない。スクリプトは、その対象を作成済みとして次へ進む。違う内容で既にある場合の扱いは、APP-09 の「競合（違う内容で既にある）」に従う。
- 権限不足: 共通の異常系に従う。必要な許可はコンテンツ管理で、トークンに許可する操作は `index.md` の「トークンの許可」に従う。
- リソース不在（スキーマを反映していない）: 存在しないモデル・項目を指定した作成に対して、CMS は対象のキーを示すエラーを返す。開発者は手順 4 を行ってから実行し直す。
- リソース不在（ワークスペース単位の作り直し）: データの作り直しは、設置の保存先を空にして起動し直す手順 1 から 3 で行い、設置のすべてのワークスペースが対象になる（HOST-02 の「データの作り直し」）。
- 操作の取り消し: 保存先を空にする操作は取り消せない。消したデータを戻す手段は、空にする前に取得したバックアップからの復旧（HOST-08）に限られる。開発者は、残すデータがある設置では行わない。

## SDEV-07 反映済みのスキーマと反映結果を確認する

- 利用者: 開発者、スキーマ変更権限を持つメンバー
- 目的: ワークスペースの現行スキーマを確かめる。反映ごとの結果と反映できなかった理由は、SMIG-14 で確かめる。
- 要件: 3.1, 6.1, 9.2

### 正常系（開発者がコマンドで確認する）

1. 開発者は、スキーマ反映の許可を持つトークンで、適用状況の確認のコマンドを実行する。出力は SMIG-04 が定める。
2. 開発者は、出力のうち、現行スキーマの版と識別子と、手元のスキーマの識別子との一致・不一致を読む。一致すれば、手元のスキーマと現行スキーマの型の形は同じである。反映ごとの結果は、SMIG-14 で読む。

### 正常系（メンバーが管理画面で確認する）

1. スキーマ変更権限を持つメンバーは、管理画面でスキーマの表示を開く。
2. 管理画面は、現行スキーマのモデルとフォームを示す。それぞれについて、キー、表示名称、項目、型、制約、説明・入力例、非推奨の指定を確認できる。管理画面ではスキーマを編集できない。
3. メンバーは、反映の結果と版の記録を SMIG-14 で確認する。

### 異常系

- 権限不足（コマンド）: 共通の異常系に従う。必要な許可はスキーマ反映。
- 権限不足（管理画面）: `index.md` の「共通の規則」に従う。必要な権限はスキーマ変更権限。スキーマ変更権限を持たないメンバーも、項目の説明、入力例、制約を編集画面で参照できる。
- リソース不在（スキーマを一度も反映していない）: コマンドと管理画面は、反映済みのスキーマが無いことを示す。開発者は SDEV-05 または SMIG-06 で反映する。
- リソース不在（識別子が一致しない）: 手元のスキーマと現行スキーマの型の形が異なる。開発者は、SMIG-04 で適用状況と食い違いを確かめ、反映するか、手元のスキーマを現行に合わせる。
