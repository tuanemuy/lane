# ワークスペースの管理

所有者・管理者が、メンバー、権限、トークン、運用設定を管理する。用語は `spec/requirements.md` の 1 章に従う。「要件」は `spec/requirements.md` の節番号を指す。

## 共通の規則

`spec/scenario/index.md` の「権限」「共通の規則」に加えて、このカテゴリーの全シナリオに適用する。

- メンバー、権限、トークン、運用設定は、ワークスペースごとに管理する。権限はワークスペース単位で付与する。モデル、フォーム、個別のコンテンツ、項目ごとの権限は設定できない。
- このカテゴリーの操作は管理画面でだけ行う。トークンでは、メンバーと運用設定を変更できない。
- 運用設定は、スキーマの再反映で変わらない。
- ワークスペースの作成、初期所有者の設定、利用終了は、ホスティング運営者が HOST-04 と HOST-09 で行う。管理画面には示さない。
- 招待の種類: 招待は、メンバーの招待（WS-01）と、ホスティング運営者が発行する初期所有者の招待（HOST-04）の二種類である。同じワークスペースの、同じ種類の、同じメールアドレスへの未使用で期限内の招待は、一つである。新しい招待が前の招待を置き換え、前の招待は失効して、前の URL では参加できない。初期所有者の招待は、宛先を変えた発行し直しでも、前の招待を置き換える。種類が違う招待は、互いを妨げず、互いを失効させない。同じ宛先に、未使用のメンバーの招待と、未使用の初期所有者の招待が同時にあってよい。一方の受諾は、他方を使用済みにも失効にもしない。

## WS-01 メンバーを招待する

- **利用者**: メンバー管理の権限を持つメンバー
- **目的**: 新しい担当者を、必要な権限を決めてワークスペースに加える。
- **要件**: 3.1, 9.1, 9.2

### 正常系

1. メンバーが、招待する人のメールアドレスを入力する。
2. メンバーが、与える権限を決める。`spec/scenario/index.md` の「権限」の標準の役割を選ぶか、同じ節の表の権限を個別に組み合わせる。問い合わせ担当者には、回答の閲覧権限だけを与えられる。権限を一つも選ばない招待で参加したメンバーは、どのメンバーも行える閲覧（`spec/scenario/index.md` の「権限」）だけを行える。
3. 通知設定の権限を含む場合、CMS は、その権限を持つ人が通知先を変えることで回答の入力内容を通知経由で取得できることを示す。
4. メンバーが招待を確定する。CMS は、対象のメールアドレスと有効期限（有効期間は APP-12）を持つ招待を作り、一度だけ使える招待の URL を、設置全体のメール送信で対象へ送る。CMS は有効期限を示す。ワークスペースの送信接続設定は招待に使わない。
5. CMS は、未使用の招待を、対象、権限、有効期限とともに一覧に示す。有効期限を過ぎた未使用の招待は、期限切れと示す。招待された人は AUTH-01 で参加する。参加すると、招待は使用済みになり、招待で決めた権限を持つメンバーになる。
6. CMS は、招待の作成と取り消しを操作履歴に残す。

メンバーは、未使用の招待を取り消せる。取り消した招待は失効し、その招待では参加できない。初期所有者の招待は、未使用の招待の一覧に示さず、メンバーは取り消せない。招待の置き換えは、「共通の規則」の「招待の種類」に従う。

### 異常系

- 入力エラー: メールアドレスの形式が正しくない場合、CMS は招待を作らず、理由を示す。メンバーは入力を直す。
- 既にメンバーである: 対象が既にこのワークスペースのメンバーである場合、CMS は招待を作らず、そのことを示す。権限を変える場合は WS-02 で行う。
- 有効な招待が既にある: 同じメールアドレスに未使用で期限内のメンバーの招待がある場合、CMS は新しい招待で前の招待を置き換え（「共通の規則」の「招待の種類」）、置き換えたことを示す。新しい招待が決めた権限と有効期限が有効になる。
- 所有者: 所有者は招待で指定できない。所有者にする場合は、参加の後に所有者が WS-04 で変更する。
- 外部メールを使えない設置: CMS は招待のメールを送らず、一度だけ使える招待の URL を、招待したメンバーに示す。メンバーは、招待する本人を確かめて、URL を CMS の外で渡す。招待の対象、有効期限、使用済み・失効の扱いは、メールで送る招待と同じである。CMS は URL を招待の確定時にだけ示す。URL を控え損ねた場合、メンバーは同じメールアドレスへ招待し直す。
- メールの送信失敗: 外部メールを使える設置で招待のメール送信に失敗した場合、CMS は招待を残し、送信に失敗したことを示す。メンバーは同じメールアドレスへ招待し直す。失敗が続く場合は、ホスティング運営者に設置全体のメール送信の確認を依頼する。
- 期限切れ: 有効期限を過ぎた招待では参加できない。メンバーは同じメールアドレスへ招待し直す。期限切れの招待は、新しい招待に置き換わり、一覧から外れる。
- リソース不在: 取り消そうとした招待が既に使用済みの場合、CMS は取り消しを拒否し、対象が参加済みであることを示す。参加を取り消す場合は WS-03 で解除する。
- 操作の取り消し: 確定前にやめると招待は作られない。確定した招待は、使用される前なら取り消せる。送った招待メールと手渡した URL は回収できないが、取り消した招待では参加できない。

## WS-02 メンバーの権限を変更する

- **利用者**: メンバー管理の権限を持つメンバー
- **目的**: 担当の変更に合わせて、メンバーが行える操作を変える。
- **要件**: 9.1, 9.2, 9.3

### 正常系

1. メンバーが、メンバーの一覧を開く。CMS は、メンバーごとに現在の役割と権限を示し、所有者であるメンバーを示す。
2. メンバーが、対象のメンバーを選び、`spec/scenario/index.md` の「権限」の標準の役割を選び直すか、同じ節の表の権限を個別に付け外しする。権限は互いに独立しており、どの組み合わせでも付与できる。
   - スキーマ変更権限は、移行と直接反映による値とコンテンツの消去、公開内容の変更、フォームの削除による受付の終了を、スキーマの反映の結果として含む。編集権限、公開権限、削除権限、メディア公開権限を兼ねない。
   - 通知設定の権限は、回答の閲覧権限と別に与える。
3. 通知設定の権限を新たに与える場合、CMS は、その権限を持つ人が回答の入力内容を通知経由で取得できることを示す。
4. メンバーが保存する。
5. 対象のメンバーに紐付くトークンと、対象のメンバーが手動発行したトークンの扱いは、`spec/scenario/index.md` の「トークンの許可」に従う。
6. CMS は、変更を操作履歴に残す。

### 異常系

- 権限をすべて外す: 権限をすべて外したメンバーは、どのメンバーも行える閲覧（`spec/scenario/index.md` の「権限」）だけを行える。利用をやめさせる場合は WS-03 で解除する。
- 所有者: 所有者は権限の変更の対象にならない。所有者を変える場合は、所有者が WS-04 で行う。
- リソース不在: 対象のメンバーが、他のメンバーの操作で既に解除されている場合、変更は確定せず、存在しない対象（`spec/scenario/index.md` の「共通の規則」）になる。
- 操作の取り消し: 保存前にやめると権限は変わらない。保存した変更を戻すには、権限を変更し直す。変更から戻すまでの間に対象のメンバーが行った操作は取り消されない。

## WS-03 メンバーの利用を解除する

- **利用者**: メンバー管理の権限を持つメンバー
- **目的**: 担当を外れた人が、ワークスペースを利用できないようにする。
- **要件**: 9.1, 9.2, 9.3

### 正常系

1. メンバーが、メンバーの一覧から対象のメンバーを選び、解除の操作を行う。
2. CMS は次を示し、確認を求める。
   - 対象のメンバーは、次の操作からこのワークスペースを利用できない。
   - 対象のメンバーに紐付くトークンと、対象のメンバーが手動発行したトークンの扱い（`spec/scenario/index.md` の「トークンの許可」）。該当するトークンの名称を示す。
3. メンバーが確定する。CMS は対象のメンバーを解除する。
4. CMS は、解除を操作履歴に残す。
5. 解除されたメンバーが手動発行したトークンは、WS-07 の一覧に、発行者が解除されたトークンとして現れる。アプリ連携の権限を持つメンバーが見直す。

### 異常系

- 所有者の解除: 所有者の解除を、CMS は拒否し、所有者が不在になることを示す。所有者だったメンバーを解除する場合は、所有者が WS-04 で別のメンバーへ所有者を変更してから、解除する。
- リソース不在: 対象のメンバーが既に解除されている場合は、存在しない対象（`spec/scenario/index.md` の「共通の規則」）になる。
- 操作の取り消し: 確定した解除を戻すには、WS-01 で招待し直す。解除で拒否されるようになったメンバーに紐付くトークンは、再び参加しても戻らない。メンバーは AUTH-06 で認証し直し、承認の画面で対象のワークスペースを選んでトークンを得る。

## WS-04 ワークスペースの所有者を変更する

- **利用者**: 所有者
- **目的**: ワークスペースの最終的な管理責任を、別のメンバーへ移す。
- **要件**: 9.1, 9.2

### 正常系

1. 所有者が、メンバーの一覧から新しい所有者にするメンバーを選び、所有者を変更する操作を行う。
2. CMS は次を示し、確認を求める。
   - 選んだメンバーが所有者になり、すべての権限を持つ。
   - 選んだメンバーが通知設定の権限を新たに持つ場合、その人が回答の入力内容を通知経由で取得できる。
   - 元の所有者は、管理者の権限の組（すべての権限）を持つメンバーになる。元の所有者が持つ権限は、変更の前後で変わらない。
   - 変更の後、元の所有者は自分で所有者へ戻せない。
3. 所有者が確定する。CMS は所有者を変更する。
4. CMS は、変更を操作履歴に残す。

### 異常系

- 権限不足: 所有者の変更は、所有者だけが行える操作（`spec/scenario/index.md` の「権限」）である。
- リソース不在: 新しい所有者にする人がメンバーでない場合、所有者に選べない。WS-01 で招待し、参加の後に変更する。選んだメンバーが確定までに解除された場合、CMS は変更を拒否し、対象がメンバーでないことを示す。所有者は変わらない。
- 所有者と連絡が取れない: 所有者がログインできない場合は AUTH-04 でアクセスを回復する。外部メールを使えない設置では、ホスティング運営者が HOST-11 で復旧する。
- 所有者がいない: 所有者がいないワークスペース（HOST-04、HOST-08）では、所有者だけが行える操作（`spec/scenario/index.md` の「権限」）を行えない。メンバーは、ホスティング運営者へ、初期所有者の招待の発行し直しを依頼する（HOST-04）。招待を受けた人が所有者になる。
- 操作の取り消し: 確定した変更を戻すには、新しい所有者が同じ操作で所有者を変更する。

## WS-05 メンバーに多要素認証を必須にする

- **利用者**: 所有者
- **目的**: ワークスペースを利用するすべてのメンバーに、多要素認証を使わせる。
- **要件**: 9.2

### 正常系

1. 所有者が、AUTH-03 で自分の多要素認証を設定する。
2. 所有者が、多要素認証を必須にする操作を行う。CMS は、多要素認証を設定していないメンバーを示し、該当するメンバーが設定を終えるまでこのワークスペースを利用できなくなることを示して、確認を求める。
3. 所有者が確定する。CMS は、このワークスペースで多要素認証を必須にする。
4. 多要素認証を設定していないメンバーがこのワークスペースを利用しようとすると、CMS は次の操作から利用を止め、設定を求める。メンバーは AUTH-03 で設定し、利用を続ける。必須にした後に自分の多要素認証を解除したメンバーにも、同じ条件を適用する。
5. 以後に WS-01 の招待で参加する人にも、同じ条件を適用する。
6. 所有者は、メンバーの一覧で、メンバーごとの多要素認証の設定の有無を確かめる。

所有者は、同じ操作で必須を解除できる。解除すると、多要素認証を設定していないメンバーも利用できる。

必須の設定は、手動発行したトークンを使う表示アプリの配信、フォームの受付、スキーマの反映を止めない。

### 異常系

- 所有者が未設定: 所有者自身が多要素認証を設定していない場合、CMS は必須にする操作を拒否し、理由を示す。所有者は AUTH-03 で設定してから必須にする。
- 権限不足: 必須にする操作と解除する操作は、所有者だけが行える操作（`spec/scenario/index.md` の「権限」）である。
- 多要素認証の手段を失ったメンバー: メンバーは AUTH-04 でアクセスを回復する。
- 操作の取り消し: 必須にした設定は、解除で戻す。メンバーが設定した多要素認証は、解除しても残る。

## WS-06 トークンを手動発行する

- **利用者**: アプリ連携の権限を持つメンバー
- **目的**: 表示アプリやスクリプトが、決めた許可の範囲でワークスペースに接続できるようにする。
- **要件**: 3.1, 9.1, 9.2, 9.3

### 正常系

1. メンバーが、トークンの名称を入力する。名称には、使うアプリと用途が分かる名前を付ける。
2. メンバーが種類を選ぶ。値を秘匿できる環境で使うトークンはサーバー用、利用者から値が見える環境で使うトークンはブラウザ用である。
3. メンバーが許可を選ぶ。
   - サーバー用は、公開取得、プレビュー取得、フォーム送信、スキーマ反映、コンテンツ管理から選ぶ。
   - ブラウザ用は、公開取得、フォーム送信から選ぶ。
   - 選べる許可は、`spec/scenario/index.md` の「トークンの許可」に従う。コンテンツ管理を選んだ場合、CMS は、そのトークンに許可する操作を示す。
4. メンバーが範囲を選ぶ。範囲は、ワークスペース全体、または選んだモデル・フォームの集合である。CMS は、範囲の選択肢として、現行スキーマのモデルとフォームを、キーと表示名称で示す。ワークスペース全体を選んだトークンは、発行の後に追加したモデル・フォームも対象にする。スキーマ反映の許可を選んだトークンの範囲は、ワークスペース全体に限る。
5. ブラウザ用の場合、メンバーが、利用元の限定と利用量の制限を設定する。CMS は、ブラウザ用トークンの値が第三者に知られる前提であることと、利用元の限定が本人確認にならないことを示す。
6. メンバーが有効期限を設定する。期限を設けない場合は、期限なしを明示して選ぶ。
7. メンバーが発行を確定する。CMS はトークンを発行し、値を示す。サーバー用トークンの値は、この時だけ示す。CMS は、後から値を表示できないことを示す。ブラウザ用トークンの値は、後からも確認できる。
8. メンバーが値を控え、アプリの設定に渡す。
9. CMS は、発行を操作履歴に残す。トークンの値は操作履歴に残さない。

範囲は、モデル・フォームに紐付く運用設定である。スキーマの再反映と表示名称の変更では変わらない。移行定義でモデルのキーを変更しても、範囲はそのモデルを対象にし続ける。モデル・フォームを削除すると、その対象は範囲から外れる。同じキーの対象を後から追加しても、範囲には戻らない。フォームのキーの変更は削除と追加として扱うため、新しいフォームは範囲に入らない。

発行したトークンの種類、許可、範囲、有効期限は、発行の後に変更できない。変える場合は、新しいトークンを発行して WS-07 で入れ替える。ブラウザ用トークンの利用元の限定と利用量の制限は、WS-07 で変更できる。

手動発行したトークンはアプリに紐付く。発行したメンバーの解除と権限の変更での扱いは、`spec/scenario/index.md` の「トークンの許可」に従う。トークンは発行元のワークスペースだけを操作でき、人のセッションの代わりにはならない。回答の閲覧と削除、メンバーと運用設定の変更は、どのトークンでも行えない。本番と検証の接続先は、アプリに渡すトークンを切り替えて変える。

### 異常系

- 入力エラー: 名称がない、許可を一つも選んでいない、有効期限が過去の日時である、有効期限を設定せず期限なしも選んでいない、のいずれかの場合、CMS は発行せず、項目と理由を示す。メンバーは入力を直す。
- 種類に合わない許可: ブラウザ用には、プレビュー取得、スキーマ反映、コンテンツ管理を選べない。これらが必要な場合は、サーバー用を発行し、値を秘匿できる環境で使う。
- 許可と範囲の組み合わせ: スキーマの反映は、ワークスペースのスキーマ全体を対象にする。スキーマ反映の許可と、モデル・フォームの集合の範囲を組にした発行を、CMS は拒否し、理由を示す。メンバーは、範囲をワークスペース全体にするか、スキーマ反映の許可を別のトークンに分けて発行する。
- 権限を超える許可: 選べない許可が必要な場合は、その権限を持つメンバーに発行を依頼するか、WS-02 で権限の付与を受ける。確定までにメンバーの権限が縮小された場合、CMS は発行を拒否し、選べなくなった許可を示す。
- 権限不足: アプリ連携の権限を持たないメンバーは、自分の作業に使うトークンを AUTH-06 で認証を経て得る。対象のワークスペースは、AUTH-06 の承認の画面で、メンバーが所属するワークスペースから選ぶ。
- リソース不在: 範囲に選んだ対象が、確定までにスキーマの反映でなくなった場合、CMS は発行を拒否し、該当する対象を示す。メンバーは範囲を選び直す。モデルもフォームも無いワークスペースでは、範囲の選択肢はワークスペース全体だけである。
- 操作の取り消し: 確定前にやめるとトークンは発行されない。発行したトークンは、WS-07 で失効させて取り消す。サーバー用トークンの値を控えずに画面を離れた場合、値は取り戻せない。メンバーはそのトークンを WS-07 で失効させ、発行し直す。

## WS-07 トークンを一覧して見直し、失効・入れ替えを行う

- **利用者**: アプリ連携の権限を持つメンバー
- **目的**: 不要なトークンと漏れたおそれのあるトークンを止め、配信と受付を止めずにトークンを入れ替える。
- **要件**: 9.2, 9.3

### 正常系

一覧して見直す。

1. メンバーがトークンの一覧を開く。CMS は、トークンごとに、名称、種類、許可、範囲、発行者、発行日時、有効期限、最終利用日時を示す。初期構成で宣言したトークンの発行者は、初期構成の所有者である。メンバーに紐付くトークン（`spec/scenario/index.md` の「トークンの許可」）は名称を持たない。名称の代わりに発行の経路（AUTH-06 のスクリプトの認証、APP-06 のプレビュー）を、発行者の代わりに紐付くメンバーを示す。
2. CMS は、メンバーに紐付くトークンを、手動発行したトークンと初期構成で宣言したトークンと区別して示す。AUTH-06 で発行したトークンは、メンバーが承認の画面で選んだワークスペースを対象とし、そのワークスペースの一覧にだけ現れる。
3. 一覧に載る範囲は、次のとおりである。失効したトークンは、種類によらず、失効の時点で一覧から外れる。メンバーに紐付くトークンは、期限切れでも一覧から外れる。手動発行したトークンと初期構成で宣言したトークンは、期限切れの後も、期限切れとして一覧に載り、有効期限から、期限切れのトークンを一覧に残す期間（APP-12）が過ぎると一覧から外れる。一覧から外れたトークンの発行と失効は、操作履歴で確かめる（WS-11）。
4. メンバーが、有効期限が近いトークン、発行者または紐付くメンバーが解除されたトークン、長く使われていないトークンに絞り込む。有効期限が近いことと長く使われていないことの基準は APP-12 が定める。
5. メンバーが、各トークンを使い続けるかを判断する。不要なトークンは失効させる。期限が近いトークンと、発行者が解除されたトークンは、必要に応じて入れ替える。

失効させる。

1. メンバーがトークンを選び、失効の操作を行う。メンバーに紐付くトークンも失効できる。CMS は、次の要求からこのトークンを拒否すること、このトークンを使うアプリの配信、受付、反映が止まること、失効を取り消せないことを示し、確認を求める。
2. メンバーが確定する。CMS はトークンを失効させ、次の要求から拒否する。
3. CMS は、失効を操作履歴に残す。メンバーに紐付くトークンの発行と失効も、操作履歴に残る。

ブラウザ用トークンの利用元の限定と利用量の制限を変える。

1. メンバーが、ブラウザ用トークンを選び、利用元の限定と利用量の制限を入力する。CMS は、利用元の限定が本人確認にならないことを示す。
2. メンバーが保存する。CMS は、次の要求から新しい利用元の限定と利用量の制限を適用する。トークンの値は変わらず、アプリの設定を変える必要は無い。
3. CMS は、変更を操作履歴に残す。

入れ替える。

1. メンバーが、WS-06 で、古いトークンと同じ用途の新しいトークンを発行する。古いトークンは有効なままである。
2. 開発者が、アプリの設定を新しいトークンへ切り替える。
3. メンバーが、一覧で、新しいトークンの最終利用日時が更新され、古いトークンの最終利用日時が切り替えの後に進んでいないことを確かめる。
4. メンバーが古いトークンを失効させる。配信と受付は止まらない。

### 異常系

- 期限切れ: 有効期限を過ぎたトークンによる要求は、`spec/scenario/index.md` の「CMS に接続するコマンドと SDK の操作」に従う。一覧での示し方は、「一覧して見直す」の手順 3 に従う。使い続ける場合は、WS-06 で新しいトークンを発行してアプリを切り替える。
- 切り替え前の失効: アプリを切り替える前に古いトークンを失効させると、そのアプリの要求は拒否される。メンバーは WS-06 で新しいトークンを発行し、開発者がアプリを切り替えて復旧する。
- 入力エラー（利用元の限定と利用量の制限）: 指定できない利用元または利用量の制限を入力した場合、CMS は保存を拒否し、項目と理由を示す。メンバーは入力を直す。
- 変更できない項目: 変更できる項目と、変更できない項目を変える方法は、WS-06 に従う。範囲が変わるのは、モデル・フォームの削除による除外と、初期構成で宣言した範囲の紐付け（HOST-03）だけである。
- 範囲が空になったトークン: 範囲に選んだモデル・フォームがすべて削除されたトークンは、どの対象も操作できない。CMS は一覧で範囲が空であることを示す。メンバーはトークンを失効させ、必要なら新しい範囲で発行し直す。
- リソース不在: 選んだトークンが、他のメンバーの操作で既に失効している場合、CMS は失効も変更もせず、失効済みであることを示す。メンバーは一覧を開き直す。失効したトークンは、開き直した一覧に載らない。
- 操作の取り消し: 確定した失効は取り消せない。再び必要になった場合は、WS-06 で発行し直す。利用元の限定と利用量の制限は、保存前にやめると変わらない。保存した変更を戻すには、以前の値を入力して保存し直す。

## WS-08 プレビュー先の表示アプリの URL を設定する

- **利用者**: アプリ連携の権限を持つメンバー
- **目的**: 編集画面からのプレビューが、正しい表示アプリで開くようにする。
- **要件**: 3.1, 5.3, 9.1, 9.2

### 正常系

1. メンバーが、プレビュー先の表示アプリの URL の設定を開く。CMS は現在の URL を示す。URL はワークスペースに一つ持つ。
2. メンバーが、表示アプリの URL を入力する。CMS は、プレビューを開く操作のたびに、メンバーに紐付くトークンへ引き換える値をこの URL の表示アプリへ渡すことを示す。
3. メンバーが保存する。CMS は URL を保存する。
4. 以後、EDIT-12 のプレビューを開く操作は、この URL と、スキーマで定義したモデルごとの経路からプレビュー先を決める。
5. CMS は、変更を操作履歴に残す。

メンバーは、URL を取り除いて未設定に戻せる。

### 異常系

- 入力エラー: URL の形式が正しくない場合、CMS は保存を拒否し、理由を示す。メンバーは入力を直す。
- 未設定: URL が未設定の間、EDIT-12 のプレビューを開く操作は、開けない理由として URL が未設定であることを示す。プレビューを開こうとしたメンバーは、アプリ連携の権限を持つメンバーに設定を依頼する。
- 誤った URL: 誤った URL を保存すると、プレビューは誤った宛先で開き、引き換えの値がその宛先へ渡る。メンバーは URL を直す。引き換えの値は一度だけ使え、有効期間が限られる。
- 権限不足: 共通の規則に従う。
- 操作の取り消し: 保存前にやめると URL は変わらない。保存した URL を戻すには、以前の URL を入力して保存し直す。

## WS-09 表示アプリへの通知設定を管理する

- **利用者**: アプリ連携の権限を持つメンバー
- **目的**: 公開内容の変更を、表示アプリが受け取れるようにする。
- **要件**: 3.1, 5.4, 9.2

### 正常系

1. メンバーが、表示アプリへの通知設定を開く。CMS は、登録済みの宛先を示す。秘密情報の示し方は、`spec/scenario/index.md` の「秘密情報」に従う。
2. メンバーが、通知の宛先と秘密情報を入力して登録する。宛先は複数登録できる。
3. CMS は設定を保存する。登録した宛先は、登録の後に作られる通知から送信先になる。通知は、公開内容の変更の確定の後に作られ、作られる時点で登録されている宛先を送信先とする。
4. メンバーが、宛先を変更する、秘密情報を新しい値に置き換える、宛先を削除する。削除した宛先は、削除の後に作られる通知の送信先にならない。
5. CMS は、変更を操作履歴に残す。秘密情報の値は操作履歴に残さない。
6. 開発者は、同じ秘密情報を表示アプリに設定し、APP-11 で通知を受け取る。通知の送信結果の確認と、失敗した通知の再試行は、PUB-08 で行う。

この設定は、フォームの通知先と送信接続設定とは別である。

### 異常系

- 入力エラー: 宛先の形式が正しくない場合と、秘密情報が未入力の場合、CMS は保存を拒否し、項目と理由を示す。メンバーは入力を直す。
- 入力エラー（宛先の上限）: 登録できる宛先の件数には、上限（APP-12）がある。上限を超える登録を、CMS は拒否し、上限を示す。メンバーは、不要な宛先を削除してから登録する。
- 秘密情報の不一致: CMS の秘密情報だけを置き換えると、表示アプリは以後の通知を検証できない。メンバーは、開発者が表示アプリの秘密情報を更新する時期に合わせて置き換える。失敗した通知は、PUB-08 で確認し、手動再試行する。
- リソース不在: 変更しようとした宛先が、他のメンバーの操作で既に削除されている場合、変更は確定せず、存在しない対象（`spec/scenario/index.md` の「共通の規則」）になる。
- 操作の取り消し: 保存前にやめると設定は変わらない。削除した宛先は、登録し直して戻す。秘密情報は表示されないため、メンバーが手元の値を入力する。削除していた間に作られた通知は、その宛先を送信先に持たない。

## WS-10 コンテンツの保持方針を変更する

- **利用者**: ワークスペース設定の権限を持つメンバー
- **目的**: 履歴とごみ箱を保持する期間を、運用に合わせて決める。
- **要件**: 3.1, 7.2, 9.2

### 正常系

1. メンバーが、コンテンツの保持方針を開く。CMS は、履歴の保持方針と、ごみ箱の保持方針を示す。どちらもワークスペースに一つ持ち、フォーム回答の保持方針とは別である。ワークスペースは、作成の時点から、履歴とごみ箱の標準の保持方針（APP-12）を持つ。初期構成で宣言した場合は、宣言した保持方針を持つ（HOST-02）。
2. メンバーが、履歴またはごみ箱の保持方針を入力する。
3. CMS は、変更によって整理対象になるものと、復元できなくなる条件を示し、確認を求める。
   - 履歴: 保持方針を外れた版を自動整理で削除する。削除した版は比較も復元もできない。新たに整理対象になる版の件数を示す。
   - ごみ箱: 保持方針を外れたコンテンツを、履歴とともに自動整理で完全削除する。完全削除したコンテンツはごみ箱から復元できない。新たに整理対象になるコンテンツの件数を示す。
   - バックアップに残る情報は、この保持方針の対象でない。
4. メンバーが確定する。CMS は保持方針を保存し、以後の自動整理に適用する。既存の履歴とごみ箱のコンテンツにも適用する。履歴の版の自動整理と、ごみ箱のコンテンツの自動の完全削除は、別の定期処理として行う。
5. CMS は、変更を操作履歴に残す。

二つの自動整理は次を守る。

- 履歴の版の自動整理は履歴だけを対象とする。コンテンツの公開内容と下書きは削除しない。
- ごみ箱のコンテンツの自動の完全削除は、コンテンツを一件ずつ削除する。PUB-07 の手順 2 の削除条件を満たさないコンテンツは、保持方針を外れても削除しない。
- 無関係なコンテンツと履歴を連鎖して削除しない。

### 異常系

- 入力エラー: 指定できる範囲（APP-12）の外の保持方針を入力した場合、CMS は保存を拒否し、指定できる範囲を示す。メンバーは値を直す。
- 操作の取り消し: 保存した保持方針を戻すには、変更し直す。変更の後に自動整理で削除した版とコンテンツは戻らない。

## WS-11 操作履歴を確認する

- **利用者**: ワークスペース設定の権限を持つメンバー
- **目的**: ワークスペースの設定とスキーマを、誰がいつ変えたかを追う。
- **要件**: 8.2, 8.3, 9.2

### 正常系

1. メンバーが操作履歴を開く。CMS は、記録を日時の新しい順に示す。記録ごとに、日時、実行者、操作の種類、対象を示す。実行者は、メンバー、トークン、ホスティング運営者のいずれかである。トークンは、WS-07 の「一覧して見直す」の手順 1 が定める名称と発行者の示し方で、記録の時点の値を示す。
2. メンバーが、期間、操作の種類、実行者で絞り込む。
3. メンバーが記録を開き、変更の内容を確かめる。

操作履歴が記録する操作は次のとおりである。

- メンバーの招待、招待の取り消し、招待の受諾によるメンバーの参加、解除、権限の変更、所有者の変更
- 初期所有者の招待の発行と発行し直し（HOST-04）。実行者はホスティング運営者
- トークンの発行、失効。メンバーに紐付くトークンを含む。ブラウザ用トークンの利用元の限定と利用量の制限の変更
- 移行定義の適用を伴わないスキーマの反映（SMIG-07）、移行の適用、直接反映、移行定義の適用済みとしての記録
- 通知定義、通知先、送信接続設定の変更
- 表示アプリへの通知設定の変更
- プレビュー先の表示アプリの URL の変更
- コンテンツの保持方針と、回答の保持方針の変更
- 初期構成の読み込み（実行者はホスティング運営者）と、運用設定の紐付け

操作履歴は、認証情報、トークンの値、通知設定の秘密情報、フォーム回答の入力内容を含まない。秘密情報の変更は、変更した事実だけを記録する。操作履歴はコンテンツの版の履歴とは別であり、コンテンツの過去の内容は EDIT-13 で確認する。回答ごとの通知の送信結果は FORM-09 で確認する。

### 異常系

- 入力エラー: 期間の開始が終了より後の指定は、条件の誤り（`spec/scenario/index.md` の「一覧の絞り込み」）になる。
- 該当なし: `spec/scenario/index.md` の「一覧の絞り込み」に従う。
- リソース不在: 記録の対象が既にない場合（解除されたメンバー、失効したトークン、期限切れのトークン、削除されたフォーム）、CMS は記録を残したまま、対象が現在はないことを示す。
