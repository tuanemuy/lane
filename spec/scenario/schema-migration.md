# スキーマの変更と移行

開発者が、スキーマの変更から移行定義を生成し、影響を確認して、ワークスペースへ適用する。用語は `spec/requirements.md` の 1 章に従う。

## 共通の前提

- スキーマと移行定義は開発者のリポジトリにある。移行定義は一本の列で、順序を持つ。
- スキーマの変更は、区分によって反映の方法が異なる。

| 区分 | 変更の例 | 反映の方法 |
| --- | --- | --- |
| コンテンツの構造 | モデル・項目・選択肢・ブロックの種類の追加、削除、キーの変更、値の種類の変更、必須の変更、参照を許可するモデルの変更 | 移行定義を生成して反映する（SMIG-01、SMIG-06） |
| コンテンツの検証 | 文字数、範囲、書式、選択数、件数、一意性 | 移行定義を作らずに反映する（SMIG-07） |
| フォームの構造 | フォーム・項目・選択肢の追加、削除、キーの変更、検証 | 移行定義を作らずに反映する（SMIG-07） |
| 表示・運用の定義 | 表示名称・順序、説明・入力例、初期値、一覧表示用の項目、非推奨、プレビュー先の経路、画像の派生形式 | 移行定義を作らずに反映する（SMIG-07） |

- 反映は、ワークスペースのスキーマ全体を単位とする。未適用の移行定義をすべて適用し、指定した移行定義までの適用はしない。
- CMS に接続するコマンドは、開発環境に設定した接続先とトークンを使う。操作対象のワークスペースはトークンで決まり、コマンドは対象のワークスペースを結果に示す。同じスキーマと移行定義の列を、トークンを切り替えて複数のワークスペースへ反映できる。
- 適用の事前確認、反映、直接反映、適用済みとしての記録は、スキーマ反映の許可を持つトークンだけが要求できる。メンバーが管理画面で行えるのは、スキーマ、版の記録、反映結果の確認だけである（SDEV-07、SMIG-14）。
- SMIG-04 の適用状況の確認は、手元の列と適用済みの列の食い違いを調べるときに使う。
- 事前確認、反映、直接反映の結果と、反映ごとの結果の一覧は、対象を、種類ごとに次のとおり示す。件数は、該当する全件を数える。「先頭の対象」は、先頭から上限（APP-12）の件数までの対象を指す。

  | 種類 | 示すもの |
  | --- | --- |
  | 失敗の対象 | 件数と、先頭の対象。残りの対象は、示された対象を解消して実行し直すと現れる |
  | データを失い得る操作で失うもの | 操作ごとに、失う値の件数と、完全削除するコンテンツの件数と先頭の対象。操作は、その操作が指すモデル・項目・選択肢・ブロックの種類で示す |
  | 公開内容が変わるコンテンツ | 件数と、先頭の対象 |
  | 制約を満たさない公開内容、入力エラーを持つ下書き | 該当するコンテンツの件数と、先頭の対象。全件は、管理画面の絞り込みで一覧できる（EDIT-15） |

- 版を変える要求（反映、直接反映、適用済みとしての記録）のコマンドは、開発者に示した現行スキーマの版を、前提とする版として要求に添える。示した版は、その開発環境の、接続先とトークンの組ごとに、事前確認（SMIG-05）、適用状況の確認（SMIG-04）、確定した版を変える要求の結果（差分が無いことを返した結果を含む）のうち、最後のものが示した版である。その組でどれも行っていない場合は、コマンドが要求の前に読んで示した版を添える。CMS は、現行の版が前提と異なる要求を、版が変わったことを理由に拒否する。開発者が確かめた後に確定した別の反映の変更は、上書きされない。
- 失敗した反映は、CMS が受け付けて、失敗で終えた反映を指す。未解消の失敗した反映は、ワークスペースの最後に終えた反映が失敗した反映で、その後に、差分が無いことを理由に成功を返した反映の要求（「版を変える要求に共通する異常系」）を受けていないものを指す。次の反映の成功、または差分が無い反映の要求で解消する。状態確認（HOST-06）が示すのは、未解消の失敗した反映である。
- 移行を適用する時期、表示アプリの配信との順序、データを失い得る操作を含む移行の前のバックアップの確認は、開発者が行う。バックアップの取得はホスティング運営者が行う（HOST-07）。

### CMS に接続する操作に共通する異常系

SMIG-04、SMIG-05、SMIG-06、SMIG-07、SMIG-08 と、SMIG-14 のコマンドには、`index.md` の「共通の規則」を適用する。このファイルは次を加える。

- 権限不足（許可の発行条件）: 必要な許可はスキーマ反映。この許可をトークンに与える条件は、`index.md` の「トークンの許可」に従う。
- 権限不足（メンバーに紐付くトークン）: 開発者が認証を経て得たトークン（AUTH-06）の認可は、`index.md` の「トークンの許可」に従う。権限の不足で拒否された場合、開発者は、メンバー管理の権限を持つメンバーに権限を依頼する。
- リソース不在（意図と異なるワークスペース）: 結果に示されたワークスペースが意図と異なる場合、開発者はトークンを切り替えて実行し直す。

### 版を変える要求に共通する異常系

反映（SMIG-06、SMIG-07）、直接反映（SDEV-05）、適用済みとしての記録（SMIG-08）に適用する。各シナリオは、ここに加わる分だけを書く。

- 別の反映が適用中: `index.md` の「CMS に接続するコマンドと SDK の操作」の「スキーマの反映の適用中」に従い、何も変更しない。開発者は、適用の完了を SMIG-14 で確かめる。先に確定した反映で版が変わるので、続けて「別の反映が先に確定していた」に従う。
- 別の反映が先に確定していた: CMS は、前提とする版が現行の版と異なる要求を、版が変わったことを理由に拒否する。直接反映の確認（SDEV-05 の手順 5）の間に別の反映が確定した場合も、同じく拒否する。開発者は、SMIG-04 で現行スキーマと適用状況を確かめ、他の変更を手元に取り込む。反映は SMIG-05 から、直接反映は SDEV-05 の手順 2 から、適用済みとしての記録は、記録できる移行定義を SMIG-04 で確かめ直してから、やり直す。
- 差分が無い: 反映では、手元のスキーマが現行スキーマと差分を持たず、未適用の移行定義も無い場合を指す。直接反映では、手元のスキーマが現行スキーマと差分を持たない場合を指す。CMS は成功として現在の版を返す。版を進めず、版の記録と操作履歴に残さず、コンテンツを変える操作も止めない。表示アプリへの通知も行わない。最後に終えた反映が失敗した反映であるワークスペースでは、この要求で、未解消の失敗した反映が解消する（「共通の前提」）。

## SMIG-01 スキーマの差分から移行定義を生成する

- 利用者: 開発者
- 目的: コンテンツの構造の変更を、既存データの扱いとともに移行定義として記録する。
- 要件: 6, 6.1, 6.2, 6.3

### 正常系

1. 開発者は、スキーマのコンテンツの構造を変更する（SDEV-01）。
2. 開発者は、開発環境で移行定義の生成のコマンドを実行する。コマンドは CMS に接続しない。
3. コマンドは、既存の移行定義を順に適用した構造と、変更後のスキーマの差分を求める。
4. 差分だけでは決まらない判断があれば、コマンドは開発者に確認する。

| スキーマの変更 | 生成する移行 | コマンドが確認すること |
| --- | --- | --- |
| モデル・項目・選択肢・ブロックの種類の追加 | 追加 | 必須の項目では、未設定の既存の値に入れる補完値。指定は任意。項目の追加で、同じ階層に、同じ変更で削除する項目または非推奨の項目がある場合は、追加する項目に、その項目を複写元とする値の複写を加えるか。候補は、追加する項目へ変換規則のある値の種類の項目 |
| 同じ階層での削除と追加 | キーの変更、または削除と追加 | キーの変更として扱うか。キーの変更の候補を示す。削除と追加として扱う場合の値の複写は、追加の行に従う |
| 任意項目の必須化 | 必須の変更 | 補完値。指定は任意 |
| 参照を許可するモデルの変更 | 参照を許可するモデルの変更 | なし |
| 変換規則のある組み合わせでの値の種類の変更 | 値の種類の変更 | 変換できない値を失うこと。変換元と変換先の値の種類と、適用する変換規則を示す |
| 変換規則のない組み合わせでの値の種類の変更 | 同じキーの項目の削除と追加 | 値を失うこと |
| 選択肢・ブロックの種類の削除 | 削除 | 選択肢の置き換え先。別の選択肢または未設定 |
| 項目・モデルの削除 | 削除 | 値・項目・コンテンツを失うこと |
| 繰り返しの内外をまたぐ構造の組み替え、単一モデルと複数件モデルの間の変更 | 削除と追加 | 値・コンテンツを失うこと。値を保つ場合の段階的変更の手順（SMIG-11）を示す。コマンドは、同じキーの項目が階層をまたいで削除と追加に現れる変更を、階層をまたぐ組み替えとして判別する |

5. データを失い得る操作では、コマンドは対象を示して確認を求める。失う値・項目・コンテンツを移行では戻せず、戻す手段が設置全体のバックアップからの復旧に限られることも示す。対象は、項目・モデル・ブロックの種類の削除、置き換え先に未設定を指定する選択肢の削除、値の種類の変更、削除と追加として生成する変更。
6. 開発者は、各確認に答える。
7. コマンドは、移行定義を一つ生成し、列の末尾に加える。移行定義は、操作の並び、開発者の判断、データを失い得る操作への確認を記録する。操作はキーで対象を指定し、保存方式に依存する情報を含まない。
8. 開発者は、移行定義をスキーマとともにリポジトリに入れ、レビューを受ける。移行定義のレビューと適用が、データを失い得る操作の承認になる。
9. 開発者は、SMIG-03 で検証し、SMIG-05 で影響を確認して、SMIG-06 で反映する。手順 4 の確認で選ばなかった値の複写を加える場合は、SMIG-02 で加える。

開発者は、CMS に接続せずに、変換規則を一覧するコマンドで、変換規則と、変換できる値の種類の組み合わせを確かめられる。

対話できない環境では、開発者は判断を指定してコマンドを実行する。コマンドは確認を求めず、指定した判断で生成する。

スキーマからキーを削除しても、そのキーを扱う既存の移行定義を直す必要は無い。

### 異常系

- 入力エラー（スキーマに不整合がある）: コマンドは、SDEV-02 と同じ不整合を示し、移行定義を生成しない。開発者はスキーマを直して実行し直す。
- 入力エラー（既存の移行定義に不整合がある）: コマンドは、SMIG-03 と同じ不整合を示し、移行定義を生成しない。開発者は該当する移行定義を直して実行し直す。
- 入力エラー（対話できない環境で判断が足りない）: コマンドは、指定が必要な判断を示し、移行定義を生成しない。開発者は判断を指定して実行し直す。
- 入力エラー（指定した判断が問いに合わない）: 問いに無い対象への判断、候補に無いキーの指定、同じ問いへの重複した判断のいずれかがある場合、コマンドは、合わない判断と理由を示し、移行定義を生成しない。開発者は判断を直して実行し直す。
- 入力エラー（差分が無い）: コンテンツの構造に差分が無ければ、コマンドはその旨を示し、移行定義を生成しない。コンテンツの検証、フォーム、表示・運用の定義だけの変更は、SMIG-07 で反映する。
- 判断を誤った: 開発者は、未適用の移行定義を削除して生成し直すか、SMIG-02 で編集する。適用済みの移行定義は変更できない。適用後に戻す場合は SMIG-12 を行う。
- 操作の取り消し: 開発者が確認の途中でコマンドを止めると、移行定義は生成されない。データを失い得る操作への確認を拒んだ場合も生成されない。開発者はスキーマを見直す。

## SMIG-02 移行定義を編集し、値の複写を加える

- 利用者: 開発者
- 目的: 生成した移行定義に、差分からは決まらない既存データの扱いを加える。
- 要件: 6.1, 6.2

### 正常系

1. 開発者は、未適用の移行定義のコードを開く。
2. 開発者は、次の操作の範囲で編集する。
   - 項目に値の複写を加える。複写元には、同じ階層にある別の項目をキーで指定する
   - 補完値を加える、変える、外す
   - 選択肢の置き換え先を、別の選択肢または未設定に変える
   - キーの変更を削除と追加に変える、または削除と追加をキーの変更に変える
3. 開発者は、SMIG-03 で検証する。検証は、編集後の移行定義が含むデータを失い得る操作も示す。
4. 開発者は、編集した移行定義のレビューを受ける。編集で加えた操作と変えた操作は、レビューと適用が承認になる。
5. 開発者は、SMIG-05 で影響を確認して、SMIG-06 で反映する。

値の複写は、複写先が未設定の値にだけ写し、設定済みの値を変えない。公開内容、下書き、ごみ箱、履歴の版のそれぞれで、その内容の複写元の値を写す。同じ項目に値の複写と補完値を指定した場合、値の複写を先に行い、残る未設定の値に補完値を入れる。

### 異常系

- 入力エラー（存在しないキーの指定）: SMIG-03 の検証は、該当する操作と、その時点の構造に無いキーを示す。開発者はキーを直す。
- 入力エラー（変換規則のない組み合わせの値の複写）: 検証は、該当する操作と、複写元・複写先の値の種類を示す。開発者は、複写先の値の種類を変えるか、SMIG-11 の値の書き換えで値を移す。
- 入力エラー（別の階層の項目の指定）: 検証は、複写元が同じ階層に無いことを示す。開発者は、SMIG-11 の値の書き換えで値を移す。
- 入力エラー（扱えない操作や関数の記述）: 移行定義には、関数などデータとして表せない処理と、生成する移行と値の複写に含まれない操作を記述できない。検証は該当する操作を示す。計算を伴う値の変換は SMIG-11 で行う。
- 入力エラー（スキーマと食い違う編集）: 編集によって、移行定義を順に適用した構造がスキーマと食い違った場合、検証は食い違う定義を示す。開発者は移行定義かスキーマを直す。
- 適用済みの移行定義を編集した: 操作の並びを変える編集は、反映、適用状況の確認、適用の事前確認で食い違いとして示され、反映は拒否される（SMIG-09）。コメントや書式など操作の並びを変えない編集は、変更として扱われない。開発者は、適用済みの移行定義を元に戻し、変更を新しい移行定義として生成する。
- 操作の取り消し: 開発者は、反映する前ならコードを元に戻すだけで取り消せる。

## SMIG-03 CMS に接続せずに、スキーマと移行定義の食い違い・移行定義の不整合を検出する

- 利用者: 開発者
- 目的: 反映する前に、移行定義の誤りと、移行定義に記録していない構造の変更を開発環境で見つける。
- 要件: 3.1, 6.1

### 正常系

1. 開発者は、開発環境で検証のコマンドを実行する（SDEV-02 と同じコマンド）。コマンドは CMS に接続しない。
2. コマンドは、移行定義を先頭から順に適用した構造を求め、スキーマのコンテンツの構造と比べる。
3. コマンドは、各移行定義の操作を検証する。存在しないキーの指定、変換規則のない組み合わせの値の複写、扱えない操作を調べる。列に同じ名前の移行定義が二つ無いことも調べる。
4. コマンドは、移行定義に含まれるデータを失い得る操作を、移行定義ごとに示す。
5. 食い違いも不整合も無ければ、コマンドは成功で終わる。開発者は SMIG-05 に進む。

コマンドは、スキーマ自体の不整合、スキーマと移行定義の食い違い、移行定義の不整合を区別して示す。既存データが反映後の条件を満たすかどうかは、SMIG-05 の適用の事前確認で確かめる。

### 異常系

- 入力エラー（スキーマと移行定義の食い違い）: コマンドは、食い違う定義を示して失敗で終わる。開発者は、SMIG-01 で移行定義を生成するか、スキーマを移行定義に合わせて直す。
- 入力エラー（移行定義の不整合）: コマンドは、該当する移行定義、操作、理由を示して失敗で終わる。開発者は SMIG-02 の範囲で直す。
- 入力エラー（同じ名前の移行定義が二つある）: コマンドは、移行定義の不整合として、重なる名前と該当する移行定義を示して失敗で終わる。開発者は、後から加えた側を列から除き、SMIG-01 で生成し直す。
- 入力エラー（スキーマ自体の不整合）: SDEV-02 に従う。
- 検証を通さずに反映した場合: CMS は反映時に同じ検証を行い、食い違いや不整合のある反映を拒否する（SMIG-06）。

## SMIG-04 ワークスペースの移行定義の適用状況を確認する

- 利用者: 開発者
- 目的: 対象のワークスペースで、どの移行定義が適用済みで、手元の列と食い違いが無いかを、データを変えずに確かめる。
- 要件: 3.1, 6.1, 6.3, 9.3

### 正常系

1. 開発者は、対象のワークスペースの、スキーマ反映の許可を持つトークンを開発環境に設定する。
2. 開発者は、適用状況の確認のコマンドを実行する。コマンドは、手元の移行定義の列を CMS の記録と照らす。データは変更しない。
3. コマンドは、適用状況、版の記録の一覧、反映ごとの結果の一覧を、一度の実行で合わせて示す。示す内容は次のとおり。この出力は、SDEV-07 と SMIG-14 でも使う。
   - 現行スキーマの版と、スキーマ全体・モデルごと・フォームごとの識別子。コマンドは、手元のスキーマの識別子を CMS に接続せずに求め（SDEV-03）、単位ごとに現行スキーマの識別子との一致・不一致を示す
   - 適用済みの移行定義。適用済みとして記録したものは、その旨を示す
   - 未適用の移行定義。反映すると、この順にすべて適用される
   - 手元の移行定義と適用済みの列の食い違い
   - 現行スキーマのコンテンツの構造が、直接反映によって適用済みの移行定義と食い違っているか
   - スキーマの版の記録の一覧。版ごとに、日時と、反映に使ったトークンを示す。トークンは、WS-11 の手順 1 と同じく、記録の時点の値で示す。移行定義の適用による版では、適用した移行定義と、含まれるデータを失い得る操作を示す。直接反映による版では、直接反映によることと、失った値・項目・コンテンツの種類を示す。適用済みとして記録した移行定義では、記録によることと、記録に使ったトークンを示す
   - 適用中の反映。適用中であることと、その間 `index.md` の「スキーマの反映の適用中」のとおり操作を止めていることを示す
   - 反映ごとの結果の一覧。CMS が受け付けて終えた反映を、失敗した反映を含めて示す。適用中の反映は、この一覧に含めず、上の「適用中の反映」として示す。拒否した反映は一覧に現れず、拒否の理由と対象は、反映のコマンドの出力が示す。反映ごとに、反映に使ったトークン、日時、成功・失敗と理由を示す。成功では SMIG-06 の手順 8 と同じ内容を、失敗では理由と対象を示す。型を満たさない入力エラー、公開中でない必須の参照先、一意性の違反による失敗では、該当するコンテンツと項目を示す

   出力は、保存方式に依存する情報とトークンの値を含まない。
4. 食い違いが無ければ、開発者は SMIG-05 に戻る。

### 異常系

- 入力エラー（手元の移行定義の不整合）: 手元の列に、SMIG-03 が示す移行定義の不整合がある場合、コマンドは、SMIG-03 と同じ内容で、該当する移行定義、操作、理由を示す。CMS の記録（現行スキーマの版と識別子、適用済みの移行定義、版の記録、適用中の反映、反映ごとの結果）は示す。未適用の移行定義、列の食い違い、適用済みとして記録できる移行定義は示さない。開発者は、SMIG-03 で不整合を直して実行し直す。
- 入力エラー（手元のスキーマの不整合）: 手元のスキーマに SDEV-02 が示す不整合がある場合、コマンドは、手元のスキーマの識別子と一致・不一致を示さず、SDEV-02 と同じ不整合を示す。ほかの出力は示す。開発者は、定義を直して実行し直す。
- 適用済みの列と手元の列が食い違う: コマンドは、食い違う移行定義を示す。食い違いは、適用済みの移行定義の操作の並びが手元と異なる、適用済みの移行定義が手元に無い、適用済みの移行定義より前の位置に未適用の移行定義がある、のいずれかである。開発者は SMIG-09 を行う。
- 直接反映による食い違い: コマンドは、食い違う定義と、食い違いを解消するために適用済みとして記録できる移行定義を示す。開発者は、SMIG-08 で記録するか、直接反映（SDEV-05）で一致する構造に戻す。
- リソース不在（スキーマを一度も反映していない）: コマンドは、適用済みの移行定義が無いことと、手元の移行定義がすべて未適用であることを示す。開発者は SMIG-05 に進む。
- 権限不足・リソース不在: 共通の異常系に従う。

## SMIG-05 適用の事前確認で、現在のデータへの影響を確認する

- 利用者: 開発者
- 目的: 反映する前に、対象のワークスペースの現在のデータで反映がどうなるかを、データを変えずに確かめる。
- 要件: 2, 3.1, 6.1, 6.3, 6.5, 9.3

### 正常系

1. 開発者は、対象のワークスペースの、スキーマ反映の許可を持つトークンを開発環境に設定する。
2. 開発者は、適用の事前確認のコマンドを実行する。コマンドは、手元のスキーマと移行定義の列を CMS へ送る。
3. CMS は、現在のデータへ未適用の移行定義と手元のスキーマを反映した場合の結果を求める。データ、現行スキーマ、運用設定は変更しない。
4. コマンドは、次を示す。対象の示し方は「共通の前提」に従う。
   - 確認の時点の現行スキーマの版。反映のコマンドは、この版を前提とする版として引き継ぐ
   - 反映が成功する見込みか、失敗するか。失敗する場合は対象と理由
   - データを失い得る操作ごとの、失う値の件数と、完全削除するコンテンツの件数と先頭の対象（「共通の前提」）
   - 公開内容が変わるコンテンツ
   - 反映後の制約を満たさない公開内容
   - 変換後に入力エラーを持つ下書き
   - 不整合となる通知定義の参照
   - 削除して受付を終了するフォーム
   - キーの違いから削除と追加として扱うフォームと項目
5. データを失う結果がある場合、コマンドは、失うものを移行では戻せず、戻す手段が設置全体のバックアップからの復旧に限られることを示す。開発者は、ホスティング運営者にバックアップの取得を確かめる（HOST-07）。
6. 開発者は、結果をもとに、反映の時期と表示アプリの配信との順序を決める。制約を満たさない公開内容と入力エラーを持つ下書きは、編集権限を持つメンバーに修正を依頼する（EDIT-15）。
7. 開発者は、SMIG-06 で反映する。

結果は確認時点のデータに基づく。確認の後にコンテンツが変わると、反映の結果も変わる。事前確認は反映の成功を保証しない。

### 異常系

- 入力エラー（スキーマ・移行定義の不整合、食い違い）: CMS は SMIG-06 と同じ検証を行い、反映が拒否される理由を示す。開発者は、SDEV-02、SMIG-03、SMIG-08、SMIG-09 のうち該当する操作で解消する。
- 失敗する対象がある（型を満たさない入力エラー、必須にした参照の参照先が公開中でない公開内容、一意性の違反、変換できない値を持つ公開内容、削除するモデルのコンテンツを指す本文のリンクを持つ公開内容）: コマンドは該当するコンテンツと項目を示す。開発者は、SMIG-06 の異常系と同じ方法で、反映の前に解消する。
- 事前確認の途中で現行スキーマが変わった: 事前確認の途中で別の反映が確定した場合、CMS は事前確認を失敗として終え、スキーマの版が変わったことを示す。開発者は、SMIG-04 で適用状況を確かめ、他の変更を手元に取り込んで、事前確認をやり直す。
- 容量や処理能力の上限で確認できない: CMS は事前確認を失敗として終え、理由を示す。開発者は、ホスティング運営者に資源の確認を依頼し（HOST-06）、解消の後に事前確認をやり直す。
- 事前確認が中断した: 進行が止まった事前確認を、CMS は中断として失敗で終える。開発者は事前確認をやり直す。
- 失うデータが意図より多い: 開発者は反映しない。未適用の移行定義を SMIG-02 で直すか、値を保つ変更（SMIG-10、SMIG-11）に切り替える。
- 権限不足・リソース不在: 共通の異常系に従う。
- 操作の取り消し: 事前確認は何も変更しないため、取り消す対象が無い。

## SMIG-06 スキーマと未適用の移行定義を反映する

- 利用者: 開発者
- 目的: 未適用の移行定義を順に適用し、手元のスキーマをワークスペースの現行スキーマにする。
- 要件: 3.1, 4.2, 5.4, 6, 6.1, 6.2, 6.3, 6.4, 7.1, 9.1, 9.2, 9.3, 10.4

### 正常系

1. 開発者は、SMIG-03 で検証し、SMIG-05 で影響を確かめる。事前確認が適用済みの列との食い違いを示した場合は、SMIG-04 で調べる。
2. 開発者は、表示アプリの配信との順序を決める。CMS は、表示アプリがどの版のスキーマに対応しているかを判断せず、表示アプリの配信を待たない。
3. 開発者は、対象のワークスペースの、スキーマ反映の許可を持つトークンで、反映のコマンドを実行する。コマンドは、手元のスキーマと移行定義の列を CMS へ送る。反映はトークンだけが要求でき、管理画面からは行えない。管理画面での承認も要らない。データを失い得る操作を、コマンドで改めて認める必要も無い。
4. CMS は、スキーマと移行定義を検証し、適用済みの列との一致と、スキーマの構造が未適用の移行定義を適用した結果と一致することを確かめる。
5. CMS は、未適用の移行定義を順に適用し、移行定義を必要としない定義を置き換える。コマンドは進行状況を示す。適用中に止める操作と管理画面の示し方は、`index.md` の「スキーマの反映の適用中」と「管理画面の操作」に従う。
6. 確定するまで、CMS は既存の公開内容を既存の構造で配信する。公開取得とプレビュー取得は、移行途中の内容を返さない。
7. CMS は、反映後のスキーマで、公開内容に型を満たさない入力エラーと一意性の違反が無いことと、必須の参照の参照先が公開中であることを確かめ、全体を一つの単位として確定する。
8. コマンドは、反映の成功と、次の結果を示す。
   - 反映後のスキーマの版と識別子
   - 適用した移行定義
   - 公開内容が変わったコンテンツ
   - 反映後の制約を満たさない公開内容
   - 変換後に入力エラーを持つ下書き
   - 不整合となった通知定義の参照、削除して受付を終了したフォーム、削除と追加として扱ったフォームと項目
9. CMS は、公開内容の変更を、スキーマの版、変更した対象、変更の種類を識別できる一つの通知で表示アプリへ伝える（APP-11）。削除したモデルの公開中だったコンテンツは、公開取り消しとして伝える。
10. CMS は、スキーマの版の記録（SMIG-14）と操作履歴に、移行の適用を残す。
11. 開発者は、編集権限を持つメンバーに、制約を満たさない公開内容と入力エラーを持つ下書きの修正を依頼する。メンバーは、管理画面の絞り込みで一覧して直す（EDIT-15）。公開内容の修正を配信へ反映する公開は、公開権限を持つメンバーが行う（PUB-01）。

確定後の状態は次のとおり。

- 公開内容、下書き、ごみ箱、履歴は、すべて現行スキーマの形になる。履歴の版も現行スキーマで比較・復元する。移行前の保存内容は再現しない。
- モデルのキーの変更では、コンテンツID、公開内容、下書き、状態、履歴、運用設定を引き継ぐ。項目のキーの変更では、履歴を含めて値を引き継ぐ。変更前のキーを使う取得は、存在しない対象への要求として扱う。
- 値の種類の変更では、変換規則で値を変換する。下書き・ごみ箱・履歴の変換できない値は未設定になる。
- 補完値、置き換え先、値の複写は、公開内容、下書き、ごみ箱、履歴のすべてに適用される。必須化と参照を許可するモデルの縮小は、補完と値の複写を除いて既存の値を変えない。
- 削除した項目の値は、公開内容、下書き、ごみ箱、履歴から無くなる。削除したブロックの種類のブロックは、すべての内容から無くなる。削除したモデルのコンテンツは、公開中のものを含めて、ごみ箱と履歴とともに完全削除される。削除したモデルを指すコンテンツ参照の項目の値は、参照定義とともに、公開内容、下書き、ごみ箱、履歴から無くなる。取り除いたものは、取得・表示・検索・復元に現れず、移行では戻せない。
- 下書きは公開されない。公開内容と下書きの対応は入れ替わらない。
- 制約を満たさない公開内容は、そのまま配信が続く。編集して保存すると違反は下書きの入力エラーになり、解消するまで公開できない。
- 運用設定は変わらない。保存済みのフォームの回答は変わらない。

互換性のない変更を適用した後、変更前のスキーマを前提とする表示アプリの表示の継続は保証しない。開発者は、表示アプリの切り替えを、段階的変更（SMIG-10、SMIG-11）か配信の順序で調整する。

### 異常系

CMS が反映を拒否する場合と、適用を試みて失敗する場合がある。どちらの場合も、現行スキーマ、データ、運用設定は変わらず、表示アプリへの通知も行わない。コマンドは、拒否または失敗の理由と対象を示す。スキーマ・移行定義の誤りと、既存データが条件を満たさないことを区別して示す。

拒否する場合。

- 入力エラー（スキーマ・移行定義の不整合）: CMS は、SDEV-02、SMIG-03 と同じ不整合を示す。開発者は定義を直して実行し直す。
- 入力エラー（スキーマの構造が移行定義と一致しない）: CMS は、食い違う定義を示す。開発者は、SMIG-01 で移行定義を生成してから実行し直す。
- 入力エラー（適用済みの列と食い違う）: 適用済みの移行定義の変更・削除と、適用済みの移行定義より前の位置への追加は拒否する。CMS は食い違う移行定義を示す。開発者は SMIG-09 を行う。
- 入力エラー（直接反映による食い違い）: 未適用の移行定義がある反映で、現行スキーマの構造が適用済みの移行定義を適用した結果と一致しない場合、CMS は食い違う定義を示す。開発者は、SMIG-08 で適用済みとして記録するか、直接反映（SDEV-05）で一致する構造に戻してから実行し直す。
- 別の反映が適用中、別の反映が先に確定していた: 「版を変える要求に共通する異常系」に従う。
- 権限不足・リソース不在: 共通の異常系に従う。

失敗する場合。

- 公開内容に型を満たさない入力エラー（`content-editing.md` の「共通の規則」）がある: CMS は該当するコンテンツと項目を示す。開発者は、次のいずれかを行って実行し直す。未適用の移行定義に補完値・置き換え先・値の複写を加える（SMIG-02）。公開内容の値を書き換える（APP-10）。編集権限を持つメンバーに修正を、公開権限を持つメンバーに公開（PUB-01）または公開取り消し（PUB-03）を依頼する。
- 必須にした参照の参照先が公開中でない公開内容がある: 参照を必須にする変更で、その参照の参照先が未公開またはごみ箱にある公開内容がある場合、反映は失敗する。CMS は該当するコンテンツ、項目、参照先を示す。開発者は、公開権限を持つメンバーに参照先の公開または参照元の公開取り消しを依頼するか、参照元の公開内容の値を公開中の参照先に書き換えて（APP-10）、実行し直す。
- 公開内容に一意性の違反がある: CMS は該当するコンテンツと項目を示す。開発者は、重複する公開内容の値を書き換える（APP-10）か、編集権限を持つメンバーに修正を、公開権限を持つメンバーに公開または公開取り消しを依頼して、実行し直す。
- 値の種類の変更で、変換できない値を持つ公開内容がある: CMS は該当するコンテンツと項目を示す。開発者は、公開内容の値を変換できる値に書き換える（APP-10）か、段階的変更（SMIG-11）に切り替える。
- 削除するモデルのコンテンツを指す本文のリンクが、ほかのコンテンツの公開内容にある: CMS は参照元のコンテンツと項目を示す。開発者は、編集権限を持つメンバーにリンクの除去を、公開権限を持つメンバーにその公開または参照元の公開取り消しを依頼して、実行し直す。
- 削除するモデルを指すコンテンツ参照の値を取り除いた結果、必須の参照が欠ける公開内容がある: コンテンツ参照の項目の値は、参照定義とともに取り除かれ、それだけでは反映は失敗しない。取り除いた後に必須の参照が欠ける公開内容は、型を満たさない入力エラーとして反映を失敗させる。CMS は該当するコンテンツと項目を示す。開発者は、その項目を任意にするか削除する変更を同じ反映に含める（SMIG-01）か、公開権限を持つメンバーに参照元の公開取り消しを依頼して、実行し直す。
- 容量や処理能力の上限で適用できない: CMS は失敗として示す。開発者は、ホスティング運営者に資源の確認を依頼する（HOST-06）。
- 確定の時点で切り替えを拒否された: 変換を終えた後、確定の時点で、反映後の内容が手順 7 の条件を満たさない場合と、使用するメディアが変換の後に削除されていた場合、CMS は切り替えを拒否し、反映を失敗で終える。CMS は、切り替えを拒否されたことと、その理由を示す。開発者は、SMIG-05 の事前確認からやり直す。拒否が繰り返す場合は、ホスティング運営者に状態の確認を依頼する（HOST-06）。

そのほか。

- 差分が無い: 「版を変える要求に共通する異常系」に従う。
- 操作の取り消し（開始前）: 開発者は、コマンドを実行しなければ何も変わらない。
- 操作の取り消し（開始後）: CMS が受け付けた反映は取り消せない。コマンドを中断しても、接続が切れても、CMS は反映を進め、確定か失敗のどちらかで終える。開発者は SMIG-14 で結果を確かめる。
- 操作の取り消し（確定後）: 適用した移行は、新しい移行定義で戻す（SMIG-12）。
- コマンドが結果を受け取る前に接続が切れた: 反映は CMS の側で進み続ける。開発者は、SMIG-14 で進行状況と結果を確かめる。結果を確かめずに反映をやり直さない。

## SMIG-07 コンテンツの検証、フォーム、表示・運用の定義だけの変更を反映する

- 利用者: 開発者
- 目的: 移行定義を作らずに、制約、一意性、フォーム、表示・運用の定義の変更を現行スキーマに反映する。
- 要件: 3.1, 4.2, 4.4, 6.1, 6.2, 6.3, 6.4, 6.5, 8.3

### 正常系

1. 開発者は、スキーマの、コンテンツの検証、フォームの構造、表示・運用の定義を変更する。
2. 開発者は、SMIG-03 で検証する。コンテンツの構造に差分が無いため、移行定義の生成は要らない。
3. フォームの構造を変える場合と、反映の前に影響を知る必要がある場合、開発者は、適用の事前確認（SMIG-05）を実行する。結果は、反映後の制約を満たさない公開内容、一意性の違反、不整合となる通知定義の参照、削除して受付を終了するフォーム、削除と追加として扱うフォームと項目を示す。
4. 通知定義の参照が不整合になる場合と、フォームを削除する場合、開発者は、通知設定の権限を持つメンバーに反映の予定を伝える。
5. 開発者は、反映のコマンドを実行する（SMIG-06 と同じコマンド）。未適用の移行定義があれば、同じ反映で適用される。
6. CMS は、現行スキーマの定義を置き換え、全体を一つの単位として確定する。フォームは、確定するまで現行の定義で受付を続ける。確定と重なった送信には、切り替え前または切り替え後のいずれか一組のフォーム定義と通知定義が適用される。
7. コマンドは、反映の成功と、手順 3 の事前確認の結果と同じ種類の結果を示す。

変更ごとの反映後の状態は次のとおり。

- 制約（文字数、範囲、書式、選択数、件数）の変更: 既存の公開内容を確認せず、反映は失敗しない。制約を満たさない公開内容は配信が続き、反映結果と管理画面の絞り込みで確認できる（EDIT-15）。以後の公開と値の書き換えに、新しい制約が適用される。識別子は変わらない。
- 一意性の変更: 反映後の公開内容に一意性の違反が一件でもあれば、反映は失敗する。
- フォームの項目・検証の変更: 反映後の送信は、新しい定義で検証される。変更前の表示から送られた送信が新しい定義を満たさない場合、項目ごとの理由を付けた入力不備として拒否される。表示アプリは入力を保持して修正と再送を促す（APP-08）。保存済み回答と未送信の通知は、受付時の定義のまま扱われる。
- フォームの追加: 新しいフォームの受付状態は、`form-operation.md` の「共通の規則」に従う。初期構成で回答の保持方針を宣言した場合を除き、回答の標準の保持方針を持つ。受付管理の権限を持つメンバーが FORM-06 で変える。通知設定の権限を持つメンバーが通知先と通知定義を整え（FORM-02、FORM-03）、受付管理の権限を持つメンバーが受付を有効にする（FORM-05）。
- フォームの削除: 受付状態によらず削除できる。新規受付が終わり、以後の送信はフォームが存在しないとして拒否される。保存済み回答は、削除済みフォームの回答として保持方針に従って残る（FORM-11）。未送信の通知は取り消されない。
- フォームとその項目のキーの変更: 削除と追加として扱われる。保存済み回答は新しいキーへ読み替えられない。フォームのキーを変えると、運用設定は新しいフォームへ引き継がれない。新しいフォームの受付状態は、`form-operation.md` の「共通の規則」に従う。受付を止めずにフォームのキーを変える場合は SMIG-13 を行う。
- 通知定義が参照する項目の削除、キーの変更、用途に合わない型への変更: 反映は拒否されない。その参照は不整合になり、受付と通知は続く。通知では不整合と分かる表示になり、返信先の参照が不整合の場合は返信先を指定せずに送られる。通知設定の権限を持つメンバーが FORM-04 で直す。CMS は運用設定を自動で補正・削除しない。
- 表示名称・順序、説明・入力例、初期値、一覧表示用の項目、プレビュー先の経路の変更: 保存済みの値と識別子は変わらない。編集画面と管理画面の表示が変わる。
- 非推奨の指定: 保存済みの値、取得結果、入力検証は変わらない。編集画面では読み取り専用になる（EDIT-16）。
- 画像の派生形式の変更: 登録済みの画像にも適用される。変更前の派生形式は、新しい派生形式を配信できるまで配信が続く（MEDIA-10）。派生形式のキーを変えると識別子が変わる。

### 異常系

- 入力エラー（スキーマに不整合がある）: CMS は反映を拒否し、該当する定義と理由を示す。現行スキーマ、データ、運用設定は変わらない。フォームは現行の定義で受付を続ける。開発者は定義を直す。
- 入力エラー（必須の項目への非推奨の指定）: 検証は、任意化と非推奨の指定を同じ反映で行う手順を示す。任意化はコンテンツの構造の変更のため、開発者は SMIG-01 で移行定義を生成する。
- 入力エラー（コンテンツの構造も変えていた）: CMS は、スキーマの構造が移行定義と一致しないとして反映を拒否する。開発者は SMIG-01 で移行定義を生成する。
- 一意性の違反で失敗した: CMS は該当するコンテンツと項目を示す。開発者は、重複する公開内容の値を書き換える（APP-10）か、編集権限を持つメンバーに修正を、公開権限を持つメンバーに公開または公開取り消しを依頼して、実行し直す。
- フォームのキーを誤って変えた: 事前確認と反映結果が、削除と追加として扱うフォームを示す。反映済みの場合、古いフォームの受付は終わり、新しいフォームが作成されている。新しいフォームの受付状態は `form-operation.md` の「共通の規則」に従う。キーを元に戻して反映しても、古いフォームの運用設定と回答は、作り直されたフォームに戻らない。通知設定の権限を持つメンバーが、いまあるフォームの通知先と通知定義を整え（FORM-02、FORM-03）、受付管理の権限を持つメンバーが受付を有効にする（FORM-05）。
- 権限不足・リソース不在: 共通の異常系に従う。
- 操作の取り消し: 確定した反映は、定義を元に戻して反映し直すことで戻す。制約と表示・運用の定義は元に戻る。削除したフォームは、同じキーで追加しても別のフォームとして作成される。

## SMIG-08 直接反映で進めた構造を、移行定義を適用済みとして記録して移行定義による管理へ移す

- 利用者: 開発者
- 目的: 直接反映で進めたワークスペースを、データを変えずに、移行定義で変更できる状態にする。
- 要件: 6.1, 9.2, 9.3

### 正常系

1. 開発者は、手元のスキーマを、対象のワークスペースの現行スキーマと同じ構造にする。
2. 開発者は、SMIG-01 で移行定義を生成する。移行定義の列を順に適用した構造が、現行スキーマのコンテンツの構造と一致する状態にする。
3. 開発者は、SMIG-04 で適用状況を確認する。コマンドは、手元のスキーマと現行スキーマの識別子の一致、現行スキーマの構造が適用済みの移行定義と食い違っていること、適用済みとして記録できる移行定義を示す。
4. 開発者は、適用済みとして記録するコマンドを実行する。記録する範囲の指定は、どの移行定義までを記録するかだけである。範囲は、常に未適用の移行定義の先頭から始まる。未適用の移行定義の一部でも全部でも指定できる。
5. CMS は、適用済みの移行定義と記録する移行定義を順に適用した結果が、現行スキーマのコンテンツの構造と一致することを確かめる。
6. CMS は、指定した移行定義を適用済みとして記録する。データと現行スキーマは変更しない。記録した移行定義の補完値・置き換え先・変換・値の複写は、既存データに適用しない。
7. コマンドは、記録した移行定義を示す。CMS は、記録によることと、記録に使ったトークンを、スキーマの版の記録と操作履歴に残す。
8. 以後、開発者は、スキーマの変更を SMIG-01 から SMIG-06 の流れで反映する。記録した移行定義より後の未適用の移行定義は、次の反映で適用される。

### 異常系

- 入力エラー（構造が一致しない）: CMS は記録を拒否し、食い違う定義を示す。何も記録しない。開発者は、次のいずれかを行って実行し直す。記録する範囲を変える。手元のスキーマと移行定義を現行の構造に合わせて生成し直す。直接反映（SDEV-05）でワークスペースの構造を移行定義に合わせる。
- 入力エラー（移行定義の不整合、適用済みの列との食い違い）: CMS は SMIG-06 と同じ検証を行い、理由を示して拒否する。開発者は SMIG-03、SMIG-09 で解消する。
- 別の反映が適用中、別の反映が先に確定していた: 「版を変える要求に共通する異常系」に従う。
- 記録した移行定義の補完値や値の複写を既存データに適用したい: 記録では適用されない。開発者は、値の書き換え（APP-10）で値を入れる。
- 権限不足・リソース不在: 共通の異常系に従う。
- 操作の取り消し: 記録は取り消せない。記録した移行定義は、適用済みの移行定義として扱われ、変更・削除できない。開発者は、記録の前に SMIG-04 で記録できる移行定義を確かめる。

## SMIG-09 適用済みの列と食い違う移行定義を生成し直して適用する

- 利用者: 開発者
- 目的: 別々に作成した移行定義の列の分岐を、現在の列に続く移行定義に作り直して適用する。
- 要件: 3.1, 6.1

### 正常系

1. 開発者は、SMIG-04 の適用状況の確認、SMIG-05 の事前確認、SMIG-06 の反映のいずれかで、手元の移行定義が適用済みの列と食い違うことを知る。コマンドは食い違う移行定義を示す。
2. 開発者は、適用済みの移行定義と、それに対応するスキーマの変更を、リポジトリから手元に取り込む。
3. 開発者は、手元の未適用の自分の移行定義を列から除く。
4. 開発者は、自分のスキーマの変更を、取り込んだスキーマに加える。
5. 開発者は、SMIG-01 で移行定義を生成する。コマンドは、現在の列を順に適用した構造と、スキーマの差分から、新しい移行定義を列の末尾に生成する。差分だけでは決まらない判断と、データを失い得る操作は、改めて確認される。除いた移行定義に値の複写を加えていた場合、開発者は SMIG-02 で加え直す。
6. 開発者は、SMIG-03 で検証し、SMIG-05 で影響を確認して、SMIG-06 で反映する。食い違いが残っていれば、事前確認がそれを示す。

### 異常系

- 生成し直さずに反映した: CMS は反映を拒否し、食い違う移行定義を示す。分岐した列を合わせて適用することはしない。現行スキーマ、データ、運用設定は変わらない。開発者は手順 2 から行う。
- リソース不在（適用済みの移行定義がリポジトリに無い）: 適用状況の確認は、手元に無い適用済みの移行定義を示す。開発者は、その移行定義を反映した開発者から移行定義とスキーマの変更を受け取り、リポジトリに入れてから手順 2 を行う。反映に使ったトークンは SMIG-14 で確認できる。
- 適用済みの移行定義を自分が編集していた: 開発者は、編集を元に戻す。操作の並びを変えない記述の変更は、食い違いとして扱われない。変更したい内容は、新しい移行定義として生成する。
- 直接反映による食い違いだった: 適用状況の確認は、直接反映による食い違いを、列の食い違いと区別して示す。開発者は SMIG-08 を行う。
- 操作の取り消し: 開発者は、反映する前なら、自分の変更を取りやめて、取り込んだスキーマと移行定義だけにできる。

## SMIG-10 値の複写で項目を置き換える

- 利用者: 開発者
- 目的: 項目の値を、履歴を含めて別の項目へ引き継ぎ、古い項目を削除する。
- 要件: 6.2, 6.3, 6.4, 7.1

### 正常系（追加と削除を同じ反映で行う）

1. 開発者は、スキーマに新しい項目を追加し、古い項目を削除する。
2. 開発者は、SMIG-01 で移行定義を生成する。コマンドがキーの変更として扱うかを確認した場合、値の種類が同じで値をそのまま引き継ぐなら、開発者はキーの変更を選んで終える。値の種類が異なるなど、別の項目として置き換える場合は、削除と追加を選び、新しい項目に古い項目を複写元とする値の複写を加えることを選んで、古い項目を削除することを確認する。必要なら補完値も指定する。
3. 開発者は、SMIG-03 で検証し、SMIG-05 で影響を確認して、SMIG-06 で反映する。
4. CMS は、公開内容、下書き、ごみ箱、履歴の版のそれぞれで、古い項目の値を新しい項目へ写してから、古い項目の値を取り除く。値の種類が異なる場合は、変換規則で変換する。

### 正常系（追加と削除を別々の反映で行う）

1. 開発者は、スキーマに新しい項目を追加し、古い項目に非推奨を指定する。古い項目が必須の場合は、任意化と非推奨の指定を同じ変更で行う。
2. 開発者は、SMIG-01 で移行定義を生成する。コマンドが値の複写を加えるかを確認したら、新しい項目に古い項目を複写元とする値の複写を加えることを選ぶ。開発者は、SMIG-06 で反映する。CMS は、履歴を含めて値を新しい項目へ写す。古い項目は、編集画面で読み取り専用になる（EDIT-16）。取得結果には新旧の項目がともに現れる。
3. 開発者は、表示アプリを、新しい項目を使うものに切り替える。
4. 開発者は、スキーマから古い項目を削除し、SMIG-01 で移行定義を生成する。値を失うことを確認する。
5. 開発者は、SMIG-05 で影響を確認して、SMIG-06 で反映する。

どちらの手順でも、履歴の版を含めて値を引き継ぐ。

### 異常系

- 入力エラー（変換規則のない組み合わせ）: SMIG-03 の検証と反映時の検証は、値の複写を拒否し、複写元・複写先の値の種類を示す。開発者は SMIG-11 の値の書き換えに切り替える。
- 入力エラー（複写元が同じ階層に無い）: 検証は該当する操作を示す。開発者は SMIG-11 に切り替える。
- 入力エラー（複写元を先に削除する並びにした）: 検証は、複写元のキーがその時点の構造に無いことを示す。開発者は、値の複写を古い項目の削除より前に置く。
- 変換できない値がある: 変換できない値は写されず、新しい項目は未設定のままになる。新しい項目が必須で、公開内容に未設定が残る場合、反映は失敗し、CMS は該当するコンテンツと項目を示す。開発者は、補完値を指定する（SMIG-02）か、公開内容の値を書き換えて（APP-10）から実行し直す。下書き・ごみ箱では入力エラーになり、履歴の版では復元時に示される。事前確認（SMIG-05）で反映の前に分かる。
- 複写先に設定済みの値がある: 値の複写は設定済みの値を変えない。上書きする場合、開発者は値の書き換え（APP-10）で行う。
- 写した値が新しい項目の制約を満たさない: 反映は失敗しない。該当する公開内容は配信が続き、反映結果と管理画面の絞り込みで確認できる（EDIT-15）。
- 別々の反映の間に古い項目の値が変わった: 値の複写は、追加を反映した時点の値を写す。その後に値の書き換えで古い項目を変えても、新しい項目へは写されない。開発者は、古い項目の削除の前に、値の書き換えで新しい項目へ移す。
- 権限不足・リソース不在: SMIG-06 に従う。
- 操作の取り消し: 古い項目の削除を反映する前なら、開発者は、新しい項目を削除する移行定義を生成して反映し、古い項目へ戻せる。古い項目の削除を反映した後は、古い項目の値は移行では戻らない（SMIG-12）。

## SMIG-11 値の書き換えと非推奨を使い、計算を伴う値の変換を段階的に行う

- 利用者: 開発者
- 目的: 移行定義では表せない値の変換を、新旧の項目を共存させながら、値を失わずに行う。
- 要件: 4.2, 5.4, 6.2, 6.4, 9.1, 9.3

### 正常系

1. 追加を反映する。開発者は、スキーマに新しい項目を追加し、古い項目に非推奨を指定する。古い項目が必須の場合は、任意化と非推奨の指定を同じ変更で行う。開発者は、SMIG-01 で移行定義を生成し、SMIG-06 で反映する。コマンドが値の複写を加えるかを確認したら、加えないことを選ぶ。新しい項目は、値を移し終えるまで任意にする。
2. CMS は、古い項目を編集画面で読み取り専用にする。編集権限を持つメンバーは、古い項目の値を編集画面で変えられない。取得結果と入力検証は変わらず、表示アプリは古い項目を使い続けられる。
3. 値を書き換える。開発者は、開発環境で、コンテンツ管理の許可を持つトークンを使うスクリプトを実行する（APP-10）。スクリプトは、コンテンツ管理の許可で呼べるモデルのコンテンツの一覧とごみ箱の一覧から対象を列挙する。一覧は、未公開のコンテンツと、入力エラーのある下書きを持つコンテンツを含む。スクリプトは、対象のコンテンツの最新の内容と公開内容を取得し、古い項目の値から新しい項目の値を計算する。
4. スクリプトは、複数のコンテンツの値の書き換えを一つの操作として要求する。公開内容と下書きは、それぞれを選んで書き換える。ごみ箱のコンテンツは、ごみ箱に置いたまま下書きを書き換える。
5. CMS は、APP-10 のとおり確定する。
6. 開発者は、表示アプリを、新しい項目を使うものに切り替える。
7. 削除を反映する。開発者は、スキーマから古い項目を削除する。新しい項目を必須にする場合は、同じ変更で必須にする。開発者は、SMIG-01 で移行定義を生成し、値を失うことを確認する。SMIG-05 で影響を確認して、SMIG-06 で反映する。

履歴の版の値は、値の書き換えでは移らない。古い項目の値は、削除の反映で履歴から取り除かれる。履歴の版にも値を引き継ぐ必要があり、計算を伴わない場合は、SMIG-10 を使う。

同じ移行定義の列を別のワークスペースへ適用する場合、値の書き換えは、ワークスペースごとに、古い項目を削除する反映の前に行う。追加と削除の移行定義がどちらも未適用のワークスペースでは、開発者は次の順で行う。

1. リポジトリから、追加を記録した時点のスキーマと移行定義を取り出して反映する。
2. そのワークスペースのトークンで、値を書き換える。
3. 最新のスキーマと移行定義を反映する。

### 異常系

- 値の書き換えの拒否（入力エラー、競合、権限不足、書き換え先の不在、件数の上限）: 拒否の条件、CMS が示す内容、開発者の次の操作は、APP-10 の異常系に従う。必要な許可はコンテンツ管理で、スキーマ反映の許可では値を書き換えられない。対象を分けた場合、分けた操作ごとに、確定と表示アプリへの通知が行われる。
- リソース不在（追加を反映する前に値を書き換えた）: CMS は、存在しない項目のキーを示すエラーを返す。開発者は手順 1 を先に行う。
- 書き換えの途中でスクリプトが止まった: 確定した操作の変更は残る。開発者は、スクリプトをやり直す。新しい項目が設定済みのコンテンツを飛ばすかどうかは、スクリプトが決める。
- 追加と削除がどちらも未適用のワークスペースへ、最新の列をそのまま反映した: 値を書き換える前に古い項目が削除され、値を失う。事前確認（SMIG-05）は、失う値の対象と件数を示す。開発者は、事前確認の結果を確かめ、上記の順で行う。
- 値を移す前に古い項目の削除を反映しようとしている: 事前確認は、失う値の対象と件数を示す。新しい項目を同じ変更で必須にした場合、未設定の公開内容があれば反映は失敗する。開発者は、手順 3 から 5 を終えてから反映する。
- 操作の取り消し: 削除を反映する前なら、古い項目の値は残っている。開発者は、表示アプリを古い項目に戻し、新しい項目を削除する移行定義を生成して反映できる。書き換えた値は、元の値を指定した値の書き換えで戻す（APP-10）。書き換え前の内容は、コンテンツごとの履歴にある（EDIT-13、EDIT-14）。削除を反映した後は SMIG-12 に従う。

## SMIG-12 適用した変更を、新しい移行定義で戻す

- 利用者: 開発者
- 目的: 適用済みの移行定義を残したまま、スキーマを以前の構造へ戻す。
- 要件: 6, 6.1, 6.2, 6.3, 6.4

### 正常系

1. 開発者は、スキーマを、戻したい構造に変更する。適用済みの移行定義は変更も削除もしない。
2. 開発者は、SMIG-01 で移行定義を生成する。コマンドは、戻す変更を新しい移行定義として列の末尾に生成する。
3. 開発者は、SMIG-05 で影響を確認して、SMIG-06 で反映する。

戻す変更ごとの結果は次のとおり。

| 適用した変更 | 戻す移行定義 | 既存データ |
| --- | --- | --- |
| キーの変更 | 元のキーへのキーの変更 | 値を引き継ぐ |
| 項目・モデル・選択肢・ブロックの種類の追加 | 削除 | 追加した後に入力した値・コンテンツを失う |
| 項目・モデル・ブロックの種類の削除 | 追加 | 対象は空で作られる。削除前の値・コンテンツは戻らない |
| 値の種類の変更 | 元の種類への値の種類の変更 | 変換規則で変換する。前の変更で失った値は戻らない |
| 必須化 | 任意への変更 | 値を変えない。補完した値は残る |
| 参照を許可するモデルの変更 | 参照を許可するモデルの変更 | 値を変えない |

削除したキーを再び追加しても、削除前の値と運用設定は新しい対象へ引き継がれない。

### 異常系

- 適用済みの移行定義を削除・変更して戻そうとした: CMS は反映を拒否し、食い違う移行定義を示す。開発者は、移行定義を元に戻し、手順 1 から行う。
- 失ったデータが必要: 移行では戻せない。戻す手段は、設置全体のバックアップからの復旧に限られる。開発者は、ホスティング運営者に復旧を依頼する（HOST-08）。復旧は設置全体を単位とし、すべてのワークスペースが復旧点へ戻る。復旧点以降の編集、回答、設定の変更は失われる。
- 戻す移行定義がデータを失う: 追加を戻す削除は、データを失い得る操作である。生成時に確認が求められ、事前確認が失う対象と件数を示す。開発者は、値を残す場合、削除せずに非推奨を指定する（SMIG-07）。
- 戻した後の表示アプリ: 変更後のスキーマを前提とする表示アプリの表示の継続は保証しない。開発者は、表示アプリの配信を戻す順序を決める。
- 入力エラー・権限不足・リソース不在: SMIG-01、SMIG-06 に従う。
- 操作の取り消し: 戻す移行定義も、適用した後は戻せない。再び変更する場合は、新しい移行定義を生成する。

## SMIG-13 フォームのキーを、受付を止めずに変える

- 利用者: 開発者、通知設定・受付管理の権限を持つメンバー
- 目的: 受付を続けたまま、フォームを新しいキーのフォームへ切り替える。
- 要件: 3.1, 6.5, 8.1

### 正常系

1. 開発者は、スキーマに、新しいキーのフォームを追加する。古いキーのフォームは残す。
2. 開発者は、SMIG-07 で反映する。CMS は新しいフォームを作成する。受付状態は `form-operation.md` の「共通の規則」に従う。古いフォームは受付を続ける。
3. 通知設定の権限を持つメンバーは、新しいフォームの通知先（FORM-02）と通知定義（FORM-03）を設定する。古いフォームの運用設定は引き継がれないため、改めて設定する。
4. 受付管理の権限を持つメンバーは、新しいフォームの受付を有効にする（FORM-05）。確認が示す回答の保持方針を変える場合だけ、有効にする前に FORM-06 で変える。この時点で、新旧のフォームがともに受付中になる。
5. 開発者は、表示アプリを、新しいキーのフォームへ送信するものに切り替えて配信する。
6. 開発者は、配信した表示アプリが新しいキーのフォームへ送信し、受付完了を受け取ることを確かめる。
7. 開発者は、スキーマから古いキーのフォームを削除する。
8. 開発者は、適用の事前確認（SMIG-05）で、削除して受付を終了するフォームが古いフォームだけであることを確かめ、SMIG-07 で反映する。
9. CMS は、古いフォームの新規受付を終了する。保存済み回答は、受付時のフォームと通知定義の情報とともに、削除済みフォームの回答として保持方針に従って残る。未送信の通知は取り消されない。閲覧は回答の閲覧権限または回答の削除権限、削除は回答の削除権限、通知の再試行は通知設定の権限を持つメンバーが、FORM-11 で行う。

### 異常系

- 一度の反映でキーを変えた: CMS は、削除と追加として扱う。古いフォームの受付は終わり、新しいフォームの受付状態は `form-operation.md` の「共通の規則」に従う。新しいフォームが受付停止の場合、運用設定を整えて受付を有効にするまで、送信は受付停止として失敗する。事前確認は、削除と追加として扱うフォームを示す。開発者は、事前確認の結果を確かめ、手順 1 から行う。
- 新しいフォームの受付を有効にできない: 扱いは FORM-05 の異常系に従う。
- 新しいフォームの受付を有効にする前に表示アプリを切り替えた: 新しいフォームへの送信は、受付停止として失敗する。表示アプリは入力を保持する。開発者は、表示アプリを古いフォームへ戻すか、メンバーに受付の有効化を依頼する。
- 表示アプリを切り替える前に古いフォームを削除した: 古いキーへの送信は、フォームが存在しないとして拒否される。削除したフォームは、同じキーで追加しても別のフォームとして作成される。開発者は、表示アプリを新しいフォームへ切り替える。
- 権限不足（メンバー）: 通知設定の権限または受付管理の権限を持たないメンバーは、該当する設定を変えられない。メンバーは、メンバー管理の権限を持つメンバーに権限の付与を依頼する（WS-02）。スキーマ変更権限だけでは、通知先と受付状態を変えられない。
- 権限不足（開発者）・リソース不在: 共通の異常系に従う。
- 操作の取り消し: 古いフォームを削除する反映の前なら、開発者は、表示アプリを古いフォームへ戻し、新しいフォームをスキーマから削除して反映できる。新しいフォームが受け付けた回答は、削除済みフォームの回答として残る。古いフォームを削除した後は、古いフォームの受付と運用設定は戻らない。

フォームの項目のキーの変更も、削除と追加として扱う。保存済み回答は、受付時の項目のキーと表示名称で閲覧できる。変更前のキーへの通知定義の参照は不整合になるため、通知設定の権限を持つメンバーが FORM-04 で直す。

## SMIG-14 スキーマの版の記録と、反映の進行状況・結果を確認する

- 利用者: 開発者、スキーマ変更権限を持つメンバー
- 目的: いつ、どの移行定義が、誰のトークンで適用されたかと、適用中の反映の進行状況、終えた反映の結果を確かめる。
- 要件: 3.1, 6.1, 6.3, 6.5, 9.2, 10.2, 10.3

### 正常系（版の記録を確認する）

1. 開発者は、スキーマ反映の許可を持つトークンで、適用状況の確認のコマンドを実行し、出力のうちスキーマの版の記録を読む。出力は SMIG-04 が定める。
2. スキーマ変更権限を持つメンバーは、管理画面でスキーマの版の記録を開く。管理画面は、コマンドの出力のスキーマの版の記録と同じ内容を示す。

### 正常系（反映の進行状況と結果を確認する）

1. 反映を実行した開発者は、反映のコマンドの出力で進行状況を確認する。反映は、コマンドの接続が切れても CMS の側で進む。コマンドの接続が切れた開発者と、ほかの開発者は、適用状況の確認のコマンドの出力のうち、適用中の反映と反映ごとの結果の一覧を読む。開発者は、反映に使ったトークンと日時から、自分の反映の結果を見分ける。後から別の反映が入っていても、自分の反映の結果は一覧に残る。スキーマ変更権限を持つメンバーは、管理画面で同じ内容を確認する。
2. 適用中の反映がある間の管理画面の示し方は、`index.md` の「管理画面の操作」の「スキーマの反映の適用中」に従う。
3. メンバーは、結果に示されたコンテンツを開いて直す。制約を満たさない公開内容と入力エラーを持つ下書きは、EDIT-15 のとおり、モデルごとの件数から絞り込んだ一覧を開いて直す。不整合となった通知定義の参照は、通知設定の権限を持つメンバーが FORM-04 で直す。
4. 版を進めた反映（移行定義の適用を伴わない反映、移行の適用、直接反映）と、適用済みとしての記録は、操作履歴にも残る。ワークスペース設定の権限を持つメンバーが確認できる（WS-11）。

失敗した反映と、結果を確認できていない反映を、CMS は成功として示さない。表示アプリへの通知の状況は、反映の結果と区別して PUB-08 で確認する。

### 異常系

- 権限不足（コマンド）: 共通の異常系に従う。
- 権限不足（管理画面）: `index.md` の「共通の規則」に従う。必要な権限はスキーマ変更権限。
- リソース不在（反映の記録が無い）: スキーマを一度も反映していないワークスペースでは、CMS は版の記録が無いことを示す。
- リソース不在（結果に示されたコンテンツが無い）: 反映の後に完全削除されたコンテンツは、結果から開けない。CMS は対象が無いことを示す。
- 反映が切り替えの拒否で失敗していた: 反映ごとの結果の一覧は、確定の時点で切り替えを拒否されたことと、その理由を示す（SMIG-06）。現行スキーマ、データ、運用設定は変わっていない。開発者は、SMIG-05 からやり直す。
- 反映が適用中のまま終わらない: 進行が、止まった反映を中断として失敗で終えるまでの時間（APP-12）止まった反映を、CMS は中断として失敗で終える。現行スキーマ、データ、運用設定は変わらず、既存の公開内容は既存の構造で配信が続く。CMS は、そのワークスペースのコンテンツを変える操作を再び受け付ける。開発者は、適用状況の確認で、反映が中断を理由に失敗したことを確かめ、SMIG-05 からやり直す。中断が繰り返される場合、開発者は、ホスティング運営者に状態の確認を依頼する（HOST-06）。適用中の反映と、中断で終わった反映は、成功として扱わない。
- 反映に使ったトークンの発行者が解除されている、またはトークンが失効している: 版の記録は、トークンを記録の時点の値で示す（SMIG-04）。発行者の解除とトークンの失効の後も、同じ値を示す。手動発行したトークンによる以後の反映は、発行者の解除で止まらない。
