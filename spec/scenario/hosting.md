# 設置の運用

ホスティング運営者が、設置を導入し、更新し、障害から復旧し、利用を終了する。用語は `spec/requirements.md` の 1 章に従う。

## 共通の規則

`spec/scenario/index.md` の「共通の規則」に、次を加える。

- ホスティング運営者は、設置の設定の宣言、運用コマンドの実行、手順書に沿った作業で設置を運用する。運用コマンドは、設置の実行環境で実行するコマンドを指す。
- 運用コマンドの実行には、設置の運用権限を必要とする。設置の運用権限は、設置の実行環境と保存先を操作できる資格情報を持つことを指す。
- 設置の運用権限は、ワークスペースの権限と区別する。メンバーは、所有者を含め、役割と権限によらず運用コマンドの操作を行えない。トークンでも行えない。設置の運用権限だけでは、管理画面にログインできない。
- 運用コマンドは、設置の状態が受け付けるものだけを実行する。設置の状態と、状態ごとに受け付ける運用コマンドは、「設置の状態」の表だけが定める。HOST-01 から HOST-11 のどの運用コマンドも、この表に従う。
- 運用コマンドの出力と通常のログは、資格情報、トークンの値、運用設定の秘密情報、回答の入力内容を含まない。
- 運用条件は、対応する実行環境、必要な資源、利用上限、バックアップ間隔、復旧手順を指す。導入手順が運用条件を示す。
- データの版は、保存済みのデータの形を表す。CMS の版ごとに、扱うデータの版が一つ決まる。設置は、保存済みのデータの版を記録する。設置の更新と復旧で比べるのは、保存済みのデータの版と、実行する CMS が扱うデータの版である。「更新前の版」「更新先の版」「復旧したデータの版」は、データの版を指す。「更新先の版の CMS」「更新前の版の CMS」は、その版を扱う CMS を指す。

### 設置の状態

設置は、次のいずれか一つの状態にある。状態は、保存先のデータと復旧の記録から決まり、設置の停止では変わらない。表の上から順に当てはめ、最初に当たる状態とする。復旧の記録は、CMS が復旧の開始と完了を残す記録で、バックアップの対象に含まず、復旧で置き換わらない。

| 状態 | 当たる設置 | 受け付ける運用コマンド | 利用者の要求 | 運営者の次の操作 |
| --- | --- | --- | --- | --- |
| 復旧の進行中 | 復旧を開始し、完了も失敗もしていない設置のうち、復旧の開始から、復旧を進行中として扱う時間（APP-12）が過ぎていないもの | 起動、バックアップの一覧。起動は、結果に、復旧が進行中であることと、復旧を始め直せる時期を示す | 受け付けない | 示された時期の後に、設置を起動して状態を確かめる |
| 復旧の失敗 | 復旧を開始し、完了していない設置のうち、CMS が失敗を示したものと、復旧の開始から、復旧を進行中として扱う時間（APP-12）が過ぎたもの（中断した復旧） | 起動、バックアップの一覧、復旧。起動は、結果に、復旧が失敗したことを示す | 受け付けない | 原因を解消して、HOST-08 で復旧を始め直す |
| 利用再開前 | 復旧が完了し、利用を再開していない設置。保存先に復旧したデータがある | 起動、バックアップの一覧、復旧、利用の再開。実行する CMS が扱うデータの版が、復旧したデータの版と違う設置では、利用の再開に、CMS を復旧したデータの版の CMS に合わせることを示す | 受け付けない | 利用の再開を行う（HOST-08）。データの版が違う設置では、先に CMS を復旧したデータの版の CMS に合わせる |
| 初期化の前 | 保存先が空の設置。一度も起動していない設置と、保存先を空にした設置が当たる。完了した復旧の記録が残っていても、保存先が空なら当たる | 起動、バックアップの一覧、復旧 | 受け付けない | 設置を起動するか、HOST-08 で復旧する |
| 読み込みの途中 | 初期構成の読み込みを終えていない設置（HOST-02 の「読み込みの中断」） | 起動、バックアップの一覧、復旧。起動は読み込みを続きから進める | 受け付けない | 設置を起動し直すか、HOST-08 で復旧する |
| 更新の途中 | 保存済みのデータの更新を始めて完了していない設置（HOST-05 の「更新の失敗・中断」） | 設置の更新、バックアップの一覧、復旧。起動とバックアップの取得は拒否する。設置の更新は、実行する CMS が更新先の版の CMS のときに受け付ける | 受け付けない | 更新先の版の CMS で設置の更新を実行し直すか、CMS を更新前の版の CMS に戻して、更新の前のバックアップから HOST-08 で復旧する |
| 更新が必要 | 更新を始めていない設置のうち、保存済みのデータの版が、実行する CMS が扱うデータの版と違うもの | 設置の更新、バックアップの取得と一覧、復旧。起動は拒否する。設置の更新は、実行する CMS が、保存済みのデータの版からの更新を持つときに受け付ける（HOST-05 の「更新を持たない CMS」） | 受け付けない | 設置の更新を実行する（HOST-05）。実行する CMS が保存済みのデータの版からの更新を持たない場合は、CMS を保存済みのデータの版の CMS に入れ替える |
| 稼働中 | 上のどれにも当たらない設置 | 起動、動作確認、紐付けを待つ運用設定の確認、ワークスペースの作成、初期所有者の招待の発行し直し、設置の更新、状態確認、バックアップの取得と一覧、復旧、終了前の確認、ワークスペースの終了、管理者復旧 | 受け付ける | なし |

- 受け付けない運用コマンドを、CMS は実行せず、設置の状態を示す。運営者は、表の「運営者の次の操作」を行う。
- 利用者の要求は、管理画面の利用と、トークンによる要求（取得、フォームの送信、スキーマの反映、コンテンツとメディアの管理）を指す。利用者の要求を受け付けない状態では、CMS は通知も送らない。フォームの送信に、受付完了を返さない。停止している設置は、状態によらず、利用者の要求を受け付けない。
- 設置の設定に不足や誤りがある設置は、状態によらず、起動せず、利用者の要求も受け付けない。CMS は、該当する設定と理由を示す。起動以外の運用コマンドは、そのコマンドが使う設定に不足や誤りがあれば実行せず、何も変えずに、該当する設定と理由を示す。どの運用コマンドもデータの保存先を使う。加えて、バックアップの取得と復旧はメディアの保管先と秘密情報の鍵を、ワークスペースの作成、初期所有者の招待の発行し直し、管理者復旧は設置の公開の URL を使う。使う設定に不足や誤りが無い運用コマンドは、表のとおりに受け付ける。運営者は、示された設定を直して起動し直す（HOST-01）。
- データの保存先の設定に不足や誤りがあって、保存先を読めない設置では、CMS は設置の状態を求められない。CMS は、起動を含むどの運用コマンドも実行せず、利用者の要求も受け付けない。設置の状態を示さず、該当する設定と理由を示す。運営者は、データの保存先の設定を直して実行し直す。
- 設定は正しく、保存先の障害でデータを読めない設置でも、CMS は設置の状態を求められない。CMS は、バックアップの一覧のほかの運用コマンドを実行せず、利用者の要求も受け付けず、保存先を読めないことを示す。運営者は、障害を解消して実行し直すか、空の保存先を用意して HOST-08 で復旧する。空の保存先の設置の状態は、表のとおりに決まり、その状態が受け付けるときに復旧を受け付ける。
- 起動は、次の二つを除いて、設置の状態を変えない。初期化の前の設置の起動は、設置を初期化して初期構成を読み込む（HOST-02）。読み込みの途中の設置の起動は、読み込みを続きから進める。

## HOST-01 設置を導入し、保存先とメール送信の動作を確認する

- **利用者**: ホスティング運営者
- **目的**: 手順に沿って設置を起動し、保存先とメール送信が動くことを確かめて、利用を始められる状態にする。
- **要件**: 2, 3.1, 9.2, 10.1, 10.4

### 正常系

1. 運営者は導入手順で運用条件を確認し、対応する実行環境と必要な資源を用意する。
2. 運営者は設置の設定に、データとメディアの保存先、秘密情報の鍵、設置の公開の URL、設置全体のメール送信を宣言する。秘密情報の鍵は、運用設定の秘密情報を保護する鍵で、設置のデータと別に管理する。設置の公開の URL は、利用者が管理画面を開く URL で、招待とアクセス回復のメールに入れる URL に使う。設置全体のメール送信は、招待とアクセス回復のメールに使う。ワークスペースの送信接続設定とは別に持つ。外部メールを使えない設置では、設置全体のメール送信を宣言しない。起動と同時にワークスペースと初期所有者を用意する場合は、初期構成も宣言する（HOST-02）。
3. 運営者は設置を起動する。CMS は設定を検証して起動し、起動の結果を示す。初期構成を宣言した設置では、CMS はこの起動で初期構成を読み込む（HOST-02）。
4. 運営者は運用コマンドで動作確認を実行し、確認メールの宛先を指定する。CMS は、保存先への書き込みと読み出し、メディアの保存と取り出し、指定した宛先へのメール送信を試し、項目ごとに成功・失敗と理由を示す。
5. 運営者は確認メールの到着を確かめる。
6. 初期構成を宣言しなかった設置では、運営者は HOST-04 でワークスペースと初期所有者を用意する。初期構成を宣言した設置では、手順 3 の起動が用意している。
7. 初期所有者が管理画面にログインできることを確かめて、導入を終える。フォームの通知に使う送信接続設定の動作確認は、通知設定の権限を持つメンバーが管理画面で行う。

### 異常系

- **入力エラー（設置の設定の誤り）**: 保存先、秘密情報の鍵、設置の公開の URL の宣言に不足や誤りがある場合と、宣言した設置全体のメール送信に不足や誤りがある場合、CMS は起動せず、利用者の要求も受け付けず、該当する設定と理由を示す。運営者は設定を直して起動し直す。
- **入力エラー（確認メールの宛先の誤り）**: 宛先の形式が誤っていると、CMS は動作確認を実行せず、理由を示す。運営者は宛先を直して実行し直す。
- **動作確認の失敗**: CMS は失敗した項目と理由を示す。認証情報そのものは示さない。運営者は保存先やメール送信の設定を直し、動作確認を実行し直す。
- **確認メールが届かない**: 動作確認の成功は、メール送信基盤が受理したことを示す。受信箱への到着は示さない。運営者は宛先とメール送信環境を確かめる。
- **外部メールを使えない設置**: 運営者は設置全体のメール送信を宣言せずに起動する。動作確認はメール送信を未設定と示す。招待の受け渡しは HOST-04、アクセスの復旧は HOST-11 で行う。
- **資源の不足**: 対応しない実行環境や、必要な資源を満たさない環境では、CMS は起動時または動作確認で不足する資源を示す。運営者は資源を用意して起動し直す。
- **権限不足**: 設置の運用権限を持たない人は、設定の宣言、起動、動作確認を行えない。
- **操作の取り消し**: 導入をやめる場合、ワークスペースを用意する前は、設置を停止して保存先を空にする。ワークスペースを用意した後は HOST-10 で終了する。

## HOST-02 初期構成を宣言して、空の設置を起動する

- **利用者**: ホスティング運営者、開発者（手元の設置）
- **目的**: ワークスペース、所有者、トークン、運用設定を宣言し、起動するたびに同じ状態から設置を用意する。
- **要件**: 3.1, 9.1, 9.2, 9.3, 10.1

### 正常系

1. 利用者は初期構成を宣言する。宣言する内容は次のとおり。
   - ワークスペース
   - ワークスペースごとの所有者。所有者の宣言は、ワークスペースごとに一人とする。メールアドレス、名前、初回のログインに使うパスワードを宣言する
   - トークン。名称、種類、許可、範囲、有効期限、値を宣言する。範囲は、ワークスペース全体、またはモデル・フォームのキーの集合で宣言する。有効期限を設けないトークンは、期限なしと明示して宣言する
   - ワークスペース単位の運用設定。送信接続設定、表示アプリへの通知設定、プレビュー先の表示アプリの URL、コンテンツの保持方針
   - モデル・フォームごとの運用設定。対象をキーで指定する。フォームごとの通知先、通知定義、受付状態、回答の保持方針と、キーの集合で宣言したトークンの範囲とする。モデルごとの運用設定は、トークンの範囲だけである
2. 利用者は、保存先が空の状態で設置を起動する。
3. CMS は初期構成を検証して読み込み、ワークスペース、トークン、ワークスペース単位の運用設定を作成する。宣言した人をワークスペースのメンバーにし、所有者に指定する。モデル・フォームごとの運用設定は、紐付けを待つ運用設定として保持する。範囲をキーの集合で宣言したトークンは、範囲が紐付くまで、そのキーの対象を操作できない。
4. CMS は起動の結果に、読み込んだワークスペース、所有者、トークンの名称、運用設定の種類を示す。秘密情報の値は示さない。
5. CMS は初期構成の読み込みと、宣言したトークンごとの発行を、各ワークスペースの操作履歴に残す。実行者はホスティング運営者とする。
6. 所有者は宣言したパスワードでログインする。開発者は宣言したトークンの値でスキーマを反映する。宣言したトークンは手動発行したトークンと同じ規則に従い、初期構成の所有者を発行者とする。トークンの値は宣言した人が保管する。
7. 読み込んだ後は、管理画面の設定を正本とする。運用設定、メンバー、トークンの変更は管理画面で行う。

### 異常系

- **入力エラー（不正な初期構成）**: CMS は起動せず、該当する宣言と理由を示す。ワークスペース、メンバー、トークン、運用設定のいずれも作成せず、保存先は空のまま残る。利用者は宣言を直して起動し直す。不正とする宣言は次を含む。
  - 所有者を宣言していないワークスペース
  - 名称が重なる複数のワークスペース
  - ブラウザ用のトークンに、公開取得とフォーム送信以外の許可を持たせる宣言
  - 有効期限も、期限なしの明示もないトークン
  - スキーマ反映の許可と、キーの集合の範囲を組にしたトークン（WS-06）
  - 受付中と宣言したフォームで、有効な通知先または送信接続設定がそろわない宣言
  - 管理画面での設定と同じ検証を満たさない運用設定
- **読み込みの中断**: 読み込みの途中で起動が止まった場合、設置は読み込みを終えていない状態で残る。運営者は同じ宣言で起動し直す。CMS は続きから読み込み、作成済みのワークスペース、所有者、トークン、運用設定を作り直さない。読み込みを終えると、起動の結果に読み込んだ内容を示す。宣言を変えて起動し直した場合、CMS は起動せず、読み込みの途中の設置であることと、同じ宣言で起動し直すか、保存先を空にして始め直すことを示す。秘密の値（所有者のパスワード、送信接続設定の認証情報、表示アプリへの通知の宛先の秘密情報）だけを変えた宣言は、同じ宣言として扱う。CMS は続きから読み込み、作成済みの分の秘密の値は変えない。トークンの値は、この秘密の値に含めない。トークンの値を変えた宣言は、ほかの項目を変えた宣言と同じく拒否する。読み込みの途中で、扱うデータの版が違う CMS に入れ替えて起動した場合も、CMS は起動せず、読み込みの途中の設置であることを示す。運営者は、読み込みを始めた版の CMS で起動し直す。
- **データがある状態の起動**: 読み込みを終えた設置と、初期構成を宣言せずに起動した設置では、CMS は初期構成を読み込まずに起動し、読み込まなかったことを起動の結果に示す。初期構成の宣言を変えても、設置のデータは変わらない。設定を変える場合は管理画面で変更する。
- **データの作り直し**: CMS はデータの初期化機能を提供しない。データを作り直す場合は、設置を停止し、保存先を空にして起動し直す。CMS は初期構成を読み込み直す。復旧の記録は保存先のデータの外にあるので、復旧の記録が残っている設置では、保存先を空にするときに、復旧の記録も消す。復旧を開始して完了していない記録が残った設置は、復旧の進行中または復旧の失敗のままで、起動しても初期化しない。復旧が完了した記録が残った設置は、初期化の前で、起動は、残った復旧の記録を消してから設置を初期化する。
- **バックアップからの復旧**: 復旧では初期構成を読み込まない。復旧後の設定はバックアップの内容に従う。
- **権限不足**: 設置の運用権限を持たない人は、初期構成の宣言と設置の起動を行えない。手元の設置では、開発者が設置の運用権限を持つ。
- **リソース不在（初期構成がない）**: 初期構成を宣言せずに空の設置を起動すると、CMS はワークスペースのない状態で起動する。運営者は HOST-04 でワークスペースを作成する。
- **操作の取り消し**: 読み込みは取り消せない。読み込んだ内容をやり直す場合は、保存先を空にして起動し直す。運用中の設置では、誤った設定は管理画面で直し、不要なワークスペースは HOST-09 で終了する。

## HOST-03 紐付けを待つ初期構成の運用設定を確認する

- **利用者**: ホスティング運営者、その運用設定を扱う権限（手順 1）を持つメンバー
- **目的**: 初期構成で宣言したモデル・フォームごとの運用設定のうち、まだ対象に紐付いていないものを把握する。
- **要件**: 3.1, 9.2, 10.1

### 正常系

1. メンバーは管理画面で、自分のワークスペースの紐付けを待つ運用設定のうち、自分が扱う種類のものを確認する。その運用設定を扱う権限は、通知先と通知定義では通知設定の権限、受付状態と回答の保持方針では受付管理の権限、トークンの範囲ではトークンの発行と失効を行うアプリ連携の権限である。ホスティング運営者は運用コマンドで、ワークスペースを指定して、すべての種類を確認する。
2. CMS は、紐付けを待つ運用設定ごとに、対象の種類（モデル・フォーム）、対象のキー、運用設定の種類と内容を示す。トークンの範囲では、トークンの名称と、紐付けを待つキーを示す。秘密情報とトークンの値は示さない。
3. 開発者が、そのキーのモデル・フォームを含むスキーマを反映する。CMS は対象の作成と同時に運用設定を紐付ける。作成したフォームの受付状態は、`form-operation.md` の「共通の規則」に従う。トークンの範囲は、そのキーの対象の作成と同時に紐付き、そのトークンは以後その対象を操作できる。
4. CMS は紐付けを操作履歴に残し、紐付けを待つ運用設定の一覧から除く。
5. 紐付けた後の運用設定は、管理画面で設定した運用設定と同じに扱う。表示名称の変更と、移行定義によるモデルのキーの変更で失わない。

### 異常系

- **入力エラー（キーの宣言の誤り）**: スキーマにないキーを指定したフォームの運用設定は、紐付けを待つ状態で残り、どの対象にも適用しない。その運用設定を扱う権限を持つメンバーは、一覧でキーを確かめ、正しい対象の運用設定を管理画面で設定する。後からそのキーのフォームを作成する反映が確定すると、残っていた運用設定はそのフォームに紐付く。メンバーは、紐付いた運用設定を管理画面で変更する。
- **不要なトークンの範囲**: キーを誤って宣言した範囲と、不要になった範囲は、紐付けを待つ状態で残る。アプリ連携の権限を持つメンバーは、そのトークンを失効させ（WS-07）、必要な範囲のトークンを発行する。
- **範囲が紐付く前のトークンの要求**: 範囲をキーの集合で宣言したトークンで、紐付けを待つキーの対象を指定した要求は、存在しない対象への要求として扱い、対象のキーを示すエラーを返す。開発者は、そのキーの対象を含むスキーマを反映してから要求し直す。スキーマの反映には、範囲をワークスペース全体で宣言したスキーマ反映の許可を持つトークンを使う。
- **紐付けた通知定義の参照が不整合**: 紐付けた通知定義が、作成したフォームにない項目を参照している場合も、CMS は紐付けと受付を妨げない。通知設定の権限を持つメンバーが管理画面で不整合に気付き、修正する。
- **紐付けの対象にならない作成**: 紐付けは、そのキーの対象を作成した反映で一度だけ行う。紐付けた対象を削除して同じキーで作り直しても、削除前の運用設定を引き継がない。作り直した対象の運用設定は、その運用設定を扱う権限を持つメンバーが管理画面で設定する。トークンの範囲は、作り直した対象を範囲に持つトークンを発行して設定する（WS-06）。
- **操作の取り消し**: 確認は何も変えない。紐付けを待つ運用設定は、そのキーの対象が作成されて紐付くまで残る。初期構成の宣言をやり直す場合は、HOST-02 の「データの作り直し」に従う。
- **権限不足**: その運用設定を扱う権限を持たないメンバーには、その種類の紐付けを待つ運用設定を示さない。ほかのワークスペースの紐付けを待つ運用設定は確認できない。運用コマンドでの確認には、設置の運用権限を必要とする。
- **リソース不在**: 紐付けを待つ運用設定がないワークスペースでは、運用コマンドは、待つものがないことを示す。管理画面は、紐付けを待つ運用設定の表示を出さない。存在しないワークスペースを指定した運用コマンドは、ワークスペースが存在しないことを示す。

## HOST-04 ワークスペースを作成し、初期所有者を設定する

- **利用者**: ホスティング運営者
- **目的**: 運用中の設置にワークスペースを追加し、最初の所有者が管理を始められるようにする。
- **要件**: 1, 2, 9.1, 9.2

### 正常系

1. 運営者は運用コマンドで、ワークスペースの名称と初期所有者のメールアドレスを指定して作成を実行する。
2. CMS は、始めにワークスペースの ID を決めて示し、ワークスペースを作成して利用できる状態にし、続けて、初期所有者に宛てた招待を有効期限付きで発行する。招待の発行は、初期所有者の招待の発行し直しと同じ手順で行う。設置全体のメール送信で招待のメールを送る。初期所有者の招待は、メンバー管理の権限によるメンバーの招待と区別し、運営者だけが発行する。権限の組み合わせを持たず、参加した人を所有者に指定する。招待の置き換えと、メンバーの招待との関係は、`workspace-admin.md` の「共通の規則」の「招待の種類」に従う。
3. CMS は、作成したワークスペース（ID と名称）、招待の宛先、招待の有効期限を運用コマンドの結果に示す。作成したワークスペースは、履歴とごみ箱の標準の保持方針を持つ。所有者と、ワークスペース設定の権限を持つメンバーが、WS-10 で変える。
4. CMS は、初期所有者の招待の発行と発行し直しを、そのワークスペースの操作履歴に残す。実行者はホスティング運営者とする。
5. 初期所有者は AUTH-01 の手順で参加する。その設置に既にアカウントを持つ人は、ログインして招待を受ける。参加すると、参加したワークスペースが開く。
6. CMS は、参加した人をワークスペースのメンバーにし、所有者に指定する。所有者はワークスペースに一人とし、すべての権限でメンバーの招待、トークンの発行、運用設定を行う。既存のワークスペースのスキーマ、コンテンツ、メンバー、設定は変わらない。

### 異常系

- **入力エラー**: メールアドレスの形式が誤っている場合、CMS はワークスペースを作成せず、理由を示す。運営者は指定を直して実行し直す。
- **作成の中断**: CMS は、止まった作成を自動で進めない。止まった作成のワークスペースは、状態確認（HOST-06）に、ID と名称とともに現れる。利用できる状態にする前に止まったものは作成の途中として、その後に止まったものは所有者がいないワークスペースとして現れる。運営者は、手順 2 で示された ID か状態確認が示す ID を指定して、同じ名称と初期所有者のメールアドレスで作成を実行し直す。どの段で止まった作成も、CMS は止まった段から続け、初期所有者へ招待を発行する。作成を終えると、結果に作成したワークスペースと招待を示す。作成を終えたワークスペースの ID を指定した実行は、何も変えずに、作成済みであることを示す。同じ ID で名称またはメールアドレスが違う指定は、その ID が使われていることを示して拒否する。作成をやめる場合は、HOST-09 で利用終了を一回実行する。
- **招待の期限切れ**: 期限を過ぎた招待では参加できない。運営者は運用コマンドで、対象のワークスペースの初期所有者の招待を発行し直す。
- **宛先の誤り**: 運営者は正しいメールアドレスを指定して、初期所有者の招待を発行し直す。前の招待は失効し（「招待の種類」）、誤った宛先の人は参加できない。
- **外部メールを使えない設置**: CMS はメールを送らず、一度だけ使える招待の URL を運用コマンドの結果に示す。運営者は初期所有者本人を確かめて、URL を CMS の外で渡す。
- **権限不足**: 設置の運用権限を持たない人は実行できない。メンバーは管理画面でワークスペースを作成できない。
- **リソース不在**: 招待の発行し直しで存在しないワークスペースを指定すると、CMS はワークスペースが存在しないことを示す。初期所有者の招待を発行し直せるのは、所有者がいないワークスペースに限る。初期所有者がまだ参加していないワークスペースと、復旧で所有者を失ったワークスペース（HOST-08）が該当する。作成の途中のワークスペースでは発行し直せず、CMS はワークスペースが存在しないことを示す。所有者がいるワークスペースでは発行し直せない。所有者の変更は所有者が管理画面で行う。所有者を失ったワークスペースへの招待の宛先は、そのワークスペースのメンバーでも、メンバーでない人でもよい。宛先に、そのワークスペースの未使用のメンバーの招待があっても、発行し直せる（「招待の種類」）。CMS は、招待を受けた人を所有者に指定する。
- **操作の取り消し**: 作成したワークスペースをやめる場合は、HOST-09 で終了を一回実行する。作成の途中のワークスペースも、作成を実行し直さずに、同じ操作で終了する。

## HOST-05 設置を更新する

- **利用者**: ホスティング運営者
- **目的**: データを壊さずに、設置を新しい版へ更新する。
- **要件**: 2, 10.1, 10.2

### 正常系

1. 運営者は更新先の版の更新手順を確認する。更新手順は、CMS の版ごとに、次を示す。
   - 更新前に必要な作業。利用者への停止の知らせ、設置の停止、バックアップの取得を含む
   - 影響。更新で形が変わる保存済みのデータと、更新の間に止まる機能
   - 必要な停止時間
   - 復旧方法。更新に失敗した場合に、更新前の版で利用を再開する手順
   - 更新先の版が必要とする実行環境と資源
2. 運営者は利用者へ停止を知らせ、設置を停止する。停止中は、管理画面、取得、フォーム受付、通知が止まる。停止中のフォーム送信に、受付完了を返さない。
3. 運営者は HOST-07 でバックアップを取得し、整合性の確認が成功したことを確かめる。このバックアップは、現在のデータの版で取得したものになる。
4. 運営者は更新手順に沿って、CMS を更新先の版へ入れ替える。保存済みのデータの版が、実行する CMS が扱うデータの版と違う間、設置は更新が必要な状態にある。CMS は起動せず、利用者の要求も受け付けず、更新が必要なことを示す。
5. 運営者は運用コマンドで設置の更新を実行する。CMS は、更新先の版が必要とする資源を満たすことを確かめる。CMS は、更新を始めたことと更新先の版を設置に記録してから、保存済みのデータを更新先の版へ更新する。
6. 更新に成功すると、CMS は保存済みのデータの版を進め、更新を始めた記録を消して、更新後の版と、更新が完了したことを示す。
7. 運営者は設置を起動する。停止中に送らなかったフォームの通知は、`form-operation.md` の「共通の規則」に従う。
8. 運営者は HOST-01 の動作確認を実行し、HOST-06 で通知と移行の状況を確認して、利用の再開を知らせる。

### 異常系

- **設置の更新を実行せずに起動した**: 保存済みのデータの版が、実行する CMS が扱うデータの版と違うため、CMS は起動せず、更新が必要なことを示す。運営者は手順 5 の設置の更新を実行してから起動する。
- **更新の失敗・中断**: 保存済みのデータの更新を始めた後に失敗した更新と、途中で止まった更新を、CMS は完了と扱わない。失敗では、失敗と理由を示す。更新を始めた記録が残り、保存済みのデータは、更新前の版の形とも更新先の版の形とも限らない。この設置は、実行する CMS によらず、更新の途中の状態にある。CMS は起動せず、更新を始めて完了していないことと、更新先の版を示す。CMS を更新前の版の CMS に戻して起動した場合も同じである。運営者の次の操作は、次の二つである。
  - 更新をやり直す: 原因を解消し、更新先の版の CMS で、設置の更新を実行し直す。実行し直した更新は、前の更新がどこで止まっていても、保存済みのデータを更新先の版へ更新する
  - 更新をやめる: CMS を更新前の版の CMS に戻し、手順 3 で取得したバックアップから HOST-08 で復旧する。更新先の版の CMS のままでは、更新前の版のバックアップは設置の版に対応しないので、復旧できない（HOST-08 の「使えないバックアップの指定」）。復旧は、更新を始めた記録を含めて、設置のデータをバックアップの内容に置き換える
- **並行した更新**: 設置の更新が進行中の間に、設置の更新をもう一度実行した場合、CMS は、後の実行を始めず、データを変えずに、更新が進行中であることを示す。運営者は、先に実行した設置の更新の出力で、結果を確かめる。出力を得られなかった更新は、「更新の失敗・中断」に従って実行し直す。
- **更新が不要な設置**: 保存済みのデータの版が、実行する CMS が扱うデータの版と同じ場合、CMS はデータを変更せず、更新が不要なことを示す。
- **更新を持たない CMS**: 実行する CMS が、保存済みのデータの版からの更新を持たない場合（更新の完了の後に、CMS を更新前の版の CMS に戻した設置が当たる）、CMS は設置の更新を始めず、データを変えず、更新を始めた記録も残さずに、保存済みのデータの版と、その版からの更新を持たないことを示す。運営者は、CMS を保存済みのデータの版の CMS に入れ替えて起動する。更新前の版で利用する場合は、「操作の取り消し」に従う。
- **資源の不足**: 更新先の版が必要とする資源を満たさない場合、CMS は設置の更新を始めず、不足する資源を示す。保存済みのデータは変わらず、更新を始めた記録も残らない。運営者は資源を用意して実行し直す。
- **権限不足**: 設置の運用権限を持たない人は更新を実行できない。
- **リソース不在**: ワークスペースがない設置も、同じ手順で更新する。
- **操作の取り消し**: 保存済みのデータの更新を始める前（設置の更新を実行していない、または、資源の不足で始まらなかった）は、CMS を更新前の版の CMS に戻して起動すると、更新前の版で利用を再開する。更新を始めた後に更新前の版へ戻す場合は、完了の前後によらず、CMS を更新前の版の CMS に戻し、手順 3 のバックアップから HOST-08 で復旧する。バックアップの取得以降の変更は失われる。

## HOST-06 容量と資源の不足を確認する

- **利用者**: ホスティング運営者
- **目的**: 保存容量と通知用の空き容量の不足、通知と移行の状況を把握し、必要な対処を決める。
- **要件**: 2, 8.2, 10.1, 10.2, 10.4

### 正常系

1. 運営者は運用コマンドで状態確認を実行する。
2. CMS は次を示す。
   - データとメディアの保存容量の使用量と空き、通知用の空き容量。不足している項目は不足と示す
   - 運用条件の利用上限に対する現在の利用量
   - ワークスペースごとの未完了の通知の件数。項目は、HOST-09 の手順 2 の未完了の通知と同じ
   - 隔離されたイベントの件数。イベントは、確定した操作に続く処理（表示アプリへの通知の作成、派生形式の生成など）を CMS の中で起こす。配送を繰り返しても処理できなかったイベントを、CMS は隔離する
   - 適用中のスキーマの反映と、未解消の失敗した反映。定義は SMIG の「共通の前提」に従う
   - 最後に取得したバックアップの日時
   - 作成の途中のワークスペース。利用できる状態にする前に作成が止まったワークスペース（HOST-04）が該当する。ID と名称を示す。必要な対処として、その ID で作成を実行し直すこと（HOST-04）、または利用終了を実行すること（HOST-09）を示す
   - 利用終了の途中のワークスペース。利用終了（HOST-09）の消去が進行中のワークスペースが該当する。ID と名称を示す。消去が完了したワークスペースは示さない。CMS が消去の続きを自動で進めるので、必要な対処は無い
   - 所有者がいないワークスペース。初期所有者がまだ参加していないワークスペース（HOST-04。利用できる状態にした後に作成が止まったものを含む）と、復旧で所有者を失ったワークスペース（HOST-08）が該当する。ID と名称を示し、初期所有者の招待が、有効か、期限切れか、無いかを添える。必要な対処は、招待の状態だけで決まる。有効な招待が無いワークスペースには、初期所有者の招待の発行し直し（HOST-04）を示す。有効な招待があるワークスペースには、招待された人の参加を待つこと、招待が届いていなければ発行し直すことを示す
   - 項目ごとの必要な対処
3. 運営者は不足している資源を増やし、状態確認を実行し直して不足が解消したことを確かめる。
4. 隔離されたイベントがある場合、運営者は実行基盤の運用手順で、隔離されたイベントを配送し直す。状態確認を実行し直して、件数が 0 に戻ったことを確かめる。
5. フォームの通知の未対処の送信失敗には通知設定の権限を持つメンバー、表示アプリへの通知の未対処の送信失敗にはアプリ連携の権限を持つメンバー、移行の失敗には開発者が対処する。運営者は該当するワークスペースの所有者へ知らせる。

### 異常系

- **容量の不足で受け付けられない操作**: CMS は受け付けられない操作を成功と扱わず、明確な失敗を返す。フォームの送信には理由付きの受付失敗を返し、受付完了を返さない。メディアの登録と保存は理由を示して拒否する。運営者は容量を確保する。確保した後、利用者は操作をやり直す。
- **処理能力の上限**: 上限を超える要求に、CMS は明確な失敗または送信制限を返す。運営者は運用条件の利用上限と現在の利用量を比べ、資源を増やす。
- **状態を取得できない項目**: CMS は取得できなかった項目と理由を示し、不足なしとは示さない。運営者は保存先への接続を確かめて実行し直す。
- **権限不足**: 設置の運用権限を持たない人は状態確認を実行できない。メンバーは、自分のワークスペースの通知と移行の状況だけを管理画面で確認する。
- **リソース不在**: ワークスペースがない設置では、設置全体の容量と資源だけを示す。
- **操作の取り消し**: 状態確認は何も変えない。途中でやめても、設置は変わらない。

## HOST-07 バックアップを取得し、取得と復旧の動作を確認する

- **利用者**: ホスティング運営者
- **目的**: 復旧に使えるバックアップを保ち、取得と復旧が動くことを定期的に確かめる。
- **要件**: 2, 7.2, 10.2, 10.4

### 正常系

1. 運営者は運用コマンドでバックアップの取得を実行する。運用条件が示す間隔での定期実行は、運営者が自分の環境で設定する。
2. CMS は設置全体を一つのバックアップとして取得する。対象は、すべてのワークスペースのスキーマ、コンテンツ、履歴、メディア、回答、運用設定、アクセス権、受付結果と通知の送信結果、削除済みフォームの回答、適用済みの移行定義の記録とする。
3. CMS は取得の結果に、取得日時、含むワークスペース、整合性の確認の結果と、復旧に必要な秘密情報の鍵（鍵の値は示さない）とその復旧条件を示す。
4. 運営者はバックアップを、設置の運用権限を持つ人だけが扱える場所に保管する。
5. 運営者はバックアップの一覧で、バックアップごとの ID、取得日時、データの版、整合性の確認の結果、保持・削除期限を確認する。バックアップの一覧は、設置のデータを読まず、設置の状態によらず受け付ける。バックアップの保持・削除期限は、通常データの保持方針とは別に定める。バックアップには取得時点の保存回答が残る。通常データで削除した回答も、バックアップの削除期限まで残る。
6. 運営者は復旧の動作を確認する。運用中の設置とは別の、検証に使う設置へ、HOST-08 の手順でバックアップを復旧し、復旧の結果（HOST-08 の手順 4）で復旧点と各ワークスペースの内容を確かめる。検証に使う設置は利用を再開せずに終了する。終了は、HOST-10 の手順 3 と手順 4 で行い、設置を停止して、保存先とともに復旧の記録も消去する。終了前の確認（HOST-10 の手順 1）は、利用再開前の設置が受け付けないので、行わない。利用再開前の設置は、配信、受付、通知を行わない。
7. 運営者は確認した日時と結果を記録し、運用条件が示す間隔で繰り返す。

### 異常系

- **取得の失敗**: 保存先の容量不足や保管先への接続の失敗で取得できない場合、CMS は失敗と理由を示す。途中で失敗した取得は、バックアップの一覧に現れない。運営者は原因を解消して実行し直す。
- **整合性の確認の失敗**: CMS はそのバックアップを復旧に使えないものと示す。運営者は取得し直す。
- **復旧の確認の失敗**: 検証に使う設置への復旧が失敗した場合、CMS は失敗と理由を示し、復旧を完了と扱わない。運営者は別のバックアップで確認し、取得の手順と保管先を見直す。
- **秘密情報の復旧条件を満たさない**: 別に管理する秘密情報を用意できない場合、CMS は復旧を実行せず、不足する秘密情報を示す。運営者は秘密情報の保管を見直す。
- **権限不足**: 設置の運用権限を持たない人は、取得、一覧の確認、復旧を行えない。メンバーは、役割と権限によらず、管理画面でバックアップを取得できない。
- **リソース不在**: バックアップが一つもない設置では、一覧は取得済みのバックアップがないことを示す。運営者は取得を実行する。
- **操作の取り消し**: 実行中の取得を中止すると、その取得はバックアップの一覧に現れない。設置のデータは変わらない。不要なバックアップは、運営者が保管先で削除する。

## HOST-08 バックアップから設置全体を復旧し、利用を再開する

- **利用者**: ホスティング運営者
- **目的**: 障害や誤操作の後に、設置全体をバックアップの時点へ戻し、失われる範囲を確かめてから利用を再開する。
- **要件**: 2, 6.2, 6.3, 8.3, 10.1, 10.2

### 正常系

1. 運営者は設置を停止し、実行中のほかの運用コマンドが終わっていることを、自分の運用手順（運用コマンドを実行した環境と、その実行の記録）で確かめる。復旧は、ほかの運用コマンドの実行が終わっている設置で行う。保存先のデータを読み出せる場合は、復旧の前に HOST-07 で現在の状態のバックアップを取得する。
2. 運営者はバックアップの一覧（HOST-07）で、復旧に使うバックアップの ID を確かめる。運用コマンドで、そのバックアップを指定して復旧を実行する。CMS は、データを変更せずに、復旧前の確認として次を示し、確認を求める。対話できない環境では、運営者は内容を確かめたうえで確認の指定を添えて実行する。
   - 復旧点（バックアップの取得日時）
   - すべてのワークスペースが復旧点へ戻ること。復旧で戻るワークスペースと、無くなるワークスペースを、ID と名称で示す。無くなるのは、現在の設置にあり、バックアップに無いワークスペース
   - ワークスペースごとの、失われる可能性のある期間。復旧点より後の受付、回答、編集、公開、スキーマの反映が失われる
   - 復旧で元に戻る可能性がある操作の種類。復旧点以降の個別の削除、メンバーの解除と権限の縮小、トークンの失効
   - 別に管理する秘密情報の復旧条件
   - バックアップの大きさと、運用条件が示す、復旧できる大きさの上限
3. 運営者は内容を確かめて確認する。確認を受けると、設置は復旧の進行中になる。CMS は設置全体のデータをバックアップの内容に置き換える。初期構成は読み込まない。
4. 復旧が完了すると、設置は利用再開前になる。CMS は、復旧の結果に、手順 5 の利用再開前の確認と同じ内容を示す。復旧の進行中、復旧の失敗、利用再開前は別の状態とする。どの間も、CMS は取得、フォーム受付、通知、管理画面の利用を止める。それぞれの状態が受け付ける運用コマンドは、「共通の規則」の「設置の状態」に従う。
5. 運営者は運用コマンドで利用の再開を実行する。CMS は、データを変更せずに、利用再開前の確認として次を示し、確認を求める。対話できない環境では、運営者は内容を確かめたうえで確認の指定を添えて実行する。
   - 復旧点と、ワークスペースごとの失われる可能性のある期間
   - 保持期間を過ぎた保存回答の件数。CMS は通知の再開前に削除する。復旧によって回答の保持期間を延長しない
   - 保存済み回答の通知の送信結果。送信済みか判断できない通知（送信を終えていない通知）は、送信成功を確認できない送信失敗として示す。CMS は、利用の再開のときに、これらの通知を送信失敗にする
   - 復旧点より後の受付は失われること。その期間を示す。受付は確定するか失敗するかのどちらかで、進行中の状態を持たない
   - 復旧点で適用中だったスキーマの反映と、進行中だった適用の事前確認。CMS は成功と扱わず、利用の再開のときに失敗にする
   - 公開中のコンテンツと公開のメディアの件数、未公開のコンテンツと非公開のメディアの件数。復旧点で未公開・非公開だったものは、未公開・非公開のまま戻る
   - アカウントが無いメンバー。バックアップの取得と重なって参加したメンバーで生じる。CMS は、利用の再開のときに、アカウントが無いメンバーを削除する。ワークスペースごとに、削除されるメンバーの数を示す
   - 所有者がいないワークスペース。所有者のメンバーが削除されて所有者を失うワークスペースと、復旧点で所有者がいなかったワークスペース（初期所有者がまだ参加していないものと、復旧点で作成の途中で、ワークスペースのデータまで作り終えていたものを含む）が該当する。ID と名称を示す
   - 作成の途中のワークスペース。復旧点で作成の途中だったワークスペースのうち、ワークスペースのデータまで作り終えていなかったものが該当する。ID と名称を示す。利用の再開の後も、作成の途中のまま残る。ワークスペースのデータまで作り終えていたものは、利用の再開の後は、所有者がいないワークスペースになる
   - 利用終了の途中のワークスペース。復旧点で消去を終えていなかったワークスペースが該当する。ID と名称を示す。利用の再開の後、CMS が消去の続きを自動で進める
6. 運営者は内容を確かめて確認する。運営者は各ワークスペースの所有者へ、復旧点、失われる可能性のある期間、元に戻る可能性がある操作の種類を伝える。
7. 確認を受けると、CMS は、ワークスペースの状態の記録をワークスペースのデータに合わせて直し、保持期間を過ぎた保存回答と、アカウントが無いメンバーを削除し、所属の記録をメンバーに合わせて直し、送信を終えていないフォームの通知を送信失敗にし、復旧点で進行中だったスキーマの反映と適用の事前確認を失敗にする。これらを終えると、設置は稼働中になる。
8. 運営者は設置を起動する。CMS は、取得、フォーム受付、通知、管理画面の利用を再開する。手順 7 の前に起動していた設置は、起動し直さずに、利用の再開の完了から利用者の要求を受け付ける。
9. 再開後、各ワークスペースのメンバーが、必要な操作を管理画面でやり直す。CMS は自動で再適用しない。
   - 復旧で元に戻ったメンバーの解除と権限の縮小は、メンバー管理の権限を持つメンバーがやり直す
   - 復旧で元に戻ったトークンの失効は、アプリ連携の権限を持つメンバーがやり直す
   - 復旧で元に戻った個別の削除は、コンテンツでは削除権限、回答では回答の削除権限、メディアでは編集権限またはメディア公開権限を持つメンバーがやり直す
   - 送信失敗として示された通知は、回答が保持されている場合に、通知設定の権限を持つメンバーが重複送信の可能性を確認して手動で再試行する。CMS は自動で再送しない
   - 復旧点以降に適用した移行は、開発者が適用状況を確認して適用し直す
   - 誤って公開した操作から復旧した場合は、公開権限とメディア公開権限を持つメンバーが、コンテンツの公開状態とメディアの公開範囲が復旧点の状態に戻ったことを確かめる
   - 表示アプリは、復旧点より後の公開内容の変更を反映したまま残る。CMS は、復旧を表示アプリへ通知しない。開発者は、表示アプリのキャッシュと生成済みのページを、公開取得で全体を取り直す。変更の順序を判別する情報は、復旧点の続きから始まる。開発者は、表示アプリが処理済みとして記録した、変更の順序を判別する情報を捨てる（APP-11）
10. 削除されたメンバーだった人は、メンバー管理の権限を持つメンバーの招待を受けて、参加し直す（WS-01）。
11. 所有者を失ったワークスペースは、再開の後も利用を続けられる。表示アプリの取得、フォームの受付、通知、残るメンバーの利用は止まらない。多要素認証の必須などのワークスペースの設定は変わらない。所有者だけが行える操作（`spec/scenario/index.md` の「権限」）は、新しい所有者が決まるまで行えない。運営者は、再開の後に、そのワークスペースの初期所有者の招待を発行し直す（HOST-04）。招待を受けた人が所有者になる。その人が既にメンバーでもよい。復旧点で初期所有者がまだ参加していなかったワークスペースと、利用の再開が利用できる状態にしたワークスペースも、同じ扱いになる。後者の招待は届いていない。運営者は、状態確認（HOST-06）で、初期所有者の招待が有効かどうかを確かめる。

### 異常系

- **入力エラー（使えないバックアップの指定）**: 整合性の確認に失敗したバックアップと、設置の版に対応しないバックアップでは、CMS は復旧を実行せず、理由を示す。設置の版に対応しないバックアップは、データの版が、実行する CMS が扱うデータの版と違うバックアップを指す。設置のデータは変わらない。運営者は、バックアップの一覧で別のバックアップを選ぶか、CMS をそのバックアップのデータの版の CMS に入れ替えて実行し直す。
- **秘密情報の復旧条件を満たさない**: CMS は復旧を実行せず、不足する秘密情報を示す。運営者は秘密情報を用意して実行し直す。
- **復旧の失敗・中断**: CMS は失敗と理由を示し、復旧を完了と扱わない。設置は復旧の失敗の状態になり、利用再開前にならず、利用を再開できない。失敗・中断した復旧は、設置のデータを途中まで置き換えていることがある。運営者は復旧を実行し直す。同じバックアップでも、別のバックアップでもやり直せる。実行し直した復旧は、前の復旧がどこで止まっていても、設置全体のデータを指定したバックアップの内容に置き換える。CMS が失敗を示した復旧は、原因を解消して、すぐに実行し直す。結果が分からないまま中断した復旧と、CMS が復旧の完了を記録できなかった復旧は、復旧の開始から、復旧を進行中として扱う時間（APP-12）が過ぎて、設置が復旧の失敗になった後に実行し直す。
- **復旧の進行中の設置への復旧の開始**: 結果を示していない復旧を、CMS は、復旧の開始から、復旧を進行中として扱う時間（APP-12）が過ぎるまで進行中として扱う。復旧は、その時間の内に、成功するか失敗する。その間の復旧の開始を、CMS は始めず、復旧の進行中であることと、始め直せる時期を示す。運営者は、復旧を実行しなくても、設置の起動の結果で、復旧が進行中か失敗かと、始め直せる時期を確かめられる。復旧を同時に開始した場合も、一方だけが始まる。その時間が過ぎても結果を示していない復旧を、CMS は中断した復旧として扱う。設置は復旧の失敗になり、次の復旧の開始を受け付ける。
- **時間内に終わらない復旧**: データの置き換えを、復旧のデータの置き換えを打ち切る時間（APP-12）の内に終えられない復旧を、CMS は打ち切り、時間内に終えられなかったことを理由とする失敗として示す。運営者は、すぐに復旧を実行し直せる。実行し直しても終えられない場合、運営者は、復旧前の確認が示すバックアップの大きさと、運用条件が示す上限を比べ、運用条件が示す資源を用意して実行し直す。運営者は、HOST-07 の復旧の動作の確認で、運用中の設置の大きさのバックアップを時間内に復旧できることを、障害の前に確かめる。
- **復旧点で作成の途中だったワークスペース**: 利用の再開の後の扱いは、復旧点でワークスペースのデータまで作り終えていたかどうかで分かれる。ワークスペースのデータまで作り終えていなかったものは、作成の途中のまま残る。CMS は、作成を自動で進めない。運営者は、状態確認（HOST-06）で対象の ID を確かめ、その ID で作成を実行し直すか（HOST-04）、利用終了を一回実行する（HOST-09）。ワークスペースのデータまで作り終えていたものは、利用の再開が利用できる状態にし、所有者がいないワークスペースになる。招待は届いていないので、運営者は初期所有者の招待を発行し直す（HOST-04）。
- **利用の再開の失敗・中断**: 手順 7 の処理を終えられなかった再開を、CMS は完了と扱わない。設置は利用再開前のまま残り、利用者の要求を受け付けない。CMS は、残っている処理の種類ごとの残件数を示す。運営者は利用の再開を実行し直す。実行し直した再開も手順 5 の確認を求め、済んだ分をやり直さずに、残りを進める。実行し直しても残件数が減らない場合、運営者は、残っている処理の種類ごとの残件数で確かめ、保存先の障害を解消する。解消できなければ、復旧をやり直す。保存先を使えない場合は、空の保存先を用意してから復旧する。
- **復旧の後に CMS を入れ替えた**: 実行する CMS が扱うデータの版が、復旧したデータの版と違う場合、CMS は利用の再開を受け付けず、CMS を復旧したデータの版の CMS に合わせることを示す。運営者は、CMS を復旧したデータの版の CMS に戻して実行し直す。新しい版へは、利用の再開の後に HOST-05 で更新する。
- **保存基盤全体の喪失**: 現在の状態のバックアップを取得できない。復旧点より後の受付、回答、編集は失われる。CMS は復旧前の確認と利用再開前の確認で、失われる可能性のある期間を示す。運営者は、空の保存先を用意し、バックアップの一覧で復旧に使うバックアップを選んで、復旧を実行する（「設置の状態」）。
- **一部のワークスペースだけの復旧**: 復旧は設置全体を単位とする。一つのワークスペースだけを戻す復旧は行えない。移行やデータを失い得る操作で失った値・項目・コンテンツを戻す場合も、設置全体を復旧点へ戻す。運営者は、ほかのワークスペースが失う期間を確認してから実行する。
- **権限不足**: 設置の運用権限を持たない人は、復旧と利用の再開を行えない。メンバーは、役割と権限によらず復旧を実行できない。所有者は運営者へ復旧を依頼する。
- **リソース不在**: 指定したバックアップが存在しない場合、CMS は存在しないことを示す。運営者は、バックアップの一覧で ID を確かめて指定し直す。復旧に使えるバックアップが一つもない場合、復旧は行えない。
- **操作の取り消し**: 復旧前の確認でやめた場合と、対話できない環境で確認の指定を添えずに実行した場合、CMS は復旧せず、設置のデータは変わらない。運営者は設置を起動し直して利用を続ける。復旧の実行後は取り消せない。復旧前の状態へ戻す場合は、手順 1 で取得したバックアップから復旧をやり直す。利用の再開の確認でやめた場合と、対話できない環境で確認の指定を添えずに実行した場合、CMS は再開せず、設置は利用再開前のまま残る。

## HOST-09 特定のワークスペースの利用を終了する

- **利用者**: ホスティング運営者
- **目的**: 一つのワークスペースの配信・受付・通知を終了し、そのデータを消去する。ほかのワークスペースに影響を与えない。
- **要件**: 1, 7.2, 9.1, 10.1

### 正常系

1. 運営者は、終了するワークスペースの所有者と、終了の時期と対象を確かめる。
2. 運営者は運用コマンドで、ワークスペースを指定して終了前の確認を実行する。作成の途中のワークスペース（HOST-04）も指定できる。CMS はデータを変更せずに次を示す。
   - 未完了の通知。フォームの通知の未送信の件数と未対処の送信失敗の件数、表示アプリへの通知の送信待ちの件数と未対処の送信失敗の件数
   - 失われるデータ。スキーマ、コンテンツ、履歴、メディア、回答、削除済みフォームの回答、運用設定、メンバーとアクセス権、トークン、操作履歴
   - 消去する資格情報。そのワークスペースのトークンと運用設定の秘密情報
   - CMS の通常データの外に残る情報。取得済みのバックアップには、バックアップの削除期限まで残る。外部のメール送信環境、受信箱、表示アプリに渡した内容は CMS から消去できない
3. 必要な通知を届ける場合は、通知設定の権限を持つメンバーが終了の前に手動で再試行する。
4. 運営者は対象のワークスペースの名称を入力して、終了を実行する。
5. CMS はそのワークスペースの配信・受付・通知を終了する。終了の実行を受け付けた時点から、消去の進み具合によらず、そのワークスペースのトークンによる要求、公開のメディアの配信、プレビューを拒否し、フォームの送信を受け付けない。未送信のフォームの通知と、送信待ちの表示アプリへの通知を送らない。メンバーはそのワークスペースを利用できなくなる。トークンによる要求は、ワークスペースを利用できないことを理由に拒否する。消去の完了の後も同じである。ただし、初期構成で宣言したトークン（HOST-02）の値による要求は、消去の完了の後は、CMS がその値を知らないので、無効なトークンとして拒否する。
6. CMS は保存データ、回答、メディア、資格情報と、そのワークスペースへの所属の消去を進める。終了の実行は、消去の完了を待たず、結果に消去の進行中であることを示す。運営者は終了を一回実行する。残りの消去は、進行中の処理（メディアの登録と派生形式の生成）が残した対象を含めて、CMS が自動で進める。利用終了は、消去の完了で完了する。運営者は、状態確認（HOST-06）で完了を確かめる。そのワークスペースへの所属が消えて、どのワークスペースにも所属しなくなった人のアカウントは、AUTH-05 の「所属するワークスペースが無い」に従う。ほかのワークスペースのデータ、設定、トークン、所属は変えない。

### 異常系

- **入力エラー（名称の不一致）**: 入力した名称が対象のワークスペースと一致しない場合、CMS は終了を実行しない。データは変わらない。運営者は対象を確かめて入力し直す。
- **消去の失敗・中断**: CMS は消去を完了と示さない。配信・受付・通知は終了したまま再開しない。途中で止まった消去は、CMS が自動で続きを進める。終了の実行の直後に止まった場合も同じで、そのワークスペースは状態確認に利用終了の途中として現れる。運営者は、状態確認（HOST-06）で、消去が進行中であることと、完了したことを確かめる。利用終了の途中のワークスペースへ終了を実行し直した場合も、CMS は同じ消去の続きを進め、消去の進行中であることを示す。
- **権限不足**: 設置の運用権限を持たない人は実行できない。メンバーは、役割と権限によらず、管理画面でワークスペースを削除できない。所有者は運営者へ終了を依頼する。
- **作成の途中のワークスペース**: 作成の途中のワークスペース（HOST-04）も、作成を実行し直さずに、終了を一回実行して終了できる。CMS は、作成済みの分を消去する。招待は発行しない。
- **リソース不在**: 存在しないワークスペースと、消去が完了したワークスペースを指定すると、CMS は対象が存在しないことを示す。ほかのワークスペースは変わらない。
- **操作の取り消し**: 終了前の確認の後に実行をやめると、ワークスペースは変わらない。終了の実行後は取り消せない。消去したデータを戻す手段は、設置全体のバックアップからの復旧（HOST-08）に限る。復旧はすべてのワークスペースを復旧点へ戻す。

## HOST-10 設置全体の利用を終了する

- **利用者**: ホスティング運営者
- **目的**: 設置全体の配信・受付・通知を終了し、保存データ、メディア、資格情報、バックアップを整理する。
- **要件**: 7.2, 9.1, 10.1

### 正常系

1. 運営者は運用コマンドで、設置全体の終了前の確認を実行する。CMS はデータを変更せずに、ワークスペースごとの未完了の通知と失われるデータを示す。作成の途中のワークスペースと、利用終了の途中のワークスペースも含める。示す内容は HOST-09 の手順 2 と同じとする。
2. 運営者は各ワークスペースの所有者へ、終了の時期と失われるデータを伝える。必要な通知を届ける場合は、通知設定の権限を持つメンバーが終了の前に手動で再試行する。
3. 運営者は設置を停止する。すべてのワークスペースの配信・受付・通知が終了する。未送信の通知は送らない。
4. 運営者は終了手順に沿って、データとメディアの保存先、復旧の記録、設置の設定と初期構成に含む資格情報を消去する。
5. 運営者はバックアップを整理する。保持・削除期限に従って残すバックアップと、削除するバックアップを決め、保管先から削除する。残すバックアップには保存回答と秘密情報が残る。
6. 運営者は、CMS の外に残る情報を所有者へ説明する。外部のメール送信環境、受信箱、表示アプリに渡した内容は、CMS の終了では消去されない。

### 異常系

- **保存先の消去の失敗**: 運営者は終了手順に沿って、残っている保存先と復旧の記録を確かめて消去し直す。消去が終わるまで、終了を完了と扱わない。
- **権限不足**: 設置の運用権限を持たない人は、設置の停止、保存先の消去、バックアップの削除を行えない。
- **リソース不在**: ワークスペースのない設置では、終了前の確認は失われるデータがないことを示す。運営者は手順 3 以降を行う。
- **操作の取り消し**: 保存先を消去する前は、設置を起動し直すと、停止前の状態で利用を再開する。初期構成は読み込まない。保存先を消去した後は、残したバックアップから HOST-08 で復旧する場合に限り、復旧点の状態へ戻せる。バックアップも削除した後は戻せない。

## HOST-11 外部メールを使えない設置で、管理者のアクセスを復旧する

- **利用者**: ホスティング運営者
- **目的**: メールによるアクセス回復を使えない設置で、ログインできなくなった人が管理画面を再び利用できるようにする。対象は設置の任意のアカウントとし、役割と権限によらない。
- **要件**: 2, 3.1, 9.2

### 正常系

1. ログインできなくなった人は、運営者へ復旧を依頼する。
2. 運営者は、依頼した人が本人であることを CMS の外で確かめる。
3. 運営者は運用コマンドで、対象のメールアドレスを指定して管理者復旧を実行する。
4. CMS は、一度だけ使える回復用の URL を有効期限付きで発行し、運用コマンドの結果に示す。対象の資格情報は、この時点では変えない。
5. 運営者は回復用の URL を CMS の外で本人へ渡す。
6. 本人は回復用の URL を開き、AUTH-04 の手順 4 以降で新しいパスワードを設定する。所属するワークスペースと権限は変わらない。
7. 本人は、AUTH-04 の手順 7 のとおり、管理画面の利用を始める。

### 異常系

- **入力エラー**: メールアドレスの形式が誤っている場合、CMS は管理者復旧を実行せず、理由を示す。運営者はメールアドレスを直して実行し直す。
- **回復用の URL の期限切れ・使用済み**: 期限を過ぎた URL と使用済みの URL では回復できない。運営者は管理者復旧を実行し直す。実行し直すと、前の URL は失効する。
- **権限不足**: 設置の運用権限を持たない人は管理者復旧を実行できない。管理者復旧は、運営者にワークスペースの権限を与えない。
- **リソース不在**: 指定したメールアドレスのアカウントが設置にない場合、CMS は回復用の URL を発行せず、理由を示す。運営者はメールアドレスを確かめる。アカウントを持たない人は、メンバー管理の権限を持つメンバーの招待を受けて参加する。
- **操作の取り消し**: 誤った対象へ発行した場合、運営者は URL を渡さずに有効期限を待つ。使われなかった URL は対象の資格情報を変えない。正しい対象には、管理者復旧を実行し直す。
