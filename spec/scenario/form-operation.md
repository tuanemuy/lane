# フォームの運用

通知設定の権限、受付管理の権限、回答の閲覧権限、回答の削除権限を持つメンバーが、フォームの受付と通知を設定し、回答と通知の結果を扱う。用語は `spec/requirements.md` の 1 章に従う。「要件」は `spec/requirements.md` の節番号を指す。

## 共通の規則

`spec/scenario/index.md` の「権限」「共通の規則」に加えて、このカテゴリーの全シナリオに適用する。

- フォームはスキーマの反映で作られる。管理画面ではフォームの項目を定義しない。
- スキーマの反映で作られたフォームは、受付停止で作成する。初期構成で受付中と宣言したフォームだけは、受付中で作成する（HOST-02、HOST-03）。
- フォームの送信制限は、迷惑送信を抑えるために CMS が定める固定の規則で、フォームごとの送信の頻度を制限する。値は APP-12 が定める。運用設定ではなく、メンバーも送信も変更できない。達した送信の結果は APP-08 が定める。
- 通知先、通知定義、受付状態、回答の保持方針は、フォームに紐付く運用設定である。スキーマの再反映とフォームの表示名称の変更では変わらない。キーを変えたフォームは別のフォームとして扱い、運用設定を引き継がない。
- 送信接続設定はワークスペースに一つあり、全フォームが使う。
- 受付完了とした回答の通知は、設置の通常の停止・再起動をまたいで送る。停止中に送らなかった通知は、起動の後に送る。停止・再起動と処理のやり直しを理由に、送信成功を確認済みの宛先へ送り直さない。
- 回答の一覧と回答の閲覧は、回答と通知に共通で、メンバーが持つ権限に応じて示す内容と操作を出し分ける。受付日時とフォームは、どの権限のメンバーにも示す。回答の入力内容と一覧表示用の項目の値は、回答の閲覧権限または回答の削除権限を持つメンバーにだけ示す。通知の送信結果、失敗の理由、宛先は、通知設定の権限を持つメンバーにだけ示す。
- このカテゴリーの操作は管理画面でだけ行う。トークンでは行えない。

## FORM-01 送信接続設定を登録・更新し、動作を確認する

- **利用者**: 通知設定の権限を持つメンバー
- **目的**: ワークスペースの通知メールを、既存のメール送信環境から送れる状態にする。
- **要件**: 3.1, 8.1, 8.3, 9.1, 9.2

### 正常系

1. メンバーが送信接続設定を開く。CMS は、登録済みの接続先と接続条件を示す。接続条件は、メール送信環境が送信に求める項目で、送信者のアドレスを含む。認証情報の示し方は、`spec/scenario/index.md` の「秘密情報」に従う。
2. メンバーが、接続先、認証情報、接続条件を入力する。更新で認証情報を入力しなかった場合、CMS は登録済みの認証情報を使い続ける。
3. メンバーが、試験メールの宛先を指定して動作確認を実行する。CMS は、入力中の設定で試験メールを送り、メール送信基盤が受理したか、失敗した理由を示す。試験メールは回答の入力内容を含まない。
4. CMS は、受理が受信箱への到着を意味しないことを示す。メンバーは、試験メールの到着を受信箱で確かめる。
5. メンバーが保存する。更新の場合、CMS は影響するフォームを示して確認を求める。影響するフォームは、受付中のフォームと、未送信または送信失敗の通知が残るフォームで、削除済みフォームを含む。
6. メンバーが確認すると、CMS は設定を保存する。未送信の通知と、以後の手動再試行は、保存後の設定で送る。送信中の通知は、保存前の設定で送り終える。
7. 保存済みの回答、受付時の通知定義、回答の保持方針は変わらない。
8. CMS は、変更を操作履歴に残す。認証情報の値は操作履歴に残さない。

### 異常系

- 入力エラー: 接続に必要な項目が欠けている、または形式が正しくない場合、CMS は保存を拒否し、項目と理由を示す。接続条件は 1 個以上を必要とし、送信者のアドレスを必ず含む。入力は画面に残る。メンバーは項目を直して保存する。
- 動作確認の失敗: CMS は、接続できない、認証を拒否された、宛先を拒否されたなどの理由を示す。登録済みの設定は変わらない。メンバーは入力を直して動作確認をやり直す。動作確認の結果は保存の条件にしない。
- 使えない状態にする変更: 登録した送信接続設定は、更新で変える。接続先を空にする更新、接続条件を 0 個にする更新、接続条件から送信者のアドレスを除く更新を、CMS は受付中のフォームの有無によらず入力エラーとして拒否し、項目と理由を示す。メンバーは値を入力して保存する。認証情報は空にできない。認証情報の入力欄を空のまま保存した場合は、手順 2 のとおり登録済みの認証情報を使い続ける。
- リソース不在: 送信接続設定が未登録の間、CMS は FORM-05 の受付の有効化を拒否する。メンバーはこのシナリオで設定を登録する。
- 操作の取り消し: 保存前に編集をやめると、登録済みの設定は変わらない。保存した設定を元に戻すには、以前の値を入力して保存し直す。認証情報は表示されないため、メンバーが手元の値を入力する。送った試験メールは取り消せない。

## FORM-02 フォームの通知先を管理する

- **利用者**: 通知設定の権限を持つメンバー
- **目的**: フォームごとに、回答の通知を受け取る宛先を決める。
- **要件**: 3.1, 8.1, 8.3, 9.1, 9.2

### 正常系

1. メンバーがフォームを選び、通知先を開く。CMS は、通知先ごとにメールアドレスと、有効か無効かを示す。
2. メンバーが、メールアドレスを入力して通知先を追加する。追加した通知先は有効になる。
3. メンバーが、通知先のメールアドレスを修正する、通知先を無効または有効にする、通知先を削除する。
4. CMS は変更を保存する。以後に受け付ける送信は、受付時に有効なすべての通知先を通知対象とする。回答の内容に応じた振り分けは行わない。
5. 受付済みの回答への影響は次のとおりである。
   - 外した宛先（無効にした通知先、削除した通知先、修正前のメールアドレス）には、以後の通知も手動再試行も送らない。
   - 追加した通知先と修正後のメールアドレスは、FORM-10 の手動再試行の宛先に含まれる。
6. CMS は、変更を操作履歴に残す。

初期構成で宣言した通知先と通知定義のうち、指定したキーのフォームがまだスキーマにないものは、紐付けを待つ運用設定としてフォームの一覧に示す（HOST-03）。

### 異常系

- 入力エラー: メールアドレスの形式が正しくない場合と、同じフォームに同じメールアドレスが既にある場合、CMS は保存を拒否し、理由を示す。メンバーは入力を直す。CMS は形式だけを検証し、宛先への到達を確かめない。
- 入力エラー（通知先の上限）: 一つのフォームに登録できる通知先の件数には、上限（APP-12）がある。上限に達したフォームへの追加を、CMS は拒否し、上限を示す。メンバーは、不要な通知先を削除してから追加する。
- 有効な通知先をなくす変更: 受付中のフォームで、有効な通知先がゼロになる無効化と削除を CMS は拒否する。CMS は、対象のフォームと、受付中のフォームには有効な通知先が一件以上必要であることを示す。メンバーは、別の通知先を先に追加するか、FORM-05 で受付を停止してから変更する。
- リソース不在: 操作の前にスキーマの反映でフォームが削除された場合、CMS はそのフォームを削除済みフォームとして示す。通知先の扱いは FORM-11 に従う。他のメンバーが先に削除した通知先への操作は、確定せず、存在しない対象（`spec/scenario/index.md` の「共通の規則」）になる。
- 操作の取り消し: 保存前にやめると通知先は変わらない。削除した通知先は、同じメールアドレスを追加して戻す。外していた間に受け付けた送信の最初の通知は、その宛先へ送られていない。

## FORM-03 通知定義を編集し、入力例による表示を確認する

- **利用者**: 通知設定の権限を持つメンバー
- **目的**: 通知メールの件名、本文、送信者の表示名、返信先を、フォームの項目に合わせて決める。
- **要件**: 3.1, 8.3, 9.1, 9.2

### 正常系

1. メンバーがフォームを選び、通知定義を開く。CMS は、現在の件名、本文、送信者の表示名、返信先を示す。新規フォームの通知定義は、件名にフォームの表示名称、本文に全項目の一覧と受付日時を持つ。
2. メンバーが、件名と本文に文章を書き、現行のフォームの項目から選んで参照を入れる。選べる参照は次のとおりである。
   - 回答の項目の値。単一選択と複数選択は選択肢の表示名称で表し、複数選択は列挙する。
   - 回答の全項目の一覧。受付時のフォームの項目を、表示名称と順序に従って列挙する。
   - 未入力の項目の出し分け。項目が未入力の場合に、その部分を出さない。
   - 問い合わせ対象の送信時の情報。モデルのキー、コンテンツID、表示名称、一意な値。
   - 受付日時。
3. メンバーが返信先を決める。現行のフォームのメールアドレス形式の項目から選ぶか、指定しない。CMS は、項目の値が形式の検証だけを経ていて、送信者がその連絡先を所有することと、連絡先へ到達できることを保証しないことを示す。
4. メンバーが、入力例による表示を確認する。CMS は、スキーマの入力例を各項目の値として当てはめた件名、本文、返信先を示す。入力例を持たない項目は未入力として表示する。
5. メンバーが保存する。CMS は、保存後に受け付ける送信へ新しい通知定義を適用する。受付済みの回答の通知と手動再試行は、受付時の通知定義のままとする。
6. CMS は、変更を操作履歴に残す。

### 異常系

- 入力エラー: 件名または本文が空の場合、CMS は保存を拒否し、項目と理由を示す。メンバーは入力して保存する。
- 参照できない項目: CMS は、現行のフォームにない項目と、用途に合わない型の項目を選択肢に示さない。返信先には、メールアドレス形式でない項目を示さない。選択肢にない参照を含む通知定義の保存は拒否し、該当する参照と理由を示す。メンバーは項目を選び直す。
- 編集中のスキーマの反映: 編集中に反映で項目がなくなった、または型が変わった場合、CMS は保存時に該当する参照と理由を示し、保存しない。入力は画面に残る。メンバーは参照を選び直すか取り除いて保存する。
- リソース不在: 編集中にスキーマの反映でフォームが削除された場合、CMS は保存を拒否し、フォームが削除済みであることを示す。削除済みフォームの通知定義は編集できない。
- 操作の取り消し: 保存前にやめると通知定義は変わらない。保存した通知定義を戻すには、編集し直して保存する。その間に受け付けた送信は、受付時の通知定義で通知する。

## FORM-04 通知定義の参照の不整合に気付き、修正する

- **利用者**: 通知設定の権限を持つメンバー
- **目的**: スキーマの反映で壊れた通知定義の参照を見つけ、通知メールを意図した内容に戻す。
- **要件**: 3.1, 6.5, 8.3, 9.1

### 正常系

1. 開発者がフォームの項目を削除する、項目のキーを変える、項目の型を変えるスキーマを反映する。CMS は通知定義の参照を理由に反映を拒否せず、通知定義を自動で補正も削除もしない。
2. メンバーが管理画面を利用すると、CMS は、参照の不整合が残る通知定義があることと、対象のフォームを示す。
3. メンバーが対象のフォームの通知定義を開く。CMS は、不整合のある参照ごとに、参照するキーと理由を示す。理由は、項目が現行のフォームにない、または項目の型が用途に合わない、のいずれかである。
4. メンバーが、不整合のある参照を現行の項目へ選び直すか、取り除く。入力例による表示で結果を確かめ、保存する。
5. CMS は、保存後に受け付ける送信へ修正後の通知定義を適用する。不整合のある通知定義が残らなくなると、手順 2 の表示を消す。

不整合が残る間も、フォームの受付と通知は続く。通知メールは、不整合のある参照を、値の代わりに不整合と分かる表示で示す。返信先の参照が不整合の場合は、返信先を指定せずに送る。不整合の間に受け付けた回答の通知と手動再試行は、受付時の通知定義のまま送る。

### 異常系

- 入力エラー: 不整合のある参照を一つでも残した保存を、CMS は拒否し、残る参照と理由を示す。メンバーは、すべての参照を選び直すか取り除いて保存する。
- 権限不足: 不整合が残ることの表示は、通知設定の権限を持つメンバーにだけ示す。
- リソース不在: 修正の途中で別の反映が行われ、新たな不整合が生じた場合、CMS は保存時に該当する参照と理由を示す。メンバーは追加で修正する。対象のフォームが削除された場合、CMS はそのフォームを不整合の表示から外す。
- 操作の取り消し: 保存前にやめると、通知定義も不整合の表示も変わらない。

## FORM-05 フォームの受付を有効・停止にする

- **利用者**: 受付管理の権限を持つメンバー
- **目的**: 通知と保持の設定を確かめてから受付を始め、必要なときに受付を止める。
- **要件**: 3.1, 6.5, 8.1, 8.3, 9.1

### 正常系

受付を有効にする。

1. メンバーがフォームの一覧を開く。CMS は、フォームごとに受付中か受付停止かを示す。作られた時点の受付状態は、「共通の規則」に従う。
2. メンバーが、受付停止のフォームで受付を有効にする操作を行う。CMS は、有効な通知先の件数、送信接続設定の登録の有無、回答の保持方針を示す。通知先のメールアドレスと送信接続設定の接続先は示さない。通知定義に参照の不整合がある場合は、不整合があることを示す。
3. メンバーが内容を確かめて確定する。CMS はフォームを受付中にし、以後の送信を受け付ける。

受付を停止する。

1. メンバーが、受付中のフォームで受付を停止する操作を行う。CMS は、以後の送信が受付停止を理由とする受付失敗になることと、保存済みの回答と未送信の通知を取り消さないことを示す。
2. メンバーが確定する。CMS はフォームを受付停止にする。保存済みの回答は残り、未送信の通知は送られる。

初期構成で宣言した受付状態と回答の保持方針のうち、指定したキーのフォームがまだスキーマにないものは、紐付けを待つ運用設定としてフォームの一覧に示す（HOST-03）。

### 異常系

- 有効な通知先がない: 有効な通知先がゼロのフォームの有効化を、CMS は拒否し、理由を示す。通知設定の権限も持つメンバーは、そのフォームの通知先を追加して（FORM-02）、有効にする。通知設定の権限を持たないメンバーは、通知設定の権限を持つメンバーに通知先の追加を依頼し、追加の後に有効にする。
- 送信接続設定がない: 送信接続設定が未登録の場合、CMS は有効化を拒否し、理由を示す。通知設定の権限も持つメンバーは、送信接続設定を登録して（FORM-01）、有効にする。通知設定の権限を持たないメンバーは、通知設定の権限を持つメンバーに登録を依頼し、登録の後に有効にする。
- 確認の後の変化: 受付の有効化が確認の後の変化として挙げるのは、確定の時点の有効な通知先と送信接続設定である。確定の時点で有効な通知先または送信接続設定が無ければ、上の二つの拒否になる。
- 通知定義の参照の不整合: 不整合は有効化を妨げない。メンバーは、そのまま有効にするか、FORM-04 で修正してから有効にする。通知設定の権限を持たないメンバーは、通知設定の権限を持つメンバーに修正を依頼する。
- 権限不足: 通知先、通知定義、送信接続設定の中身の確認と修正には、通知設定の権限が要る。通知設定の権限を持たないメンバーには、有効な通知先の件数、送信接続設定の登録の有無、参照の不整合の有無だけを示す。
- リソース不在: 操作の前にスキーマの反映でフォームが削除された場合、CMS は操作を拒否し、フォームが削除済みで受付が終了していることを示す。他のメンバーが先に同じ状態へ変えていた場合、CMS は現在の受付状態を示す。
- 操作の取り消し: 有効にした受付を戻すには停止し、停止した受付を戻すには有効にする。その間に受け付けた回答と、受付失敗を返した送信は変わらない。

## FORM-06 回答の保持方針を変更し、既存の回答へ適用する

- **利用者**: 受付管理の権限を持つメンバー
- **目的**: フォームの回答を保持する期間を決め、必要な場合は既存の回答にも同じ期間を適用する。
- **要件**: 3.1, 7.2, 8.2, 9.1, 9.2

### 正常系

保持方針を変更する。

1. メンバーがフォームを選び、回答の保持方針を開く。CMS は、現在の保持方針を示す。保持方針は、回答を受付日時から保持する期間である。コンテンツの履歴とごみ箱の保持方針とは別に持つ。
2. メンバーが新しい保持期間を入力する。CMS は次を示す。
   - 新しい保持方針は、保存後に受け付ける回答に適用する。
   - 既存の回答は、受付時の保持方針のままである。
   - 保持期間を過ぎた回答は自動整理で削除し、復元できない。削除した回答からは通知も手動再試行も行えない。
   - バックアップと、メール送信環境や受信箱に残る情報は、この保持方針の対象でない。
3. メンバーは、既存の回答にも新しい保持方針を適用するかを選べる。選んだ場合、CMS は同じ確認で、「既存の回答へ適用する」の手順 2 の内容を示す。
4. メンバーが保存する。CMS は保持方針を保存し、変更を操作履歴に残す。既存の回答への適用を選んだ場合は、続けて「既存の回答へ適用する」の手順 3 を行う。

既存の回答へ適用する。保持方針を変えずに、現在の保持方針の適用だけを行う場合も、この手順で行う。

1. メンバーが、現在の保持方針を既存の回答へ適用する操作を行う。適用範囲は、そのフォームの既存の回答すべてである。
2. CMS は、適用範囲の回答の件数と受付期間、適用で保持期限が変わる回答の件数、適用後に保持期間を過ぎていて次の自動整理で削除する回答の件数を示し、確認を求める。
3. メンバーが確定する。CMS は、適用範囲の回答の保持方針を現在の保持方針に置き換える。適用は、件数によらず、一部の回答ずつ置き換えて進める（`index.md` の「複数の対象を扱う操作」の外にある）。途中で止まった場合、それまでに置き換えた回答は置き換えたまま残る。保持期間を過ぎた回答は、自動整理で削除する。

通知の成功、失敗、再試行は、回答の保持期間を変えない。送信失敗の通知が残る回答も、保持期間を過ぎると削除する。

### 異常系

- 入力エラー: 指定できる範囲（APP-12）の外の保持期間を入力した場合、CMS は保存を拒否し、指定できる範囲を示す。メンバーは値を直す。
- リソース不在: スキーマの反映でフォームが削除された場合、CMS は保持方針の変更と適用を拒否し、フォームが削除済みであることを示す。削除済みフォームの回答は、受付時の保持方針で保持する。早く削除する場合は FORM-11 で削除する。
- 適用の途中での保持方針の変更: 既存の回答への適用が確認の後の変化として挙げるのは、そのフォームの保持方針である。確認の後、適用が終わるまでに、ほかのメンバーがそのフォームの保持方針を変えた場合、CMS は適用を止め、保持方針が変わったことを示す。確認していない保持方針を既存の回答へ適用しない。止めるまでに置き換えた回答は、確認した保持方針を持つ。メンバーは、現在の保持方針で適用範囲と削除する件数を確認し直して、適用する。
- 保存の後の適用の失敗: 保持方針を保存した後に、既存の回答への適用が終わらなかった場合、保持方針は保存したままで、適用が止まるまでに置き換えた回答のほかは変わらない。CMS は、適用を終えられなかったことを示す。メンバーは「既存の回答へ適用する」で適用し直す。
- 操作の取り消し: 保存前にやめると保持方針は変わらない。適用後に元の保持期間へ戻すには、保持方針を変更し直して再び適用する。自動整理で削除した回答は戻らない。

## FORM-07 保存した回答を一覧・検索し、閲覧する

- **利用者**: 回答の閲覧権限を持つメンバー
- **目的**: 受け付けた回答を見つけ、送信時の内容を確かめる。
- **要件**: 8.1, 8.2, 9.1

### 正常系

1. メンバーが回答の一覧を開く。CMS は、回答を受付日時の新しい順に示す。各回答に、受付日時、フォーム、一覧表示用の項目の値を示す。一覧表示用の項目の値は、項目の型によらず、文字列で示す。通知設定の権限も持つメンバーには、通知の送信結果も示す。
2. メンバーが、フォーム、受付期間で絞り込む。通知設定の権限も持つメンバーは、通知の送信結果でも絞り込む。フォームの選択肢には、削除済みフォームを現行のフォームと区別して含む。
3. メンバーが、一覧表示用の項目の部分一致で検索する。CMS は、現行スキーマの一覧表示用の項目のキーと、各回答の受付時の項目のキーが一致する値を検索する。検索するのは、テキストの項目の値である。
4. メンバーが回答を開く。CMS は次を示す。
   - 受付時のフォームの項目を、受付時の表示名称と順序で示す。選択肢は受付時の表示名称で示す。
   - 送信者の入力内容。メールアドレスなどの連絡先の項目には、形式の検証だけを経た値であり、送信者がその連絡先を所有することと、連絡先へ到達できることを保証しないことを示す。
   - 受付日時。
   - 問い合わせ対象の送信時の情報。モデルのキー、コンテンツID、表示名称、一意な値。
5. 問い合わせ対象のコンテンツが現在もある場合、CMS は現在のコンテンツへのリンクを、送信時の情報と区別して示す。どのメンバーもコンテンツを閲覧できるため、リンクの表示に追加の権限は要らない。
6. 同じ送信者が再送した回答は、別々の回答として並ぶ。メンバーは、検索で同じ送信者の回答を並べ、重複を見分ける。不要な回答は、回答の削除権限を持つメンバーが FORM-08 で削除する。

回答は、フォームの変更と移行の後も、受付時の項目と入力内容のまま示す。

### 異常系

- 入力エラー: 受付期間の開始が終了より後の指定は、条件の誤り（`spec/scenario/index.md` の「一覧の絞り込み」）になる。
- 該当なし: `spec/scenario/index.md` の「一覧の絞り込み」に従う。
- キーが一致しない回答: 現行スキーマの一覧表示用の項目のキーを受付時に持たない回答は、一覧表示用の値を空で示し、検索に該当しない。テキストでない一覧表示用の項目の値は、一覧に示し、検索に該当しない。メンバーは、フォームと受付期間で絞り込んで見つける。
- 問い合わせ対象の変化: 問い合わせ対象のコンテンツが更新、公開取り消し、削除されていても、CMS は送信時の情報をそのまま示す。コンテンツが完全削除済みの場合は、現在のコンテンツへのリンクを示さない。
- 権限不足: 権限ごとに示す内容と操作は、「共通の規則」に従う。回答の閲覧権限と回答の削除権限を持たないメンバーには、一覧表示用の項目での検索を示さない。宛先ごとの結果と再試行は、通知設定の権限を持つメンバーが FORM-09 と FORM-10 で扱う。
- リソース不在: 開こうとした回答が、他のメンバーの削除または自動整理で既にない場合は、存在しない対象（`spec/scenario/index.md` の「共通の規則」）になる。

## FORM-08 回答を削除する

- **利用者**: 回答の削除権限を持つメンバー
- **目的**: 不要な回答、重複した回答、削除を求められた回答を、保持期間を待たずに消す。
- **要件**: 7.2, 8.2, 9.1

### 正常系

1. メンバーが、FORM-07 の一覧または回答の閲覧から、削除する回答を選ぶ。一覧では、複数の回答を選んで一度に削除できる。CMS は、選んだ回答の件数を示す。
2. CMS は次を示し、確認を求める。
   - 削除した回答は復元できない。
   - 削除後は、その回答の未送信の通知と手動再試行を開始しない。
   - 削除の時点で送信中の通知と、メール送信基盤が受理済みの通知は取り消せない。
   - バックアップと、メール送信環境や受信箱に残る情報は、この削除で消えない。
3. メンバーが確定する。CMS は、メンバーの回答の削除権限を確かめてから、選んだ回答のうち確定の時点で残っている回答を一括で削除する。既に無い回答は、削除済みとして結果に示し、`spec/scenario/index.md` の「複数の対象を扱う操作」の、条件を満たさない対象に当たらない。回答は一覧と検索に現れなくなる。通知のための入力内容も残さない。

### 異常系

- 権限不足: 必要な権限は `spec/scenario/index.md` の「権限」に従う。回答の閲覧権限だけを持つメンバーは、回答の削除権限を持つメンバーに削除を依頼する。
- リソース不在: 選んだ回答が、他のメンバーの削除または自動整理で既にない場合の扱いは、手順 3 に従う。選んだ回答がすべて既にない場合も同じである。メンバーは、選び直さない。
- 操作の取り消し: 確定した削除は取り消せない。

## FORM-09 通知の送信失敗に気付き、送信結果と失敗の理由を確認する

- **利用者**: 通知設定の権限を持つメンバー
- **目的**: 届いていない可能性のある通知を見つけ、何を直せば届けられるかを知る。
- **要件**: 8.2, 8.3, 9.1

### 正常系

1. 通知の送信が失敗する。自動の再試行は、`spec/scenario/index.md` の「未対処の失敗」に従う。回答は保存済みで、送信者への受付結果は受付完了のままである。
2. CMS は、`spec/scenario/index.md` の「未対処の失敗」のとおり、フォームの通知の未対処の失敗を示す。この表示は管理画面の中にあり、通知メールの送信経路を使わない。
3. メンバーが表示から、回答の一覧（FORM-07）を、未対処の送信失敗で絞り込んだ状態で開く。CMS は、回答を受付日時の新しい順に示す。回答ごとに、受付日時、フォーム、通知の送信結果を示す。送信結果と、未送信の内訳は、`spec/scenario/index.md` の「未対処の失敗」に従う。送信失敗の通知には、未対処か対処済みかを示す。メンバーは、フォーム、受付期間、送信結果、未対処・対処済みで絞り込む。未送信で絞り込むと、内訳によらず、未送信の通知をすべて含む。
4. メンバーが回答を開く。CMS は、宛先ごとにメール送信基盤の受理を確認できたかどうか、失敗の理由、必要な対処を示す。
5. 回答の入力内容と一覧表示用の項目の値は、「共通の規則」に従って、同じ一覧と同じ場面で示す（FORM-07）。
6. CMS は、送信失敗が通知の未着を意味しないことを示す。成功を確認できなかった宛先にも、通知が届いている場合がある。
7. メンバーは、理由に応じて対処する。
   - 宛先の誤りや拒否: FORM-02 で通知先を修正し、FORM-10 で再試行する。
   - 送信接続設定の誤りやメール送信基盤の障害: FORM-01 で設定を直す、または障害の解消を待ち、FORM-10 で再試行する。
   - 成功を確認できない: 受信箱で到着を確かめる。届いていなければ FORM-10 で再試行する。
   - 有効な宛先が残らない: FORM-02 で通知先を追加または有効にし、FORM-10 で再試行する。
8. 届いていることを確かめて再試行しない場合、メンバーは通知の送信失敗を対処済みとして記録する。回答の一覧では、送信失敗の通知を一件以上選び、一度に記録できる。回答を開いた場面では、その回答の通知を記録する。記録できるのは送信失敗の通知だけである。

未対処と対処済みの規則は、`spec/scenario/index.md` の「未対処の失敗」に従う。CMS は送信者に再送を求めない。

### 異常系

- 権限不足: 未対処の表示、通知の送信結果、宛先ごとの結果と失敗の理由を示す相手は、「共通の規則」に従う。通知設定の権限だけを持つメンバーが回答の内容を必要とする場合は、回答の閲覧権限または回答の削除権限を持つメンバーに FORM-07 での確認を依頼する。
- リソース不在: 削除または自動整理で既にない回答は、通知とともに一覧に現れない。開こうとした回答が既にない場合、CMS は対象がないことを示す。
- 選んだ後の変化: 確定するまでに再試行が始まっていた通知（`spec/scenario/index.md` の「未対処の失敗」の表）と、回答が既にない通知は、`spec/scenario/index.md` の「複数の対象を扱う操作」の、条件を満たさない対象に当たる。
- 操作の取り消し: 対処済みの記録の扱いは、`spec/scenario/index.md` の「未対処の失敗」に従う。

## FORM-10 送信に失敗した通知を、宛先を確認して手動で再試行する（複数の通知を含む）

- **利用者**: 通知設定の権限を持つメンバー
- **目的**: 保存済みの回答から、届いていない通知を現在の通知先へ送り直す。
- **要件**: 8.2, 8.3, 9.1, 10.2

### 正常系

1. メンバーが、FORM-09 の回答の一覧または回答の閲覧で、送信失敗の通知を選び、再試行の操作を行う。一覧では、複数の通知を選んで一度に再試行できる。
2. CMS は、選んだ通知の再試行の宛先（`spec/scenario/index.md` の「未対処の失敗」の手動再試行）を、通知ごとに一度に示す。
3. CMS は、受付時の通知対象との違いを併せて示す。受付後に外した宛先は「外れた宛先」、受付後に追加または修正した宛先は「加わった宛先」として示す。
4. CMS は、成功を確認できなかった宛先にも通知が届いている可能性があり、再試行で重複して届き得ることを示す。
5. メンバーが確定する。再試行を始めた通知の送信結果と未対処の扱いは、`spec/scenario/index.md` の「未対処の失敗」に従う。CMS は通知ごとに、保存済みの回答と受付時の通知定義から通知を作り、現在の送信接続設定で送る。回答は複製しない。
6. CMS は、通知ごとの結果を示す。すべての宛先でメール送信基盤の受理を確認できた通知は、送信結果が送信成功になる。送信の結果は通知ごとに決まり、ある通知の失敗はほかの通知の結果を変えない。
7. 再試行は、回答の保持期間を変えない。

バックアップからの復旧で送信済みか判断できなくなった通知は、送信失敗として現れる。メンバーは、重複して届く可能性を確かめ、同じ手順で再試行する。

### 異常系

- 宛先が残らない: 現在有効な通知先がない場合と、有効な通知先のすべてで送信成功を確認済みの場合、CMS は再試行を拒否し、理由を示す。メンバーは、FORM-02 で通知先を追加または有効にしてから再試行する。複数の通知を選んだ再試行では、CMS は確認の時点で宛先が残らない通知を示す。メンバーは、その通知を選択から外して確定する。
- 再試行の失敗: 一部の宛先だけが成功した場合と、成功を確認できない場合、CMS は宛先ごとの結果と理由を示す。メンバーは FORM-09 の対処を行い、再び再試行する。成功を確認した宛先は、次の再試行の宛先から外れる。
- 操作の繰り返し: メンバーが確定する再試行は、宛先を確認した時点（手順 2）の通知を対象とする。確認の後に、その通知の再試行が先に始まっていた場合の扱いは、`spec/scenario/index.md` の「未対処の失敗」の表に従う。先に始まった再試行が送信中でも、終わっていても同じである。同じ操作を誤って繰り返した場合、結果を受け取れずに操作し直した場合、ほかのメンバーが先に再試行した場合が当たる。メンバーは、結果が送信失敗であれば、宛先を確認し直して再試行する。
- 選んだ後の変化: 確認の後、確定するまでに宛先が残らなくなった通知は、`spec/scenario/index.md` の「複数の対象を扱う操作」の、条件を満たさない対象に当たる。再試行が先に始まっていた通知は「操作の繰り返し」、回答が既にない通知は「リソース不在」に従う。
- 対象外の通知: 送信結果が未送信または送信成功の通知は、再試行に選べない。
- 権限不足: 必要な権限は `spec/scenario/index.md` の「権限」に従う。回答の閲覧権限または回答の削除権限だけを持つメンバーは、通知設定の権限を持つメンバーに再試行を依頼する。
- リソース不在: 回答が削除または自動整理で既にない場合、CMS は再試行を開始せず、回答が存在しないことを示す。確認から確定までに回答が削除された場合も同じである。複数の通知を選んだ再試行では、回答が既にない通知は、`spec/scenario/index.md` の「複数の対象を扱う操作」の、条件を満たさない対象に当たる。
- 操作の取り消し: 確定した再試行は取り消せない。メール送信基盤が受理した通知は回収できない。

## FORM-11 削除済みフォームの回答を閲覧・削除し、通知を再試行する

- **利用者**: 回答の閲覧権限・回答の削除権限・通知設定の権限を持つメンバー（閲覧、削除、通知の確認と再試行のそれぞれに、対応する権限が要る）
- **目的**: スキーマの反映で削除したフォームの回答を、受付時の意味のまま扱い終える。
- **要件**: 6.5, 8.2, 8.3, 9.1

### 正常系

1. 開発者が、フォームを削除するスキーマを反映する。CMS は、そのフォームの新規受付を終了する。保存済みの回答は、受付時のフォームと通知定義の情報とともに、各回答の受付時の保持方針に従って保持する。未送信の通知は取り消さずに送る。
2. 回答の閲覧権限または回答の削除権限を持つメンバーが、FORM-07 の一覧でフォームの絞り込みから削除済みフォームを選ぶ。CMS は、削除済みフォームを、削除の時点の表示名称で、現行のフォームと区別して示す。フォームの一覧と、回答の一覧のフォームの絞り込みは、この名称を使う。
3. メンバーが回答を開く。CMS は、FORM-07 と同じく、受付時の項目、表示名称、選択肢、入力内容、問い合わせ対象の送信時の情報を示す。回答ごとの表示は、フォームの削除の時点の定義でなく、その回答の受付時の表示名称を使う。
4. 回答の削除権限を持つメンバーが、FORM-08 と同じ手順で回答を削除する。複数の回答を選んだ削除の扱いも FORM-08 に従う。
5. 通知設定の権限を持つメンバーが、FORM-09 の回答の一覧をフォームで絞り込み、削除済みフォームの通知の送信結果と失敗の理由を確認する。FORM-10 と同じ手順で再試行する。複数の通知を選んだ再試行と、繰り返しを一件として扱う規則も、FORM-10 と同じである。再試行は、受付時の通知定義と、現在の送信接続設定を使う。
6. 削除済みフォームの通知先は、そのフォームの回答が残る間保持する。通知設定の権限を持つメンバーは、FORM-02 と同じ操作で通知先を修正してから再試行できる。

同じキーのフォームを後から追加しても、CMS は別のフォームとして扱う。削除済みフォームの回答と運用設定を、新しいフォームへ引き継がない。

### 異常系

- 行えない操作: 削除済みフォームでは、受付の有効化、通知定義の編集、保持方針の変更を示さない。受付を再開する場合は、開発者がフォームをスキーマに追加して反映し、メンバーが新しいフォームの運用設定を整える。
- 一覧表示用の項目: 削除済みフォームは現行スキーマに一覧表示用の項目を持たない。回答の一覧表示用の値は空で示し、部分一致の検索に該当しない。メンバーは、フォームと受付期間で絞り込んで見つける。
- 宛先が残らない: 削除済みフォームに有効な通知先がない場合、CMS は再試行を拒否し、理由を示す。メンバーは通知先を追加してから再試行する。
- 権限不足: 必要な権限は `spec/scenario/index.md` の「権限」に従う。
- リソース不在: 回答がすべて削除または自動整理された削除済みフォームは、フォームの絞り込みに現れない。開こうとした回答が既にない場合、CMS は回答が存在しないことを示す。
- 操作の取り消し: 回答の削除と再試行の取り消しは、FORM-08 と FORM-10 に従う。フォームの削除は管理画面から取り消せない。
