# 送信失敗を対処済みとして記録する

操作は、組ごとに、確認した回を添える。断りが無い限り、確認した回は、「通知と宛先の組を一覧する」が返した、その組の今の `retryRound`。

| ID | 前提条件 | 操作 | 期待結果 |
|---|---|---|---|
| TC-webhook-markDeliveryFailureHandled-01 | アプリ連携の権限を持つメンバー。宛先 B の送信が送信失敗（未対処）の通知 | その組を指定して対処済みとして記録する | 対処済みになった組を返す。B の送信は送信失敗のまま、対処済みになり、記録したメンバーと日時を持つ。未対処の送信失敗の件数は 1 減る。操作履歴に残さない |
| TC-webhook-markDeliveryFailureHandled-03 | アプリ連携の権限を持つメンバー。宛先 B の送信が送信失敗（未対処）の通知。B は削除されている | その組を指定して対処済みとして記録する | B の送信は送信失敗のまま、対処済みになる |
| TC-webhook-markDeliveryFailureHandled-04 | アプリ連携の権限を持つメンバー。通知 N1 の宛先 B の送信は送信失敗（未対処）。通知 N2 の宛先 B の送信は、メンバーが選んだ後に、ほかのメンバーの再試行で送信待ち（手動）になった | 二つの組を一度に指定して対処済みとして記録する | エラーにしない。N2 の組を理由 `notFailed` とともに返す。どの組も変わらず、N1 の組は未対処のまま |
| TC-webhook-markDeliveryFailureHandled-05 | アプリ連携の権限を持つメンバー。宛先 B の送信が送信失敗（未対処。`retryRound` は 0）。メンバーが選んだ後に、ほかのメンバーの再試行が再び送信失敗（未対処。`retryRound` は 1）で終わった | その組を、確認した回 0 を添えて対処済みとして記録する | エラーにしない。その組を理由 `notFailed` とともに返す。送信は未対処のまま変わらない |
| TC-webhook-markDeliveryFailureHandled-07 | アプリ連携の権限を持つメンバー。送信失敗（未対処）の組 R と、次の自動の試行を待つ送信待ちの組 P がある。通知 N は宛先 A の送信だけを持つ | R、存在しない通知の組 X、N と送信の無い宛先 C の組 Y、P を一度に指定して対処済みとして記録する | エラーにしない。X と Y を理由 `notFound`、P を理由 `notFailed` とともに返す。どの組も変わらず、R は未対処のまま |
| TC-webhook-markDeliveryFailureHandled-10 | アプリ連携の権限を持たないメンバー。送信失敗（未対処）の送信を持つ通知 | 対処済みとして記録する | `ForbiddenError`（`PERMISSION_MISSING`）。不足する権限（`integration:manage`）を示す。送信は未対処のまま |
| TC-webhook-markDeliveryFailureHandled-12 | アプリ連携の権限を持つメンバー。通知 N1 の宛先 B の送信は送信失敗（未対処）、通知 N2 の宛先 B の送信は、別のメンバーが記録した送信失敗（対処済み） | 二つの組を一度に指定して対処済みとして記録する | 受け付けた結果として、二つの組を、どちらも対処済みの状態で返す。N1 の組は、実行したメンバーと日時を持って対処済みになる。N2 の組は、記録したメンバーと日時が変わらず、送信の `version` は進まない |
| TC-webhook-markDeliveryFailureHandled-13 | アプリ連携の権限を持つメンバー。宛先 B の送信が送信失敗（未対処）。対処の記録が送信を読んだ後、確定までに、別のメンバーが同じ組の再試行を要求して確定する | 対処の記録を確定する | `ConflictError`（`STALE_VERSION`）。送信は送信待ち（手動）のままで、対処の状態を持たない |
