# 表示アプリへの通知を再試行する

断りが無い限り、送信は、定期ジョブが対象にするワークスペース W の通知の送信。「次の試行の時刻を過ぎた送信待ち」は、断りが無ければ、自動の再試行を待つ送信を指す。「定期ジョブを起動する」は、W を対象に起動することを指す。一つの送信の「送信の試行」の結果（`DeliveryDispatch.plan` と `WebhookDelivery.record` の例）は、[sendRequestedDelivery.md](sendRequestedDelivery.md) が持つ。

| ID | 前提条件 | 操作 | 期待結果 |
|---|---|---|---|
| TC-webhook-retryDueDeliveries-01 | 次の試行の時刻を過ぎた送信待ち（自動の 2 回目）の送信が一つある。宛先は 200 番台で応答する | 定期ジョブを起動する | その宛先へ一回送る。送信は送信成功になる。操作履歴に残さない |
| TC-webhook-retryDueDeliveries-02 | 次の試行の時刻を過ぎていない送信待ちの送信だけがある | 定期ジョブを起動する | 何も送らない。送信は変わらない |
| TC-webhook-retryDueDeliveries-04 | 次の試行の時刻を過ぎた送信待ち（自動の最後の回。`DeliveryPolicy.maxAutomaticAttempts` 回目）の送信。宛先は 500 で応答する | 定期ジョブを起動する | 送信は送信失敗（未対処）になる。以後、自動の再試行を行わない |
| TC-webhook-retryDueDeliveries-05 | 最初の試行を待つ送信待ちの送信と、手動再試行を待つ送信待ち（手動）の送信。どちらも、作成または再試行の要求から `DeliveryPolicy.requestGraceMs` が過ぎていない | 定期ジョブを起動する | 何も送らない。送信は変わらない。送信の要求の消費者に任せる |
| TC-webhook-retryDueDeliveries-06 | 最初の試行を待つ送信待ちの送信と、手動再試行を待つ送信待ち（手動）の送信。どちらも、`webhook.delivery_requested` が届かないまま、作成または再試行の要求から `DeliveryPolicy.requestGraceMs` が過ぎた。宛先は 200 番台で応答する | 定期ジョブを起動する | それぞれの宛先へ一回送る。二つの送信は送信成功になる |
| TC-webhook-retryDueDeliveries-10 | 次の試行の時刻を過ぎた送信待ちの送信。通知の作成の後に、宛先の URL を変更し、秘密情報を置き換えた | 定期ジョブを起動する | 変更後の URL へ送る。送る通知の署名は、新しい秘密情報で検証でき、置き換え前の秘密情報では検証できない |
| TC-webhook-retryDueDeliveries-12 | 次の試行の時刻を過ぎた送信待ちの送信。宛先は 500 で応答する | 定期ジョブを一回起動する | その起動は、その宛先へ一回だけ送る。同じ起動の中で送り直さない |
| TC-webhook-retryDueDeliveries-15 | 次の試行の時刻を過ぎた送信待ちの送信が複数ある。定期ジョブが途中で中断する | 定期ジョブをもう一度起動する | 結果を記録済みの送信は変わらない。残りの送信を送る |
| TC-webhook-retryDueDeliveries-17 | 次の試行の時刻を過ぎた送信待ちの送信が三つある。どの宛先も 200 番台で応答する。一つ目の送信の結果の記録が、同じ送信へのほかの書き込みと競合する。二つ目の送信の結果の記録は、保存の失敗（`SystemError`）で確定しない | 定期ジョブを起動する | 一つ目の送信の、定期ジョブの試行の結果は記録されず、先に確定した書き込みの状態で残る。二つ目の送信は送信待ちのまま残る。三つ目の送信は送って、送信成功を記録する。定期ジョブは、失敗した送信を同じ起動の中で送り直さず、エラーを投げずに終える |
| TC-webhook-retryDueDeliveries-20 | 宛先 A へ送った後に結果が記録されず、送信待ち（自動の 2 回目）のまま残った送信。A は 200 番台で応答する | 定期ジョブを起動する | A へ、前に送った通知と同じ `notificationId` と `sequence` を持つ通知をもう一度送る。送信は送信成功になる |
