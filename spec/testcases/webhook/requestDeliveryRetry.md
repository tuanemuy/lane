# 送信失敗の通知を再試行する

操作は、組ごとに、確認した回を添える。断りが無い限り、確認した回は、「通知と宛先の組を一覧する」が返した、その組の今の `retryRound`。「送信待ち（手動）」は、手動再試行を受け付けた送信を指す。

| ID | 前提条件 | 操作 | 期待結果 |
|---|---|---|---|
| TC-webhook-requestDeliveryRetry-01 | アプリ連携の権限を持つメンバー。宛先 A の送信が送信成功、宛先 B の送信が送信失敗（未対処）の通知。B は登録されている | その通知と宛先 B の組を指定して再試行を要求する | B の組の再試行を始めた結果を返す。B の送信は送信待ち（手動）になり、次の試行の時刻は要求の時刻で、直前の試行として送信失敗の日時と失敗を持ち、対処の状態を持たない。`retryRound` は 1 になる。A の送信は変わらない。`webhook.delivery_requested`（ペイロードは、通知の ID と宛先 B の ID）を一件記録する。操作履歴に残さない。このユースケースは宛先へ送らない |
| TC-webhook-requestDeliveryRetry-02 | アプリ連携の権限を持つメンバー。通知 N1 の宛先 A と宛先 B の送信と、通知 N2 の宛先 B の送信が、どれも送信失敗 | 三つの組を一度に指定して再試行を要求する | 三つの組は送信待ち（手動）になる。それぞれの送信の `version` が 1 進む。`webhook.delivery_requested` を組ごとに一件、合わせて三件記録する |
| TC-webhook-requestDeliveryRetry-04 | アプリ連携の権限を持つメンバー。宛先 B の送信が送信失敗（対処済み）の通知 | その組を指定して再試行を要求する | B の送信は送信待ち（手動）になり、対処の状態を持たない。再試行の前の対処済みを引き継がない。イベントを記録する |
| TC-webhook-requestDeliveryRetry-05 | アプリ連携の権限を持つメンバー。送信失敗の送信を持つ通知。対象のコンテンツは完全削除されている | その組を指定して再試行を要求する | 送信は送信待ち（手動）になる。イベントを記録する |
| TC-webhook-requestDeliveryRetry-06 | アプリ連携の権限を持つメンバー。通知 N1 の宛先 B の送信と、通知 N2 の宛先 B の送信が送信失敗（どちらも `retryRound` は 0）。メンバーが二つの組を選んだ後に、ほかのメンバーが N2 の組を再試行し、N2 の送信は送信待ち（手動。`retryRound` は 1） | 二つの組を、確認した回 0 を添えて、一度に指定して再試行を要求する | エラーにしない。N1 の組は再試行を始めた、N2 の組は再試行が先に始まっていた（`alreadyRequested`）、という結果を返す。N2 の結果は、今の状態（送信待ち）を持つ。イベントは N1 の一件だけ。N2 の送信は、`retryRound` 1 の送信待ち（手動）のまま変わらない |
| TC-webhook-requestDeliveryRetry-07 | アプリ連携の権限を持つメンバー。宛先 B の送信が送信失敗（`retryRound` は 0）。メンバーが、確認した回 0 を添えて再試行を要求し、その再試行が再び送信失敗（未対処）で終わった | 同じメンバーが、同じ操作（確認した回 0）をもう一度行う | エラーにしない。その組は `alreadyRequested` で、今の状態（送信失敗と、新しい失敗）を返す。送信は `retryRound` 1 の送信失敗（未対処）のまま変わらない。イベントを記録せず、二通目を送らない |
| TC-webhook-requestDeliveryRetry-10 | アプリ連携の権限を持つメンバー。通知 N1 の宛先 B の送信は送信失敗、通知 N2 の宛先 B の送信は、次の自動の試行を待つ送信待ち（`retryRound` は 0） | 二つの組を、確認した回 0 を添えて、一度に指定して再試行を要求する | エラーにしない。再試行を始めず、N2 の組を理由 `notFailed` とともに返す。どの組も変わらない。イベントを記録しない |
| TC-webhook-requestDeliveryRetry-12 | アプリ連携の権限を持つメンバー。通知 N1 の宛先 B の送信と、通知 N2 の宛先 C の送信が送信失敗。メンバーが二つの組を選んだ後に、C が削除された | 二つの組を一度に指定して再試行を要求する | エラーにしない。再試行を始めず、N2 の組を理由 `endpointDeleted` とともに返す。どの組も変わらず、C の組は送信失敗のまま、対処の状態も変わらない。イベントを記録しない |
| TC-webhook-requestDeliveryRetry-13 | アプリ連携の権限を持つメンバー。送信失敗の組 R と、次の自動の試行を待つ送信待ちの組 P がある。通知 N は宛先 A の送信だけを持つ | R、存在しない通知の組 X、N と送信の無い宛先 C の組 Y、P を一度に指定して再試行を要求する | エラーにしない。再試行を始めず、X と Y を理由 `notFound`、P を理由 `notFailed` とともに返す。どの組も変わらない。イベントを記録しない |
| TC-webhook-requestDeliveryRetry-16 | アプリ連携の権限を持たないメンバー。送信失敗の送信を持つ通知 | 再試行を要求する | `ForbiddenError`（`PERMISSION_MISSING`）。不足する権限（`integration:manage`）を示す。通知は変わらない。イベントを記録しない |
| TC-webhook-requestDeliveryRetry-18 | アプリ連携の権限を持つメンバー。宛先 B の送信が送信失敗（未対処）。二人のメンバーが、同じ組の再試行を並行して要求する | 二つの要求を確定する | 一方だけが確定し、他方は `ConflictError`（`STALE_VERSION`）。イベントは一件だけ記録され、B へ送るのは一回。競合した側が同じ操作を送り直すと、その組は `alreadyRequested` になる |
| TC-webhook-requestDeliveryRetry-20 | アプリ連携の権限を持つメンバー。宛先 B の送信が送信失敗（未対処）で、B は登録されている。再試行の要求が宛先を読んだ後、確定までに、別のメンバーが B を削除して確定する | 再試行の要求を確定する | `ConflictError`（`STALE_VERSION`）。B の送信は送信失敗（未対処）のまま。イベントを記録しない。同じ操作を送り直すと、その組を理由 `endpointDeleted` とともに返す |
